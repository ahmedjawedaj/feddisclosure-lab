# v0.7 research protocols (declared before running)

## B1: Equal-capacity non-IID study

- **Question:** Does client label heterogeneity change global and worst-client accuracy when training and validation sizes and per-round training work are held constant?
- **Dataset:** approved public scikit-learn 8×8 digits. Holdout = first 20% of each 900-example seed cohort. Three clients each receive exactly 240 train+validation records (192 train, 48 validation).
- **Partitions:** IID, capacity-constrained class-conditioned Dirichlet α=0.1, α=0.5, α=10.0. The historical `label_skew` strategy is a contextual extreme and can be run separately. These configurations share the exact selected records and heldout cohort for a seed.
- **Preselected seeds:** 241, 242, 243. **Fixed training budget:** FedAvg 4 communication rounds, 2 local epochs, batch size 32, SGD LR 0.15, same architecture and initialization per seed. Identical client sizes imply identical minibatch counts and model-transfer bytes.
- **Observer:** honest-but-curious coordinator sees site model states and scalar metrics. Class histograms stay evaluator-only. Evaluation is a distinct process using public held-out data. No formal privacy protection.
- **Metrics:** final global held-out accuracy, global accuracy per round, worst-client global-model validation accuracy, between-site validation gap, per-client total record counts, optimizer minibatch counts, model-transfer bytes, and evaluator-only mean total-variation distance from global training-label distribution.
- **Hypothesis:** stronger heterogeneity may worsen worst-client utility; do not infer a monotone relationship if pilot data contradicts it.
- **Limits:** Three seeds and four rounds are exploratory, not statistical significance or convergence. Client class difficulty remains a potential confound; different label assignments can change validation difficulty despite equal sample/optimizer budgets. Not Flower or native Docker.

## D1: Differentially private per-site count adapter

- **Threat:** external analytics user can issue allowlisted query IDs and combine previously released noisy counts. A privileged site admin is outside this release threat model. Query rejection may leak information, so budget-exhaustion rejects must depend only on spent budget, never raw data.
- **Planned mechanism:** established OpenDP floating-point Laplace measurement, with count add/remove adjacency (one participant row can change the count by at most one); public sensitivity Δ=1; target pure-DP epsilon per release. Each participating site uses OpenDP on the exact local count *without data-dependent small-cell checks* and a shared principal-level, monotonically spent budget. Basic sequential composition epsilon_total = sum(epsilon_query), delta=0 **if** OpenDP mechanism/privacy-map verification and the release ledger both operate as specified.
- **Budget:** global per-site scope independent of attacker-controlled experiment ID. Transactionally reserve before release, rollback on failure. No query-dependent information in budget denials. No raw exact counts returned by this policy.
- **Acceptance:** actual OpenDP runtime, repeat-query exhaustion, rollback/failure tests, cross-experiment non-reset, no raw response, multi-site DP query, utility/error measurements. If OpenDP cannot be installed, the mechanism cannot be marked verified and no epsilon guarantee is claimed.
- **Not equivalent to:** current deterministic small-cell threshold/history suppression, Gaussian gradient noise, Opacus DP-SGD, or cryptographic secure aggregation.

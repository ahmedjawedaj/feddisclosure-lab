# FedDisclosure Lab v0.11.0 — native gate preparation and retry safety

2026-11-20. Educational research only, using synthetic/public data. **This is not a formal DP/SecAgg+ certification.**

## Executed milestone — retry-safe per-site count release

Prior behavior: a gateway request that partially succeeds can spend site epsilon before a failed aggregate is returned. Blindly retrying makes fresh independent releases and consumes additional budget. New behavior: when the caller supplies an allowlisted `request_id` (12–100 alphanumeric, underscore or hyphen characters), the same principal/query/epsilon maps to one persisted released noisy answer. The ledger increment, computed release and cached answer are committed atomically inside a SQLite `BEGIN IMMEDIATE` transaction. A mismatched query or epsilon with an existing retry ID is rejected. A retry after restart or concurrent retries reuse the existing released answer. Omitted request IDs preserve legacy behavior to enable a matched comparison.

The gateway forwards the same `request_id` to all sites, requires the returned ID to match, and returns no partial count when a site fails. The gateway does not yet provide a general distributed commit protocol or rollback for a newly created release that fails halfway through the federation.

### Measured fault-injection comparison

`python scripts/benchmark_retry_safety.py` exercised three HTTP ASGI institution apps, one gateway, a deterministic fake count mechanism (not DP), and an initial simulated failure at institution C. The exact sequence and ledgers are recorded in `reports/results/sprint4/retry_benchmark.json`.

| Case | HTTP outcomes across 3 attempts | Site A epsilon units | Site B | Site C |
|---|---|---:|---:|---:|
| No request ID | 409, 200, 409 | 0.50 | 0.50 | 0.50 |
| Stable request ID | 409, 200, 200 (cached replay) | 0.25 | 0.25 | 0.25 |

The stable third response was **the same cached answer**, not a third independently randomized release. The fake mechanism is used ONLY for software, transaction, and HTTP tests. Its `epsilon` bookkeeping describes intended spend, not a mathematical privacy guarantee.

### Scientific caveats

- A nonprivate query route must remain disabled when actual DP accounting applies, including across database restarts.
- Epsilon composition is scoped to one research principal in one site; multiple real-world user identities and federated accounting are future deployment work.
- A released answer stored in SQLite is sensitive operational state. Site storage must be permission-isolated; the current local OS is a development environment.
- OpenDP privacy statements need verified count sensitivity, add/remove adjacency, a native randomized mechanism, correct prior-release history, composition assumptions, and applicable adversary capabilities.
- The benchmark is not a defense against every adaptive-query or all-but-one-collusion attack.

## Native Flower, OpenDP, Opacus, Docker and upstream SecAgg+

The runtime still has no Docker CLI or daemon and cannot install Flower/OpenDP/Opacus because the package-index host cannot be resolved. The concrete availability result is saved as `reports/results/runtime_gates/v011_preflight.json` in the full archive.

Added a separate Flower 1.27 SecAgg+ research app at `experiments/flower_secagg/`, using ONLY upstream `SecAggPlusWorkflow` and `secaggplus_mod`. It assumes three participants, three shares, and a reconstruction threshold of two. This configuration does not rule out all-but-one collusion. A successful workflow return is not a standalone proof of cryptographic security, dropout tolerance, or hospital-grade isolation. Native execution is **unverified**.

The multi-component GitHub Actions workflow `.github/workflows/native-v1-certification.yml` is prepared to run on a Docker-capable network-enabled runner and check the native evidence with `scripts/verify_native_release.py`. Those workflows have not been executed because this repository has no authorized GitHub remote. Static source tests and PyTorch reference runs are not substitutes.

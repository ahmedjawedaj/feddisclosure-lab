# FedDisclosure Lab v0.15: pre-registered tests of what secure aggregation, differential privacy and their checks actually show

Ahmed Jawed. Draft technical report for release 0.15.0, 2026-11-23. Not peer reviewed. Every number below is copied from the saved files under `reports/results/privacy/v0150/` and from the `docs/v0.15-*.md` notes, and `scripts/verify_readme_claims.py` checks the README copy of the headline numbers against those files.

## Abstract

FedDisclosure Lab is a benchmark for measuring how much a federated learning system discloses. Release 0.15.0 adds eight work packages, each judged against numeric pass rules that were written before the runs: a proof and property tests for the error of one SecAgg+ round, a closed-form bound on reconstruction under differential privacy checked against an informed attacker, a wire-level check on a deployed Flower stack, a seeded-fault matrix, comparisons with external attack implementations, a reply-order study with an opt-in deterministic aggregation, a scaling study to 8 clients, and a second dataset. Of 26 pre-registered predictions, five failed and are reported as failures: a float32 bias claim (E2), a closeness-to-bound claim for same-label candidates (D3), a comparison with a tuned external inversion attack (B1, ratio 1.86), a reply-order claim for the shipped 4-client configuration (P2) and a Fashion-MNIST ordering claim that missed by 0.6 points (X1). Several passes are weak and are labelled so. The main reading is that a naive aggregate-only attack learns less than the labels alone give, that this says the attack is weak and not that the aggregate is private, and that n-1 collusion recovers the victim update about as well at 8 clients as at 4. Most attack results come from an observation model with real quantiser arithmetic. The deployed stack was checked at 4 clients, one round and one local step.

## 1. Scope and what is simulated

Two kinds of evidence appear in this report and they are kept apart throughout.

* **Observation model.** The attacker is given the object a protocol is supposed to expose, built in process with the real upstream SecAgg+ quantiser arithmetic, real Opacus noise or real PyTorch training. Proofs, property tests, the DP bound study, the fault matrix, the scaling attack study and the Fashion-MNIST study are of this kind.
* **Deployed stack.** Flower 1.27.0 SuperLink, SuperNodes and client apps in Docker Compose on GitHub hosted runners. The wire capture (4 clients, one round), the live parity runs (3 and 4 clients) and two 8-client memory rounds are of this kind. No attack was run on captured traffic from an 8-client stack.

Nothing here is a formal privacy or security certification. A failed reconstruction is evidence about one attack, not a guarantee.

## 2. Setup

**Data and model.** Primarily the 1,797 public 8x8 scikit-learn digits and a 2,410-parameter MLP (`DigitMLP`, 64 inputs, 10 outputs). The second dataset is the Fashion-MNIST training split (MIT licence, loaded at run time, not redistributed) with a 9,098-parameter CNN. Clients hold 8 distinct records each and take one full-batch SGD step (learning rate 0.15 unless stated). Client 0 is the victim.

**Attacker views.** Plaintext update, SecAgg+ aggregate only (the attacker holds all labels), n-1 collusion (the aggregate minus the other clients' updates) and, for DP, the noised update. The inversion attack is gradient matching with known labels, known initial model and known learning rate. "Recognisable" means per-image MSE below 0.05.

**Baseline.** Every inversion number is shown next to the label-only floor, which rebuilds each victim record as the class-average image of a public pool. It is a reference for prior knowledge and not an attack. It reached 67.5% recognisable on seeds 0 to 9 (v0.14.3) and 75.0% on 30 seeds, because later seeds are easier.

**Pre-registration.** `docs/preregistration/v0.15.md` was committed before the runs. It fixes seeds (evaluation seeds 0 to N-1, tuning seeds 9000 and up), intervals (Wilson for rates, Clopper-Pearson against formal bounds, percentile bootstrap over seeds for continuous metrics) and a pass rule per prediction. A threshold is never changed. When a rule was ambiguous, the reading used and the result under the other reading are in its deviation log. Wilson intervals pooled over images are optimistic because the 8 images of a seed share an initial model, so seed-level bootstrap intervals are shown where it matters.

## 3. Work packages

### 3.1 One-round SecAgg+ error (E1, E2, E3, M1)

**Method.** The note `docs/proofs/one-round-secagg-error.md` states and proves, for upstream Flower 1.27.0 arithmetic (clipping range c = 8, quantisation range Q = 2^22, n clients, T the sum of integer weights), that the error of the dequantised weighted mean against the integer-weighted mean is below 2cn/T in the worst case. With independent client randomness a Hoeffding bound of order (2c/T) sqrt((n/2) ln(2d/delta)) holds with probability 1 - delta over all d coordinates. A separate term covers weight rounding when client sizes differ. The searches in `scripts/run_secagg_bound_search.py` check the statements on real upstream code.

| ID | Rule | Observed | Verdict |
|---|---|---|---|
| E1 | zero counterexamples in at least 10,000 float32 cases with unequal sizes | 0 in 20,000 cases, largest error 0.91 of the bound | PASS |
| E2 | a counterexample to the float64-only bound exists for float32 inputs, or the float32 term is below 1e-6 of the bound | none found, float32 bias up to 3/16 of a unit (0.1875 measured) and never breaks 2cn/T | FAIL |
| E3 | independent-RNG 99th percentile below the Hoeffding bound for 4 to 256 clients, and a violation at 256 clients with a shared seed | 0.67 to 0.73 of the bound, and 3.9 to 7.2 times the bound at 256 clients with a shared seed (7.2 with identical data) | PASS |
| M1 | two-round ReLU counterexample reproduced and no violation of the convex L2 bound in 1,000 trials | reproduced (fraction of tiny-model trials above twice the one-round bound 0.335), 0 violations in 1,000 trials | PASS |

**What failed and what it means.** E2 predicted that float32 clients add a bias the float64 bound misses. The bias exists (up to 3/16 of a quantisation unit per client, deterministic) but a client error never reaches a full unit, so the float64 bound survives. At 4 clients the Hoeffding bound is weaker than the worst case, so E3 is weak there. The proof is for quantisation error only and says nothing about privacy.

### 3.2 DP against an informed attacker (D1 to D5)

**Method.** A replication of the reconstruction-robustness setting of Hayes, Mahloujifar and Balle. One full-batch step with the real Opacus 1.6.0 engine, clipping norm 1.0, noise multiplier sigma in {0.2, 0.5, 1, 2, 4}, 8 records. The attacker knows the other 7 records and a list of u candidates for the eighth. For u equally likely candidates the success probability is at most Phi(Phi^-1(1/u) + 1/sigma) under add-or-remove adjacency. The study also computes the exact optimal success on the actual candidate sets by Monte Carlo over the noise. 1,000 trials per cell, evaluation seeds 0 to 999.

| Candidates (u = 10, chance 0.100) | sigma | Attack success (Clopper-Pearson 95%) | Exact optimum | Bound |
|---|---|---|---|---|
| same label | 0.2 | 0.662 [0.632, 0.691] | 0.681 | 1.000 |
| same label | 0.5 | 0.305 [0.277, 0.335] | 0.295 | 0.764 |
| same label | 1 | 0.174 [0.151, 0.199] | 0.185 | 0.389 |
| same label | 2 | 0.137 [0.116, 0.160] | 0.137 | 0.217 |
| same label | 4 | 0.096 [0.078, 0.116] | 0.118 | 0.151 |
| any label | 0.2 | 0.942 [0.926, 0.956] | 0.946 | 1.000 |
| any label | 0.5 | 0.616 [0.585, 0.646] | 0.613 | 0.764 |
| any label | 1 | 0.336 [0.307, 0.366] | 0.325 | 0.389 |
| any label | 2 | 0.193 [0.169, 0.219] | 0.195 | 0.217 |
| any label | 4 | 0.129 [0.109, 0.151] | 0.143 | 0.151 |

D1 PASS (no cell exceeds the bound plus 0.01, 50 comparisons of which 25 are distinct). D2 PASS (Wilson lower limit 0.632 same-label and 0.926 any-label at sigma 0.2). D4 PASS (success falls with sigma for all five candidate sets, with non-overlapping Wilson intervals). D5 PASS (the exact optimum lies between attack and bound up to Monte Carlo error).

**What failed.** D3 asked for the attack to be within 0.05 of the bound at sigma 4 with 10 candidates. Any-label candidates pass (gap 0.022). Same-label candidates miss (gap 0.055). The same-label attack is also 0.022 below the exact optimum for its own candidate sets, about 2.2 standard errors, which this report does not explain. D1 is vacuous in two cells where the 0.01 slack exceeds the bound itself, so the exact-optimum column is the tighter evidence.

**Limits.** Record-level privacy of one Gaussian mechanism invocation, no accountant, no composition and no epsilon claim. It is not client-level privacy and says nothing about several local steps, which are a stronger threat model.

### 3.3 Wire-level validation (W1 to W6)

**Method.** A recording proxy wraps the ServerApp grid and records every message and hash across the four SecAgg+ stages. A TCP relay in front of each SuperNode logs byte counts and dumps the stream. A matched plaintext run per seed gives the control. Four clients, eight records each, one round, 5 seeds, Flower 1.27.0 on a GitHub hosted runner (run 45075971652).

| ID | Observed | Verdict |
|---|---|---|
| W1 | 0 of 40 victim images recognisable from one masked vector (Wilson upper limit 0.088), label floor 72.5% | PASS, vacuous |
| W2 | worst coordinate error 3.74e-4 against the proven bound 4.77e-4, which is 78% of the bound, 5 runs of 2,410 coordinates | PASS |
| W3 | captured aggregate 60.0% recognisable (Wilson 44.6% to 73.7%), simulated 57.5% (42.2% to 71.5%), mean MSE 0.0557 against 0.0528 | PASS, pooled, low power |
| W4 | plaintext mode 97.5% recognisable (Wilson lower limit 0.871), 20 of 20 relay updates equal the proxy record | PASS |
| W5 | sample counts visible in 20 of 20 SecAgg+ replies, the metrics record present in 20 of 20 but empty | PASS for counts only |
| W6 | 100 of 100 proxied objects found in the relay stream | PASS |

**Caveats.** W1 passes because the attack gets nothing from a single masked vector, which is expected, and not because it sits at the floor. W3 uses pooled rates. Per-seed rate gaps (captured minus simulated) are +0.25, 0, -0.125, -0.25 and +0.25, four of five exceed the 10 point tolerance, and a per-seed reading would fail. W5 is limited because the repository client returns no metric values. The result supports the observation model at 4 clients and one round and no further.

### 3.4 Seeded-fault matrix (F1, F2)

**Method.** Five fault types are injected one at a time: wrong DP noise scale (factors 0.25, 0.5, 2), skipped clipping, plaintext fallback, wrong threshold or dropout handling, and a stale global model. Detectors: the existing verifiers run on tampered copies (A), a white-box DP audit (ten real Opacus runs per audit, chi-square at level 0.01, plus a clip audit) (B), a black-box informed attack (C), the one-round error bound (D1) and an added test of the error distribution (D2). 200 audits per condition.

| Fault | Caught by |
|---|---|
| DP noise x0.25, x0.5 | B (power 1.000), C (1.000 and 0.950) |
| DP noise x2 | B only (C cannot see extra noise) |
| Clipping skipped | clip audit only (noise audit 0.010, C 0.350) |
| Plaintext fallback | none of A, B, C, D1. D2 only (power 1.000) |
| Dropout and threshold handling | A (the cached-update variant also by D1 and D2) |
| Stale model | A, D1, D2 |

F1 PASS by the strict count: 4 of 5 faults detected by the specified detectors, the evading fault named (plaintext fallback). With the D2 extension it is 5 of 5. F2 PASS: the noise audit has power 1.000 at factors 0.25, 0.5 and 2 with a false positive rate of 0.010 [0.001, 0.036].

**What it shows.** A plaintext aggregate is closer to the independent recomputation than a real SecAgg+ aggregate is, so numerical gates pass it. The existing verifiers record `secure_aggregation_enabled` but no rule reads it. The gap is a missing check on the workflow marker, and D2 needs the honest client vectors, which a deployment auditor does not have. The naive two-round tolerance of 2 times the one-round bound is exceeded by honest runs 35% of the time, so it is a weak check.

**Limits.** Faults are simulated or written into copies of saved real evidence, and no faulty stack was deployed. Two variants test how a verifier reads evidence and not how a deployed stack behaves. Mask reuse was not seeded. The faults are large, and small or partial faults were not injected.

### 3.5 External baselines (B1, B2)

**Method.** B1 matches the 4-client one-step setting of the inversion study (20 seeds, 8 victim records, plaintext update, known labels) and gives the repository attack and `breaching` 0.1.2 the same gradient. Three `breaching` configurations are used: the shipped Inverting Gradients setting, a known-label DLG setting, and a configuration with its total-variation scale chosen on tuning seeds 9000 to 9002. The tuned one is the registered headline. B2 scores the saved 64 shadow and 16 target LiRA models with the repository LiRA and with `mialibrary` 0.1.5 in four variants.

| Attack | Mean MSE (95% bootstrap) | Recognisable |
|---|---|---|
| Label-only floor | 0.0423 (0.0390 to 0.0458) | 0.738 |
| Repository gradient matching | 0.0115 (0.0080 to 0.0154) | 0.956 |
| breaching, shipped Inverting Gradients | 0.0482 (0.0428 to 0.0536) | 0.731 |
| breaching, DLG with known labels | 0.0246 (0.0171 to 0.0323) | 0.850 |
| breaching, tuned (headline) | 0.0062 (0.0040 to 0.0087) | 0.994 |

**B1 FAIL.** The ratio of repository MSE to the tuned external MSE is 1.86 with a seed bootstrap 95% interval of 1.47 to 2.51, against a limit of 1.5. The paired MSE difference is +0.0053 (0.0030 to 0.0079) and the repository attack is lower in only 3 of 20 seeds. Against the two shipped configurations the ratios are 0.24 and 0.47 and B1 would pass. The tuned configuration got a search and the repository attack got none, and iterations were not equalised (4,000 against 300), so the comparison favours `breaching`. Both attacks recover most records from a plaintext update. **Consequence:** every statement that an aggregate view sits at or below the floor is conditional on the weaker attack.

**B2 PASS.** Repository LiRA mean AUC 0.7416 (0.7258 to 0.7577) against 0.7401 (0.7238 to 0.7563) for the strongest `mialibrary` variant, paired difference +0.0015 (-0.0003 to +0.0035), limit -0.03. This covers one no-DP overfit setting. `mialibrary` is new and declares no licence, so agreement with it is modest evidence. An independent reimplementation agrees with it to 1e-14.

### 3.6 Reply order and deterministic aggregation (P1 to P3)

**Method.** Flower 1.27 `FedAvg` sums float32 updates in the order replies are handed over, and float addition is not associative. A replay study in plain PyTorch retrains every client in every round and aggregates under every reply order (6 for 3 clients, 24 for 4) with upstream arithmetic and with `DeterministicFedAvg`, an opt-in strategy that sorts replies by site id and accumulates in float64. The unchanged float64 gate (1e-5) is applied. The replay reproduces the saved native final models bit for bit in 7 of 7 runs and the saved gate gaps exactly.

| Run | Clients, rounds | Upstream pass rate over orders | Deterministic pass rate |
|---|---|---|---|
| run-mnist-full-iid-seed3 | 3, 10 | 0% (worst difference 1.3e-02) | 100% |
| run-mnist-full-labelskew | 3, 10 | 0% (6.9e-03) | 100% |
| the 5 other native runs | 3, 2 or 10 | 100% | 100% |
| shipped 4-client Digits, 2 rounds (primary for P2) | 4, 2 | 100% (3.0e-08) | 100% |
| 4-client Digits, 10 rounds (exploratory) | 4, 10 | 100% (8.9e-08) | 100% |
| 4-client MNIST, 10 rounds (exploratory) | 4, 10 | 83.3% (20 of 24) | 100% |

**Results.** P1 PASS in replay only (7 of 7 native runs, worst difference 0). The rule says native runs and they were not re-run with the strategy on. P2 FAIL: the pre-declared primary configuration passes for all 24 orders. Order dependence is shown for one of three 4-client setups and by two of the seven 3-client native runs, but P2 is about the shipped 4-client config. P3 asks whether reply order moves the victim MSE of the repository inversion beyond seed noise. The order effect is 3.2e-09 against a seed standard deviation of 0.0160, PASS, but a perturbation control shows the metric stays below the seed standard deviation even at a perturbation scale of 1e-2, so it cannot fail on this setup.

**Live runs.** Six hosted Docker runs (run 45076810526, three Digits configs with the strategy on and off) all pass the unchanged gate, and with the strategy on the checkpoint equals the reference bit for bit. None of these configs fails upstream, so the live runs confirm transport and client determinism and neither confirm nor refute P2.

**Credit and caveat.** Reply-order dependence in Flower was already discussed publicly (a thread on the Flower forum about non-determinism, and the BlazeFL project on deterministic federated simulation, Azuma and Nishio, arXiv 2604.03606). This work does not claim to have discovered it. It only measures how the effect interacts with the repository's own gate. With `DeterministicFedAvg` on, the gate tests transport and client determinism and no longer tests Flower's aggregation arithmetic. It is an opt-in workaround and the default is unchanged.

### 3.7 Scaling to 8 clients (S1, S2, S3)

**Method.** The inversion study with the client count as a parameter, 30 seeds (240 victim images per row), in-process with the upstream quantiser. The victim images of a seed are the same at 4 and 8 clients. A native 8-client Docker round measured memory with `docker stats` on a 4 CPU hosted runner. The server check that required one share per client was relaxed to allow fewer shares than clients (shares at least 3 and odd, threshold below shares), with unit tests against the upstream constructor.

| View | 4 clients | 8 clients |
|---|---|---|
| Label floor | 75.0% [69.2, 80.1] | 74.6% [68.7, 79.7] |
| Plaintext individual update | 95.0% [91.5, 97.1] | 95.0% [91.5, 97.1] |
| n-1 collusion (max weight 1000) | 90.4% [86.0, 93.5] | 90.8% [86.5, 93.9] |
| Aggregate only (max weight 1000) | 46.3% [40.1, 52.6] | 35.0% [29.2, 41.2] |

Recognisable rate with Wilson 95% intervals pooled over images.

S1 PASS, vacuous: the aggregate view at 8 clients is 35.0% against a floor of 74.6%, a gap of -39.6 points (seed bootstrap -47.5 to -32.1). The rule is one-sided and a two-sided reading would FAIL. The pass says this attack is weak, and it gets weaker with more clients. S2 PASS: collusion is 90.4% at 4 clients and 90.8% at 8, with Wilson lower limits 86.0% and 86.5% against the 85% rule. The collusion result is the real finding, because the victim is as recoverable at 8 clients as at 4. S3 PASS: the peak of the summed container memory was 3.25 GB at one poll against the 6 GB rule (largest single container 0.32 GB, 19 containers seen). Polls were about 4 seconds apart and the sum swung by up to 1.2 GB between polls, so the true peak is probably higher. A second hosted round with proper neighbourhoods (7 shares, threshold 4) peaked at 3.16 GB.

### 3.8 Fashion-MNIST (X1)

**Method.** The same protocol on 28x28 images with a 9,098-parameter CNN, 4 clients, 20 seeds (160 victim images per row). Attack settings were tuned on seeds 9000 to 9002 by lowest mean MSE.

| View | Recognisable, Wilson | Gap to floor, seed bootstrap (points) |
|---|---|---|
| Label floor | 58.1% [50.4, 65.5] | 0 |
| Plaintext individual | 86.3% [80.1, 90.7] | +28.1 [+20.6, +35.6] |
| n-1 collusion, max weight 1000 | 67.5% [59.9, 74.3] | +9.4 [+0.6, +18.8] |
| Aggregate only, max weight 1000 | 45.0% [37.5, 52.7] | -13.1 [-22.5, -3.8] |
| n-1 collusion, max weight 16 | 71.9% [64.5, 78.3] | +13.7 [+4.4, +23.1] |

**X1 FAIL.** Collusion is +9.4 points over the floor against a +10 rule. The seed bootstrap interval is +0.6 to +18.8, and about 0.475 of resamples reach 10 points, so the data cannot say whether another seed set would pass or fail, and the verdict stays FAIL. At the secondary max weight of 16 the rule would pass (+13.7). The reason was not tested. This row was not registered and does not change the verdict. The collusion attack setting sits at the edge of the tuning grid and the MSE tuning criterion disagrees with the rate criterion for this view, so a stronger attack may exist. The ordering of plaintext above collusion above floor above aggregate matches the digits study. The hosted Fashion-MNIST workflow has not been run.

## 5. Limits and threats to validity

* **Observation model.** Most attack numbers come from an in-process model of the protocol with real quantiser arithmetic. Wire capture supports it at 4 clients, one round, one local step, and not beyond. The 8-client numbers have no capture behind them.
* **Weak attacker.** B1 shows a tuned external attack beats the repository attack by a factor of 1.86 in MSE on the plaintext view. The aggregate and DP rows used the weaker attack and were not rerun with a stronger one. The DP rows of the v0.14 study use a naive attacker that does not model clipping or noise.
* **Vacuous and low-power passes.** W1 and S1 pass because the attack is far below the floor. W3 passes on pooled rates with 5 seeds. P3's metric cannot fail on its setup. P1 holds in replay. W5 covers counts only.
* **Small scale.** Small MLP and CNN, one local step, 8 records per client, known labels, known initial model and learning rate, one dataset family per study, one Docker host. Results do not transfer to larger models, several local steps or other data without new runs.
* **Statistics.** Pass rules are applied to point estimates and intervals are shown beside them. Images of one seed are not independent, so pooled Wilson intervals are optimistic. D5 compares the attack with its optimum on the same trials and shows a mild unexplained shortfall (paired z from -2.38 to +0.77, mean -0.52).
* **Tuning.** Attack settings were tuned on separate seeds, but the tuning criterion and search edges are documented limits for X1. Some operational readings of the rules (D2, D3, D4, F1, B1, S1 to S3) were recorded in code and commits and were not separately timestamped before the runs. Each is listed in the deviation log with the verdict under the alternative reading. No threshold changed.
* **Simulated faults.** The fault matrix deployed no faulty stack.
* **Reviews.** Independent reviews R2 to R4 led to wording corrections after the runs. They are in the deviation log and none changed a threshold or a result number.

## 6. Related work

Federated learning with secure aggregation builds on Bonawitz et al., who introduced practical secure aggregation, and on the SecAgg+ construction of Bell et al., which Flower implements. This work does not propose a protocol. It analyses the quantisation arithmetic of one implementation and checks what its captured traffic shows. Gradient inversion work includes Zhu et al. (deep leakage from gradients) and Geiping et al. (inverting gradients), whose method is available as the `breaching` library used here as an external baseline. The DP study replicates the reconstruction-robustness analysis of Hayes, Mahloujifar and Balle (arXiv 2302.07225) for one record-level Gaussian step, in simplified form. The closed-form bound here is derived directly from the Gaussian mechanism (see `docs/v0.15-dp-informed-attack.md`). The LiRA membership inference attack is that of Carlini et al., and the reference implementation used here is `mialibrary`. Opacus provides the DP-SGD engine and Flower the federation runtime. Reply-order non-determinism in federated aggregation has been discussed publicly, and this repository only measures its effect on its own parity gate.

## 7. Reproducibility

* Every verdict is in a `prereg_check_*.json` file under `reports/results/privacy/v0150/` with the rule copied from the pre-registration. `docs/v0.15-*.md` give the commands.
* An independent review (R4) regenerated the scaling study (61 JSON files), the DP informed trials, the fault matrix summary and the external inversion summary byte for byte, and the SecAgg+ bound search, the label floor and the recomputed intervals numerically, with only runtime or version fields differing. Docker runs, hosted workflows and attack tuning were not part of it.
* Local v0.15 runs used torch 2.15.0+cpu. The Docker image and the hosted workflows use torch 2.5.1. Opacus 1.6.0 needs torch 2.6.0 or newer, so the two do not share one environment. `docs/reproducibility-v0.15.md` lists which torch produced which evidence.
* The files that regenerate `prereg_check_parity.json` and `prereg_check_external.json` are tested against the committed copies. A fresh checkout lacks the git-ignored `data/` and `*.pt` files, and tests and scripts that need them skip or stop with a message.
* The fast test suite count depends on the installed packages, and the README gives it for the hosted CI environment and for a full environment, recorded with the commit.

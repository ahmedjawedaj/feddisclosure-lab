# v0.16 P2: what the Flower server observes with protections on

Status: released in 0.16.13. Not peer reviewed.
Pre-registration: `docs/preregistration/v0.16-p2.md`, committed alone as `43e931e` before the script and before any run.
Evidence: `reports/results/privacy/v0160/p2/flwr-1.27.0/p2_server_view.json` and the saved Docker runs in `reports/results/privacy/v0160/p2/flwr-1.27.0/s4_docker/`.
Harness: `scripts/audit_p2_server_view.py`, SHA-256 `636079925de64901aca06c429e05b40750e04dd0bffa602074f2155baa9fcdb7` (committed as `6f3b0be` before the full run). Metric returning client and strategy hook: `src/feddisclosure/training/p2_metrics_client.py` and `src/feddisclosure/training/p2_metrics_server.py`. Tests: `tests/privacy/test_audit_p2_server_view.py`.
Subject: `flwr` 1.27.0, SecAgg+ (`SecAggPlusWorkflow` and `secaggplus_mod`) and `flwr.server.strategy.DifferentialPrivacyServerSideFixedClipping`.

## Summary

All three pre-registered predictions held. No prediction failed, and no row was dropped or re-drawn. The run took 175.8 seconds, of which two Docker runs were most of the time.

1. S4 PASS. In two real Docker runs of the SecAgg+ stack (4 clients each) the three metrics that each client returned were present in the collect-stage reply that the ServerApp received, with the exact values that the client wrote to its own receipt (8 of 8 replies). The same values were in the `FitRes` objects that the strategy's `aggregate_fit` received (8 of 8). The array record of each of those replies held zero arrays (8 of 8).
2. S6 PASS, under the stated model. If a client's participation depends on its clipped update norm as modelled, the release bit predicts the norm class with accuracy 0.8425 (Wilson 95% interval 0.8259 to 0.8578) and the participant set with accuracy 0.8515 (0.8352 to 0.8664) over 2,000 rounds each. Controls with no dependence gave 0.5045 and 0.5035, and both intervals contain 0.5.
3. S6b PASS. With 9 results instead of 10 at `num_sampled_clients` 10, the measured sensitivity went from 0.1000 to 0.1111, the noise scale stayed at 0.1000 and the effective noise multiplier went from 1.0001 to 0.9001, a ratio of 0.9000. Exact epsilon at delta 1e-5 for one round went from 4.377 to 4.947.

These are statements about channels that the server process observes. They are not proofs of leakage. S4 shows that metric values reach the server, and says nothing about what anyone can infer from them. S6 rests on a dependence that this study assumes and did not observe. The accuracy of 0.85 is the number that the registered participation probabilities (0.85 for a high norm and 0.15 for a low one) give for a predictor that reads participation exactly, so the S6 result shows that the real strategy passes the participation through to the release bit and the result list without extra noise, and it does not show that any client behaves this way.

## S4 (Docker, real strategy)

Setup. `compose.flower.n4.yaml` plus `compose.wire.yaml`, driven by `scripts/run_wire_capture.py --modes secagg --seeds 2`. Four clients with eight public digits each, one round, one local full batch step, upstream `SecAggPlusWorkflow` with `num-shares` 4 and `reconstruction-threshold` 2. The ServerApp is the recording ServerApp of v0.15 with one more hook (`p2_metrics_server`) that saves what `aggregate_fit` receives. The ClientApp is the repository client plus `fit` metrics (`p2_metrics_client`): `probe_const` (1234.5 plus the site index), `train_loss` (the local cross entropy after the step) and `n_local`. Each client also wrote the dictionary it sent to a receipt in its own attestation mount. The Docker host is this sandbox. Run time was 89 seconds for seed 0 and 47 seconds for seed 1 (from `wire_run.json`).

| Check | Seed 0 | Seed 1 |
|---|---|---|
| S4a, the reply has a `fitres.metrics` record with exactly the three keys | 4 of 4 | 4 of 4 |
| S4b, the values equal the client receipt, one receipt per reply | 4 of 4 | 4 of 4 |
| S4c, the `FitRes` that reached `aggregate_fit` carries the same values | 4 of 4 | 4 of 4 |
| S4d, the array records of the reply hold zero arrays | 4 of 4 | 4 of 4 |

Example, seed 0, one client: `probe_const` 1234.5, `train_loss` 2.33266544342041, `n_local` 8, seen in the reply and in `aggregate_fit` and equal to the receipt of site 0. The record `fitres.parameters` was present in the reply and held zero arrays. The masked vector travelled as bytes in the `secaggplus_configs` config record (present in 4 of 4 replies of each run, descriptive). The sample count of 8 was visible in 4 of 4 replies. The recorded payload size was 19,928 bytes in all 8 replies, the same figure as in the v0.15 capture where the metrics were empty. The recorder sums array and bytes objects only, so this figure does not include the metric values and says nothing about message size as a channel. The four node identifiers that sent a collect-stage reply were visible to the server in each run (descriptive).

Flower logged `No fit_metrics_aggregation_fn provided` in the ServerApp. The application strategy does not aggregate the metrics, so they reach `aggregate_fit` and are not used there. Whether a deployment keeps, logs or discards them depends on its own strategy and was not examined.

The orchestrator retried the Flower CLI call of seed 0 once. Attempt 1 exited with code 1 and the message that the SuperLink was unreachable before any client event, attempt 2 completed. This is the retry built into `scripts/run_wire_capture.py` for a start order problem (deviation log entry 6 of the pre-registration). Seed 1 needed one attempt.

Relation to W5 of v0.15. W5 showed the sample count visible and the metrics record present and empty, because that client returned no metric. S4 closes the half that was not exercised. The new result is for floats and an integer in one run configuration. The same record and the same reading of the source apply to other values of those types, and that was not tested.

## S6 (in process, release bit and participant set)

Strategy driven: `flwr.server.strategy.DifferentialPrivacyServerSideFixedClipping(FedAvg(inplace=True, ...), noise_multiplier=1, clipping_norm=1, num_sampled_clients=10)`, through `configure_fit` and `aggregate_fit`, 16 float32 parameters, equal weights, 2,000 rounds per arm. Client 0 is the target. Its raw norm is drawn from Uniform(0.2 C, 1.4 C), its clipped norm is min(r, C), and the label is high when the clipped norm exceeds 0.8 C. A target with a high label participates with probability 0.85 and one with a low label with probability 0.15 (dependence arms), or both with probability 0.5 (control arms). The observer predicts high when the target participated.

| Arm | What a non-participating target does | Accuracy | Wilson 95% | Participation, high / low | Rounds with release rule as read from source |
|---|---|---|---|---|---|
| bit-dep | reported as a failure, nothing released | 0.8425 (1,685 of 2,000) | 0.8259 to 0.8578 | 0.833 / 0.148 | 2,000 |
| bit-ctl | same | 0.5045 (1,009) | 0.4826 to 0.5264 | 0.490 / 0.480 | 2,000 |
| set-dep | absent, 9 results, rescaled aggregate released | 0.8515 (1,703) | 0.8352 to 0.8664 | 0.865 / 0.163 | 2,000 |
| set-ctl | same | 0.5035 (1,007) | 0.4816 to 0.5254 | 0.492 / 0.486 | 2,000 |

Verdicts. S6-bit PASS (lower limit above 0.5 and accuracy within 0.03 of 0.85). S6-set PASS. S6-ctl PASS (both control intervals contain 0.5). S6-exact PASS (in every round of every arm the strategy returned nothing exactly when a failure was reported, and returned an aggregate with 9 plus the participation indicator results otherwise). S6-clip PASS (200 of 200 draws, worst relative error 9.1e-8 between the norm of the released single client update and min(r, C)). The mean clipped norm was 0.895 for rounds in which the target participated and 0.579 for rounds in which it did not (bit-dep), and 0.891 and 0.575 in set-dep. In the control arms the two means were 0.747 and 0.729, and 0.732 and 0.731.

Detection power of the control result. The rule excludes 0.5 from 1,044 correct predictions of 2,000 (accuracy 0.522). It finds a true accuracy of 0.531 with 80 percent power, which for the symmetric rule here is a difference of 0.062 between the participation probabilities of the high and the low class. The control arms therefore rule out a dependence of that size or larger for this threshold and this observer in this seed. They say nothing about a smaller dependence, a dependence on another function of the norm, or an observer that uses other signals. The power figures come from the exact binomial computation of the scratch file named in the pre-registration and are reproduced in `tests/privacy/test_audit_p2_server_view.py` (they are not stored in the evidence JSON). The size of the one sided rule at a true accuracy of 0.5 is 0.026, so each control interval excludes 0.5 by chance with probability about 0.05 and no re-draw was made.

## S6b (effective noise multiplier and exact epsilon)

Two configurations at n = 10, z = 1, C = 1, delta 1e-5, zero-out adjacency, one round, no amplification and no composition. M10 has 10 results. M9 has 9 results, with the target absent. The measured client is client 1, present in both. Sigma is from 20,000 runs per configuration (the two configurations use the same seeded noise draws, so their sigma is one measurement and not two, as in P1).

| Quantity | M10 | M9 | Predicted |
|---|---|---|---|
| Sensitivity of a present client | 0.100000 | 0.111111 | 0.1000 and 0.1111 |
| Noise scale sigma | 0.100012 | 0.100012 | 0.1000 |
| Effective noise multiplier | 1.0001 | 0.9001 | 1.000 and 0.900 |
| Ratio M9 over M10 | 0.9000 | | 0.900 |
| mu | 0.99988 | 1.11098 | |
| Exact epsilon at delta 1e-5 | 4.3766 | 4.9466 | 4.377 and 4.947 |

The noise is consistent with a Gaussian in a Kolmogorov-Smirnov check (p = 0.679 in both, a weak check because mean and scale are estimated from the same sample). Per coordinate sigma ranged from 0.09892 to 0.10128.

S6b-mix. In the set-dep arm 47.6 percent of the rounds had 9 results (predicted 0.50 within 0.03). Using the measured multiplier of each configuration for each round, the mean effective multiplier was 0.9866 in rounds with a high label and 0.9164 in rounds with a low label (predicted 0.985 and 0.915, each within 0.01). The mean of the per round exact epsilon over those rounds was 4.648. That mean is a descriptive average of independent per round values and is not a composed guarantee.

All five S6b rows passed (sensitivity, sigma, effective multiplier, epsilon, mixture). The factor is the one of row C4 of P1, z m / n with m / n = 0.9. It is small here because only one of ten results is absent. The effect is that the clients that remain have a weaker per round guarantee in the rounds where the target is absent, and whether the target is absent is correlated with its norm in this model.

## Power of each null result

1. Controls (S6-ctl). Stated above. Smallest true accuracy found with 80 percent power 0.531, difference of participation probabilities 0.062, 2,000 independent rounds, one seed per arm, two observers (release bit, participant set).
2. S4d. Exact for the recorded objects, with no sampling error. Positive controls in the tests: a reply with a non-empty array record fails S4d, a reply with the metrics removed fails S4a, a changed value fails S4b, and a changed strategy record fails S4c. The null covers the array records of the collect-stage replies only. It says nothing about the masked vector bytes, nor about the setup, share keys and unmask stages.

## Limits and what was not measured

Clauses that no script check covers are marked with an asterisk.

1. The dependence of participation on the norm is a modelling assumption. No real deployment was observed.
2. The nine other clients always respond with equal norm, weight and direction type. Background dropout, other failures and unequal weights (row C3 of P1) are not in the rounds.
3. The observer is told the direction of the dependence. An observer without it needs labelled rounds, which were not modelled.
4. S6 and S6b call the strategy class with a constructed result list and a constructed failure list. They do not run the SecAgg+ workflow, so how a real missing or failed client appears in `state.failures` is not exercised. The classes in `flwr.serverapp.strategy` and the other versions of `flwr` were not driven in this phase.
5. How a given deployment reports a missing reply (a timeout, an error message or silence) was not examined.*
6. S4 is one Docker host, four clients, one round, two seeds, the legacy strategy API with `SecAggPlusWorkflow`, two float metrics and one integer. Other metric types, large records and several rounds were not run.
7. S4 says the values reach the ServerApp process and the strategy. It says nothing about what can be inferred from them. The metrics were fabricated for the probe, and `train_loss` depends on the client's own records only through its local training.*
8. The relay streams of the two S4 runs were saved and not analysed. A network observer between a SuperNode and the SuperLink was not examined.
9. S4d counts arrays in array records of the collect-stage reply. It does not test that the masked vector carries no information about the update. That is W1 and W2 of v0.15 with their own limits.
10. The participant set and reply sizes in S4 are descriptive. Message timing and size as a channel (channel 8) were not measured. An active server (channel 7) is outside the assumptions of both protections and was not examined.
11. S6b epsilon values are per round, zero-out adjacency, delta 1e-5, Gaussian only, without sampling amplification, composition or an accountant. The sensitivity was measured for a client present in both configurations. The sensitivity of the target itself was not measured separately.
12. The S6b-mix numbers combine the measured M10 and M9 values with the participation of the S6 set-dep arm. They are not a separate measurement.
13. One seed per S6 arm, no multiplicity correction, tolerances chosen by the author. One in twenty control intervals is expected to exclude 0.5 by chance.
14. The text of the pre-registration says that the Docker image comes from a local rebuild. The rebuilt tag `feddisclosure-flower-exec:0.12.0` holds the working tree of the build time, and the `env` files of the saved runs hold paths of this sandbox.*
15. The repository history cannot prove that no mechanism ran before the pre-registration commit. The deviation log of the pre-registration lists what was read or probed before and after it.*
16. The wording of this document and of the README section was read against the evidence by hand.*

Not measured: the Message API strategies, `flwr` 1.44.0 or any release other than 1.27.0, the other fixed clipping variants and adaptive clipping, `LocalDpMod`, channel 5 as a sampling effect (only recorded), channel 7, channel 8, several rounds, more than four clients, another framework, and any inference attack that uses the observed bits or metrics.

## Reproduce

```bash
export PYTHONPATH=src:.
python scripts/audit_p2_server_view.py --out out/ --s4 run          # about 3 minutes, needs Docker and the images
python scripts/audit_p2_server_view.py --out out/ --quick --s4 skip # a few seconds, not evidence
python scripts/audit_p2_server_view.py --out out/ --s4 existing --s4-dir DIR
pytest tests/privacy/test_audit_p2_server_view.py
```

If the image build runs behind a proxy that re-signs traffic, set `FDL_BUILD_CA_BUNDLE` to the proxy's CA file. The Dockerfile already reads it through the `fdl_build_ca` secret.

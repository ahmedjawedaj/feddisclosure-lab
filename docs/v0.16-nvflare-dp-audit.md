# v0.16 T10: measured behaviour of NVIDIA FLARE's SVTPrivacy and PercentilePrivacy filters

Status: measured on `nvflare` 2.9.1 (not yet peer reviewed, not yet integrated in a release).
Pre-registration: `docs/preregistration/v0.16-nvflare.md` (committed before the harness existed and before any measurement of this phase).
Evidence: `reports/results/privacy/v0160/nvflare_dp_audit/nvflare-2.9.1/nvflare_dp_audit.json`.
Harness: `scripts/audit_nvflare_dp.py`. Tests: `tests/privacy/test_audit_nvflare_dp.py`.

## Summary

The harness calls the real `SVTPrivacy` and `PercentilePrivacy` classes of `nvflare` 2.9.1 in process on synthetic updates and compares the mechanism that executes with the one that the documented parameters and the filter's own accountant describe. The two source files are identical by sha256 in 2.8.3, 2.9.0 and 2.9.1 (a hash comparison made before the pre-registration was written, not a run). Only 2.9.1 was run.

18 pre-registered rows (13 for `SVTPrivacy`, 5 for `PercentilePrivacy`) were turned into 63 programmatic checks. All 18 rows held and all 63 checks held. No prediction failed. The full run took 149.6 seconds.

1. The accountant arithmetic matches the documented description. In all 16 cells of the (epsilon, n_upload) grid the ledger split is epsilon / (1 + (2 n)^(2/3)) for the threshold phase and the remainder for the query phase, with no relative difference at all (row N1). With the class defaults and 25,578 parameters one call records epsilon 255.9 and ten calls sum to 2559.0 with delta 0 (row N3). Of the 255.9, 255.8 comes from the release phase, because the default derives the release budget as n_upload times `noise_var`.
2. The Laplace scales that are drawn equal the formulas of the class docstring. For n 100 and epsilon 1 the recorded draws are one scalar of scale 3.520e-4 (gamma / epsilon_threshold), query draws of scale 2.058e-3 and a release draw of scale 2.000e-4, each equal to the expected value computed from the configuration with a relative difference of 0 (row N2).
3. The acceptance step does not stop after n_upload positive answers. It runs a whole pass over all remaining entries, so with epsilon 100 and 100 entries wanted, 656 of 1,000 entries were accepted in the single pass, 6.56 times n_upload (row N4). The release then samples n_upload entries from the accepted set.
4. The acceptance loop has no pass limit. At epsilon 0.1 a call returned after 1 pass, at 1e4 after 30 passes, and at 1e6 the call had not returned after the 10 second limit (row N5). With three entries at gamma and the rest at 0, the noise scale falls below the threshold tau and almost no zero entry is accepted.
5. No lower bound exceeded the claimed epsilon. For the release step (row N6a) the 95% Clopper-Pearson lower bound from 200,000 runs per input was 0.088 against a claimed epsilon_release of 0.2. For the selection step (row N6b) it was 0.871 against a claimed 20.0, which is above the 10.9 that this run count can certify, so that check has little power. Every run called the real `process_dxo`.
6. With the default `replace` True, the number of nonzero entries released is below n_upload in every one of 200 runs (mean 92.89, range 85 to 99 of 100), because repeated picks overwrite the same output cell. With `replace` False it is exactly 100 in all 200 runs (row N7). The ledger records n_upload either way.
7. Edge handling follows the prediction. Fraction 0 returns zeros for array entries, the scalar unchanged and an empty ledger. Fraction 1e-12 gives n_upload 1 (row N8). A scalar entry is returned unchanged and the ledger carries `has_scalar_passthrough` True and a note (row N9). In that one call the scalar took part in acceptance and received 1 of the 11 selected counts, so at most 10 array entries were released.
8. The generator is the global numpy one. The constructor has no seed argument, the same `numpy.random.seed` gives the same output and the state advances during a call (row N10). `START_RUN` clears the ledger and the sum (row N11). With `NUM_STEPS_CURRENT_ROUND` 5 the recorded scales are identical to those with 1 and the release noise in output units is 4.946 times larger (row N12).
9. `PercentilePrivacy` is deterministic. Zeroed entries are exactly 1,000, 5,000 and 9,000 of 10,000 for percentiles 10, 50 and 90. Entries above the cutoff and above gamma come out as sign times 4 times gamma, scalars are returned unchanged by value, and at percentile 100 one entry survives (rows P0 to P4). A plain Python float entry raises `AttributeError` in this filter, while a numpy float64 scalar works.

The documentation page for `SVTPrivacy` states the guarantee is scoped to the filter and is not an end-to-end accounting. These are measurements of one version under stated configurations. They are not statements about how the filters are meant to be used, and no epsilon of a deployment is reported.

## Setup

`nvflare` 2.9.1 is installed in a separate virtual environment (Python 3.13.18, numpy 2.5.5, Linux). `scipy` is not installed there, so the Clopper-Pearson helper is implemented with a pure Python incomplete beta function and checked against `scipy` in the tests when `scipy` is available. The harness imports only the two filter modules and the DXO, Shareable and FLContext classes. No NVFlare server, client, job configuration or training loop was started.

Every row builds `DXO(data_kind=WEIGHT_DIFF, data={...})`, `Shareable()` and `FLContext()` and calls `process_dxo`. Randomness is observed by wrapping `numpy.random.laplace` (recording scale and size, passing the call through) and the module function `_sample_partition_counts` (recording its `group_counts` and result, passing through). Seeds are fixed per row, derived from 20261125, and listed in the JSON. Logging is disabled during the runs.

Input values that the pre-registration did not name were chosen as follows. N1, N3 and the N11 call use all entries at 0.5 gamma. N2, N4, N6a and N7 use all entries at gamma as written or implied. N8 to N10 use small random float64 values of order gamma. P rows use standard normal values, 10,000 distinct, with percentile 10 and gamma 0.01 unless stated. N12 pools 200 calls per step count (the call count was not named). N6a and N6b run 200,000 calls of the real `process_dxo` per input, with a fresh filter instance every 10,000 calls to keep the ledger small.

The empirical bound is epsilon_lb = ln(p_lo_a / p_hi_b) with two-sided 95% Clopper-Pearson intervals (2.5% per tail) on both probabilities, taking the larger of the two directions. Taking the larger of two directions adds a small multiplicity that the bound does not correct for. N5 runs each epsilon in a fresh Python subprocess with a 10 second timeout that covers interpreter start and the `nvflare` import (0.24 to 0.30 seconds).

## SVTPrivacy accounting and scales (N1 to N3, N11, N12)

N1. The grid is epsilon in 0.1, 1, 10 and 100 against n_upload 1, 10, 100 and 1,000 (total parameters ten times n_upload at `fraction` 0.1). The ledger `epsilon_threshold` and `epsilon_query` equal the independently written formula in every cell. Acceptance took 1 pass in 15 cells and 3 in the cell (1, 10).

N2. With d 1,000, epsilon 1 and `noise_var` 0.1 the release epsilon is 10 and n_upload is 100. The recorded draws were 3 in number: one scalar draw, one query draw of size 1,000 (a single pass) and one release draw of size 100.

N3. The default `noise_var` 0.1 implies epsilon_release = n_upload times 0.1. For n_upload 2,558 that is 255.8 and the other two phases sum to the configured epsilon 0.1. Both the per-call ledger and the cumulative metadata report delta 0.0.

N11. The sum equals the ordered sum of the entries exactly. After `START_RUN` the ledger and the sum are empty and the next call (epsilon_total 2.1) starts a new sum.

N12. With 5 steps and entries of 5e-5 the filter divides by the step count, clips at gamma, adds noise of the recorded scale, then multiplies by 5. The measured mean absolute deviation of released values from 5 gamma was 9.909e-4 against 2.003e-4 for 1 step, a ratio of 4.946, from 17,988 and 18,115 released values.

## Acceptance and release (N4 to N7)

N4 and N5 concern the loop that accepts entries until n_upload are accepted. The pass is not cut at n_upload. The standard sparse vector technique stops at c positive answers, and here c is n_upload. The filter takes the whole pass and then samples n_upload entries from the accepted set. N5 shows the cost when the query noise is far below the threshold: the number of passes grows from 1 (epsilon 0.1) to 30 (1e4) and the call did not return at 1e6 within 10 seconds. The pre-registration did not predict a cause for the 1e6 case beyond the scale argument above, and the timeout was not investigated further.

N6a and N6b measure one event each. The bounds are lower bounds on the epsilon of the whole call restricted to that event, so a bound at or below the claimed value is the pre-registered expectation and not a proof of the claim. For N6a the two inputs (all +gamma and all -gamma) have the same absolute values, so selection is identically distributed and the difference is only in the release noise, whose claimed epsilon is 0.2. The sum of the two released values is a coarse statistic and the bound reached 44% of the claim. For N6b the selection step has a claimed epsilon of 20.0 and the run count cannot certify more than 10.9. The measured 0.871 is therefore a weak check.

N7. The nonzero counts for `replace` True were 85 to 99 with mean 92.89. This matches the expected number of distinct picks when 100 draws are made with replacement from about 650 accepted entries.

## Edge cases and randomness (N8 to N10)

N8. At `fraction` 0 the call returns before the accountant is reached, so no ledger entry and no budget metadata are created for that call. N9. The scalar is returned as a zero-dimensional numpy array holding 0.123. The group counts sorted by name were [1, 33] (scalar, array) and the selected counts [1, 10], so the scalar group received one of the 11 selected counts and released nothing for it. N10. The harness records the full constructor parameter list in the JSON.

## PercentilePrivacy (P0 to P4)

P0 to P4 all held with exact or zero differences. In P3 the single surviving entry is clipped to gamma, so the filter at percentile 100 releases one coordinate and sets the other 9,999 to zero. P4 used numpy float64 scalars. A Python float scalar in the same dictionary raised `AttributeError: 'float' object has no attribute 'ravel'`, recorded in the JSON as an observation and not as a check. The page for the filter makes no DP claim, so these rows make no accounting comparison.

## Limits

1. One framework version. Only `nvflare` 2.9.1 was run. The two source files are identical in 2.8.3 and 2.9.0 by sha256 only, and `svt_privacy.py` differs in 2.7.2, which has no `pure_dp_sum` accountant. The files were not run in those releases.
2. Synthetic updates in one process. No training, no real model, no NVFlare server, client, runner or job configuration. Where `data_kinds`, filter placement or the workflow would change what reaches the filter, that was not exercised.
3. No end-to-end guarantee was measured. The accountant is filter-level and the documentation says so. The rows compare executed noise and ledger arithmetic with the stated description. They do not establish or refute an epsilon for a training run.
4. The documentation text was read through a summarising fetch on 2026-11-25, so the quoted claim wording comes from that summary. The page gives no sensitivity bound, neighbouring definition or number of selected entries, so the reading used here is the one of the class docstring and the code.
5. The vendor issue tracker could not be read from this environment. A web search found no external audit of these filters at title level only.
6. N6a and N6b test one event each on one pair of inputs at one configuration, with a coarse statistic. A bound below the claim does not certify the claim. N6b cannot certify above 10.9 at 200,000 runs.
7. The chunk size of 1,000,000 entries in the filter was not exercised, because the largest vector has 25,578 entries. Thread use of the accountant lock was not exercised.
8. The environment has numpy 2.5.5, where the pre-registration states 2.5.3.
9. Input values and call counts that the pre-registration left open were chosen as listed under Setup, and results at other values were not run. The harness was written after the pre-registration commit in the same session, and predictions were written from code reading before the full run. The history cannot prove that no mechanism ran earlier than the commit order shows.

## Reproduce

```bash
python3 -m venv /tmp/nvflare_venv
/tmp/nvflare_venv/bin/pip install nvflare==2.9.1 pytest
/tmp/nvflare_venv/bin/python scripts/audit_nvflare_dp.py            # about 150 seconds, writes the evidence file
/tmp/nvflare_venv/bin/python scripts/audit_nvflare_dp.py --quick --out out/   # about 12 seconds
/tmp/nvflare_venv/bin/python -m pytest tests/privacy/test_audit_nvflare_dp.py
```

Quick mode uses 2,000 runs per input for N6, 40 runs for N7 and 20 calls per step count for N12. Quick output is not evidence. `--quick` requires `--out` so the committed evidence is not overwritten. Script sha256 of the evidence run: `7b41455704bdadd3ef925cd57135646b5ceeb9af07df4b61effa8f2081c9a84f`.

# v0.16 T10 pre-registration: measured privacy of NVIDIA FLARE's SVTPrivacy and PercentilePrivacy filters

Status: written before the harness exists and before any measurement of this phase. Date: 2026-11-25.
Subject: `nvflare` 2.9.1, files `nvflare/app_common/filters/svt_privacy.py` and `nvflare/app_common/filters/percentile_privacy.py`.

## Question

Does the mechanism that the two filters execute match the mechanism that their documented parameters and accountant describe, for the configurations below?

This is a measurement of one framework version under stated configurations. It is not a claim about how NVFlare is meant to be used.

## What "claimed" means here

The documentation page `user_guide/admin_guide/security/differential_privacy.html` (main branch, read on 2026-11-25) says that `SVTPrivacy` models one call as the composition of three pure-DP phases (threshold noise with `epsilon_threshold`, query noise with `epsilon_query`, release noise with `epsilon_release`), that `epsilon_call` is the sum of the three, that `epsilon_total` sums over calls with `delta` 0, and that "no subsampling amplification is assumed". The same page states the guarantee is scoped to the filter and is not an end-to-end accounting. It gives no sensitivity bound, neighbouring definition or number of selected entries, so the reading used below is the one the class docstring and the code state: per-coordinate values are divided by `NUM_STEPS_CURRENT_ROUND`, clipped to `[-gamma, gamma]`, and `n_upload = ceil(fraction * total_params)` entries are released. For `PercentilePrivacy` the page claims no DP guarantee, so its rows measure what the code does and make no accounting comparison.

## Method

All rows run the real classes in process with `DXO(data_kind=WEIGHT_DIFF, data={...})`, `Shareable()` and `FLContext()`. Randomness is observed by wrapping `numpy.random.laplace` (recording `scale` and `size` per call and passing the call through) and by wrapping the module function `_sample_partition_counts` (recording its `group_counts`). Seeds are fixed per row and recorded. A row "holds" when its prediction is met inside the stated tolerance. Failed predictions stay in the record as written.

## Rows, SVTPrivacy

Parameters not named are the class defaults (`fraction` 0.1, `epsilon` 0.1, `noise_var` 0.1, `gamma` 1e-5, `tau` 1e-6, `replace` True). Input vectors are float64 unless stated.

| Row | Configuration | Prediction | Tolerance |
|---|---|---|---|
| N1 | Grid of (epsilon, n_upload): epsilon in 0.1, 1, 10, 100 and total params so that n_upload in 1, 10, 100, 1000 with `fraction` 0.1. | Ledger `epsilon_threshold` equals epsilon / (1 + (2 n)^(2/3)) and `epsilon_query` equals epsilon minus that, in every cell. | relative 1e-12 |
| N2 | d = 1000, `fraction` 0.1 (n 100), epsilon 1, `noise_var` 0.1, all entries 1e-5. | The recorded Laplace scales are: one scalar draw of scale gamma / epsilon_threshold, query draws of scale 2 gamma n / epsilon_query, release draw of scale 2 gamma n / epsilon_release. | relative 1e-12 |
| N3 | Default class parameters, d = 25,578 (the P3 model size), one call and then ten calls. | Ledger `epsilon_total` for one call equals 0.1 + 0.1 * 2558 = 255.9. After ten calls `get_privacy_spent()` equals 2559.0. `delta` is 0. | absolute 1e-9 |
| N4 | d = 1000, n 100, epsilon 100, all entries equal to gamma (every entry above the clip). | The number of accepted entries recorded before selection (sum of `group_counts`) is at least 5 times `n_upload`. In the standard sparse vector technique the algorithm stops after c positive answers, here c is `n_upload`. | ratio at least 5 |
| N5 | d = 1000, n 100, three entries equal to gamma and the rest 0, run in a subprocess with a 10 second limit. epsilon 0.1, then epsilon 1e4, then epsilon 1e6. | At 0.1 the call returns and the ledger shows 1 acceptance pass. At 1e4 it returns with between 5 and 200 passes. At 1e6 it does not return within 10 seconds. | as stated |
| N6a | Release neighbours. d = 8, `fraction` 0.25 (n 2), epsilon 20, entries all +gamma against all -gamma, `replace` False, 200,000 runs each. Event: the sum of released values is above 0. | The empirical 95% lower bound on epsilon (Clopper-Pearson on both probabilities) is at most the ledger `epsilon_release` for this call. | lower bound at most claimed |
| N6b | Selection neighbours. Same configuration, entries (gamma, 0, ..., 0) against all 0, 200,000 runs each. Event: entry 0 of the output is nonzero. | The empirical 95% lower bound is at most `epsilon_threshold` + `epsilon_query` of the call. | lower bound at most claimed |
| N7 | d = 1000, n 100, epsilon 100, all entries equal to gamma, 200 runs, `replace` True and then False. | With `replace` True the number of nonzero released entries is below `n_upload` in at least 95% of runs and its mean is between 90 and 100. With `replace` False it is exactly `n_upload` in every run. | as stated |
| N8 | `fraction` 0 and then 1e-12 with a float64 vector of 100 entries and one scalar entry. | At 0 the output is all zeros for array entries, the scalar is unchanged, and the ledger is empty. At 1e-12 `n_upload` is 1 and the ledger has one entry. | exact |
| N9 | One array of 100 entries and one scalar entry equal to 0.123. | The scalar is returned unchanged, the ledger entry has `has_scalar_passthrough` True and a `note`, and `n_upload` is computed from 101 entries with `fraction` 0.1 (11). | exact |
| N10 | d = 1000, seeds 123, 123, 124 through `numpy.random.seed`. | The constructor has no seed argument. The same seed gives identical output, a different seed differs, and the global numpy state advances. | exact |
| N11 | Three calls, then a `START_RUN` event through `handle_event`, then one call. | The ledger has 3 entries and `get_privacy_spent()` equals their sum. After `START_RUN` it is empty and the next call starts a new sum. | exact |
| N12 | `NUM_STEPS_CURRENT_ROUND` 1 and 5, d = 1000, epsilon 1, all entries 1e-5 times the step count. | The release noise in output units is 5 times larger with 5 steps (scale ratio 5), and the recorded Laplace scales are unchanged. | relative 1e-9 on recorded scales, 10% on measured ratio |

## Rows, PercentilePrivacy

Defaults are `percentile` 10 and `gamma` 0.01. Input is 10,000 distinct random values.

| Row | Configuration | Prediction | Tolerance |
|---|---|---|---|
| P0 | Same input twice, with and without `numpy.random.seed` changes. | The output is identical every time, because the filter uses no randomness. | exact |
| P1 | Percentiles 10, 50 and 90. | The number of entries that become exactly 0 is within 1 of `percentile` percent of the entries. | 1 entry |
| P2 | Entries with absolute value above the cutoff and above `gamma`. `NUM_STEPS_CURRENT_ROUND` 4. | They are clipped to `gamma` after division by the step count and multiplied back, so the output equals sign times 4 times `gamma`. | relative 1e-12 |
| P3 | `percentile` 100. | Every entry with absolute value strictly below the maximum becomes 0, and the entry at the maximum is kept. | exact |
| P4 | A scalar entry mixed with arrays. | The scalar is returned unchanged by value (multiplied by the step count after division), with no clipping. | relative 1e-12 |

## Deviation log

Nothing above this heading may be edited after the commit that adds this file. Deviations are appended here with the date and the reason.

Entries dated 2026-11-25.

1. Environment. The virtual environment has numpy 2.5.5, where the "Subjects and environment" section states 2.5.3. Python is 3.13.18 as stated. `scipy` is not installed there, so the Clopper-Pearson helper uses a pure Python incomplete beta function instead of `scipy.stats.beta`. A test compares it with `scipy` on the system interpreter, where it agrees to relative 1e-8. `pytest` was installed in the virtual environment for the tests.
2. Choices the pre-registration left open. Input values for N1, N3 and N11 are all entries at 0.5 gamma. N8 to N10 use small random float64 values of order gamma. P rows use standard normal values, 10,000 distinct. N12 pools 200 calls per step count. N7 runs 200 calls per `replace` setting as written. P4 uses two numpy float64 scalars (3.7 and 1e-9) and 3 steps. Seeds are derived from 20261125 and listed in the JSON.
3. Added checks. Beyond the pre-registered statements the harness also checks the call structure and the release draw size in N2, delta in the cumulative metadata in N3, and that the global numpy state is not advanced in P0. It records import time in N5 and the group and selected counts in N9. None of these replaces a pre-registered check. A plain Python float scalar in `PercentilePrivacy` is recorded in P4 as an observation and is not a check.
4. N6a and N6b. Full mode runs 200,000 calls of the real `process_dxo` per input, as pre-registered, with a fresh filter instance every 10,000 calls to bound the ledger. No run count was reduced. The empirical bound uses a = 2.5% per tail on each probability and takes the larger of the two directions.
5. Exploratory runs before the full run, none of which changed a prediction, tolerance or configuration. (a) An interpreter probe in the virtual environment: one `SVTPrivacy` call on 100 random entries and a scalar, 2,000 timed calls of the N6 configuration (about 0.15 ms each), and one `PercentilePrivacy` call with a numpy float64 scalar and one with a Python float (the second raised `AttributeError`). (b) A first quick run of the harness in which row N7 raised `ValueError`, because the harness passed an array where a dict is required. The harness was fixed and a second quick run held 18 of 18 rows. (c) The test file was run on the virtual environment interpreter and on the system interpreter.
6. The full run used the harness as committed in `2c3c490` (script sha256 `7b41455704bdadd3ef925cd57135646b5ceeb9af07df4b61effa8f2081c9a84f`) and ran once.
7. Prediction failures: none. All 18 rows and all 63 checks held.

# v0.16.11 pre-registration: does the distributed DP aggregator of TensorFlow Federated deliver the noise and sensitivity that its configuration states

Status: written before the script exists and before any call of `process.next` in this phase. Date: 2026-11-26.
Subject: `tensorflow-federated` 0.87.0, the module `tensorflow_federated/python/aggregators/distributed_dp.py` (`DistributedDpSumFactory`), the components that it nests (`rotation.py`, `discretization.py`, `modular_clipping.py`, `secure.py`, `robust.py`, `differential_privacy.py`), the `tensorflow-privacy` 0.9.0 queries `DistributedSkellamSumQuery` and `DistributedDiscreteGaussianSumQuery`, and the wrapper `tff.learning.ddp_secure_aggregator`.
Follows: `docs/preregistration/v0.16-tff-dp.md` (the Gaussian aggregators of the same TFF release) and `docs/preregistration/v0.16-nvflare-selection.md` for the power statements.

## Question

Q1. When n clients report and `expected_clients_per_round` is n, is the noise that arrives in the aggregate the configured `noise_multiplier` times `l2_clip` per coordinate, for both mechanisms (distributed Skellam and distributed discrete Gaussian) and both rotations (DFT and Hadamard)? Where does the delivered noise differ from that value because of the scale heuristic, the integer local standard deviation or modular wrapping?

Q2. The class docstring says that the local noise standard deviation is the central one divided by `expected_clients_per_round`. The code divides by its square root. Which reading does the delivered noise follow?

Q3. When more or fewer clients report than expected, what noise and what sensitivity are delivered?

Q4. What is the norm of the change that one client above the clip makes to the output, including the growth from randomized rounding, with and without conditional rounding (`beta`)?

Q5. What happens when the aggregate exceeds the field of the secure sum (small `bits`, a large `modclip_prob`, or many more clients than expected)? Is the output wrapped or clipped?

Q6. With `auto_l2_clip`, does the noise follow the clip that the clients used in the round or stay tied to the initial clip?

Q7. What does the process report about privacy accounting, and is the noise seedable?

This is a measurement of one framework version under stated configurations. It is not a claim about how TFF is meant to be used. A pass says nothing about other versions, a trained model, a real secure aggregation protocol (TFF's runtime here evaluates the secure sum as a plain sum, and the field and the wrap come from TFF's own modular clipping aggregators), client sampling or composition over rounds. No privacy guarantee is claimed or tested. Row I turns measured numbers into an implied epsilon under a Gaussian approximation and labels it so.

Claimed behaviour and where it is written, copied by hand from the installed 0.87.0 sources and shortened.

1. Class docstring of `DistributedDpSumFactory`, `noise_multiplier`: central noise stddev divided by L2 clip norm, "with respect to the initial L2 clip norm", and "The specified noise will be split into `expected_clients_per_round` noise shares to be added locally on the clients."
2. Same docstring, `expected_clients_per_round`: "In particular, local noise stddev = central noise stddev / `expected_clients_per_round`."
3. In `_build_aggregation_factory` the code reads `local_stddev = central_stddev / math.sqrt(self._num_clients)` with `central_stddev = self._value_noise_mult * self._initial_l2_clip`.
4. Class docstring: a TODO reads "Add exact privacy accounting for DDP using new accounting APIs", and the text says that one could use `tensorflow_privacy` analysis tools on the metrics of each round to obtain (epsilon, delta).
5. `bits`: "2^B will be the field size for SecAgg operations", "should be at least as large as log_2(expected_clients_per_round)", range 1 to 22.
6. `modclip_prob`: "the target probability for modular wrapping due to SecAgg's modulo operations", default 1e-4.
7. `beta`: "The larger the value, the less post-rounding L2 sensitivity inflation."
8. `_heuristic_scale_factor`: `2^b = 2k * sqrt(rho / dim * (cn)^2 + (gamma^2 / 4 + sigma^2) * n) / gamma`, with k the number of standard deviations for `modclip_prob`.

Neighbouring inputs. The documentation read does not state an adjacency relation. The reading used here is add or remove one client, so the sensitivity of the sum is the norm that one clipped client adds. Replace-one is not measured.

## Method and statistics

Noise measurement. Clients send zero vectors, so the expected output is zero and the output is the noise. The statistic is the root mean square (RMS) over all coordinates of all calls of the configuration. With N values its relative standard error is 1 over the square root of 2N. Ratios to a prediction are written measured over predicted. The ratio check holds when the ratio is within the stated relative tolerance of 1.

Predicted noise values. For a configuration (z, n, C, bits b, modclip_prob p, mechanism), k is the standard normal quantile of 1 minus p over 2, sigma_l is z C over the square root of n, scale is the capped (at 1e6) value of `sqrt(2^(2b) - n k^2) / (2 k sqrt(C^2 n^2 / D + n sigma_l^2))`, the local scaled standard deviation s is sigma_l times scale in float32, and the delivered sum X has per-coordinate variance n s^2 for Skellam and n times the variance of a discrete Gaussian of integer scale ceil(s) for the discrete Gaussian mechanism. The output coordinate is the wrap of X into `[-2^(b-1), 2^(b-1))` divided by the scale. The predicted RMS ratio is the square root of the second moment of the wrapped X over the square of z C scale, computed from the exact probability table of X. This is the model behind every predicted ratio below.

Noise-free checks. A noise multiplier of 0.0 is allowed by the constructor and removes the DP noise. Rounding stays. Norms of float32 outputs are formed in float64.

Rounding model. For a client vector of norm r the rotated scaled coordinates are modelled as Gaussian with standard deviation tau = r scale over the square root of D. Randomized rounding adds variance rho(tau) = E[f(1-f)] per coordinate with f the fractional part, computed by numerical integration.

Seeds. Input vectors are drawn with `numpy.random.RandomState(20261127 + 100 * k + j)` for row index k (A 0, B 1, C 2, D 3, E 4, F 5, G 6, H 7, I 8, J 9) and sub-configuration index j. `tf.random.set_seed` and `numpy.random.seed` are called with the same number before each process is created. Whether this controls the noise is row H, and the prediction there is that it does not, so noise values are not reproducible and the evidence records one run.

Process reuse. For noise rows one process is created per configuration and every call starts from the same initial state, so rotation is fixed within a configuration. Rows A3, D and E3 initialize a fresh state before each call, so each call has a new rotation seed and new rounding draws.

## Power of each null result

A null result is a statement that a delivered value matches a prediction, or that no dependence is seen. For an RMS check the decision threshold is a fixed tolerance t, so a true deviation d is found with 80% power when d is at least t plus 0.8416 standard errors. The standard error of the RMS is 1 over the square root of 2N, with N the number of values.

| Null result | N | Standard error | Decision threshold | Smallest effect found with 80% power |
|---|---|---|---|---|
| A1 RMS ratios | 245,760 | 0.1426% | 0.7% | 0.820% |
| A2, B, C, E2 RMS ratios | 163,840 | 0.1747% | 0.7% | 0.847% |
| A3 RMS ratios (absolute) | 163,840 | 0.1747% | 0.8% | 0.947% |
| J RMS ratios | 122,880 | 0.2017% | 1.0% | 1.17% |
| F RMS ratios per round | 40,960 | 0.3492% | 1.5% | 1.79% |
| A1 dispersion of per-call RMS | 120 calls | 0.00101 | window 0.0116 to 0.0197 | a share of about 2.3% of calls with a repeated-noise pair, by the formula below |
| D mean norm, b 8 | 80 | 0.000316 | 0.0012 | 0.00147 (19% of the predicted growth 0.00765) |
| D mean norm, b 5 | 80 | 0.00247 | 0.02 | 0.0221 |
| D mean norm, b 16 | 80 | 1.2e-6 | 1e-5 | 1.1e-5 |
| E3 mean norm, m 64 and m 16 | 20 | about 0.02 and 0.03 | 0.2 and 0.4 | 0.22 and 0.43 (2.4% and 4.8% of the norm) |
| F mean ln clip | 20 chains | 0.00292 | 0.01 | 0.0125 |
| H correlations | 40,960 | 0.00494 | 0.0198 | 0.0239 |
| H seed digests | two processes per mechanism | none | equality of 32 byte digests | any difference at all |
| Exact checks (B3, C3, C4, D3, F5, G, I1, E1) | one run each | float32 rounding below 1e-6 relative | stated relative tolerance | any difference above the tolerance on the inputs tried |

Dispersion formula. With a share q of calls that carry one repeated-noise pair, the variance of the per-call RMS is 0.01562 squared plus q (1 - q) times 0.0954 squared. The upper edge 0.0197 is reached at q about 1.6% and the 80% power point is q about 2.3%. A pair that repeats noise in every call would shift the A1 mean by 9.5%, so rows A to C would fail on the mean as well. A shift of the mean by less than the 0.7% tolerance is not seen, which means a collision share below about 7% is not excluded by the mean and only by the dispersion check.

Effects that matter for the readings are far above these limits. The two readings of Q2 differ by a factor of the square root of n (2.0 at n 4). The arrived-count reading of Q3 differs by 41% at m 5. A noise tied to the initial clip differs by 38% at round 5 of F. The integer scale at 8 bits is 8.4%. A saturating field against a wrapping one differs by 22% at p 0.3.

Which events, inputs and settings the statements cover. Zero update vectors for the noise rows, one dense vector direction per row for the rounding rows, the stated n, m, bits and `modclip_prob`, 2048 coordinates in one float32 tensor, one TFF version, one platform and TFF's local C++ runtime. They do not cover other dimensions (padding and slicing happen for other sizes), integer inputs, structures of several tensors, other norms, a trained model, a real secure aggregation protocol, client sampling, composition over rounds or any claim about privacy.

Positive controls. B check 2 (the docstring reading), C check 2 (the fixed total reading), E2 (the clip reading), F check 2 (the clip after the update), H check 3 (a correlated vector), A2 at 8 bits (an 8.4% deviation that the RMS check can see) and E3 at m 64 against the clip reading. Each can register a deviation of the size it is meant to show.

What a pass means. For a row that holds, the delivered value matches the pre-registered prediction within the stated tolerance for the inputs tried, for TFF 0.87.0. Several predictions are not "equals the configuration", for example the discrete Gaussian at small `bits` and the wrap at large `modclip_prob`. A pass there means the model of the code is right, and the difference from the configuration is reported as a measured difference. No row says that the mechanism is differentially private, since TFF states no adjacency, and no epsilon is a guarantee.

## Decision thresholds

1. A row holds when every check in it holds. A check holds when its measured value is inside the tolerance written in Predictions.
2. A mismatch between delivered and predicted noise is reported with its ratio. It is called found only when the statistical check fails in both the first run and the one replication. An exact check has no replication.
3. A null result counts as informative only when its smallest effect at 80% power is at most 1% of the quantity for the RMS checks (A1, A2, B, C, E2, A3), at most 2% for F and 1.2% for J. Otherwise it is reported as uninformative whatever the measured value is.
4. H check 4 is a prediction about seeding. If a pair of digests is equal the row is reported as not held.

## Stopping rule

The rows, configurations, calls, chains, clients, coordinates and seeds are fixed above before the first run. The script runs once in full mode. If a statistical check of a row fails, that row alone is run once more with fresh calls (seed offset 5,000,000 added to the seed rule, which changes input vectors and the call to `tf.random.set_seed` and not the noise, which cannot be seeded). Both results are reported and nothing else is added. No other replication, extra configuration, extra seed or change of tolerance is made after the first full run. Test runs of the script in quick mode go to a temporary directory outside the repository and are not evidence. The evidence JSON records the sha256 of the script that ran.

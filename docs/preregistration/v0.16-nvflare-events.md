## Question

Q1. v0.16.5 limit 1 says that the lower bounds cover one event, one pair of inputs and small sizes (d 6, n 2 or 3). For six further configurations, does the 95% lower bound on the empirical epsilon of the chosen event stay at or below the epsilon that the documentation or the code implies for that event? The configurations add larger d and n, the class default `replace` True, input values between 0 and gamma, the release values (the noisy output vector, not only the selected set), and an event that joins the selection and the release.

Q2. For every null result in this file, what is the smallest excess over the claim that the check would have found with 80% power?

This is a measurement of one framework version under stated configurations. A pass says nothing about other inputs, other events, other neighbouring pairs, other values of the parameters or the whole 2.9.1 mechanism. The list of what stays untested is in the section "Not covered".

Versions. The two filter files are byte identical in 2.8.3, 2.9.0 and 2.9.1 (v0.16.5, sha256 `c543bbea2ce3bfe2e35a1d85a26acac8dffc0e95024e777010cdbf0cd0f92858` for `svt_privacy.py`), so a run on the other two versions adds nothing and none is made.

## Method and statistics

Neighbouring inputs. Neither the documentation nor the code states a neighbouring definition. Two readings are used and each row says which. Reading A: neighbours differ by at most gamma in every coordinate of the clipped absolute value, which is what the selection step sees. Reading B: neighbours differ by at most gamma in the signed clipped value. The noise scale of the release step, `gamma * 2 * n / epsilon_release`, is built for a signed range of 2 gamma per selected entry, which only reading A allows (a sign flip). Rows E1 to E4 and E6 satisfy both readings, E5 satisfies reading A only. All vectors are float64 and named `w`. gamma is the default 1e-5 and the values below are multiples of gamma.

Runs. Every run calls the real `SVTPrivacy.process_dxo` once on a fresh `DXO` of kind `WEIGHT_DIFF`. Each world is run in 5 blocks of 100,000 calls, which is 500,000 calls per world and 1,000,000 per row. The block seed is 20261201 + 10000 * r + 100 * w + b with r the row number (1 for E1 up to 6 for E6), w the world (0 for a, 1 for c) and b the block (0 to 4), set with `numpy.random.seed` before the block. A fresh filter instance is made every 10,000 calls, and the ledger of each instance is read for the sum of `acceptance_passes`. The seeds differ from the seeds of v0.16.5.

Interval. For each world the count k out of N gets a Clopper-Pearson interval with 1.25% in each tail, using the pure Python helper of `scripts/audit_nvflare_dp.py`. This is the interval of v0.16.5.

Lower bound. LB is the largest of four log ratios, floored at 0: ln(lo_a / hi_c), ln(lo_c / hi_a), ln((1 - hi_c) / (1 - lo_a)) and ln((1 - hi_a) / (1 - lo_c)). If the true epsilon of the event under the pair is at most the claim, LB exceeds the claim with probability at most 5% for that row. The six rows are six separate checks and no correction is made across rows.

Claims. Selection rows (E1 to E4): the ledger `epsilon_threshold` plus `epsilon_query` of the first call, which equals `epsilon`, here 1. Release row (E5): the ledger `epsilon_release`, which is `n * noise_var` for the default `noise_var`, so 0.3 at n 3 (the documentation says that `epsilon_release` is the total budget of the release noise phase and that `noise_var` implies `n_upload * noise_var`). Joint row (E6): the ledger `epsilon_total`, the sum of the three parts, which is the accountant's claim for one call, so 1.2 at n 2.

Numeric prediction for the selection part. The numeric computation integrates over the threshold noise on 3,000 quantile points and sums over the pass at which the acceptance loop stops, with the accepted entries then drawn as the code does. Its functions (`lap_sf`, `split`, `g_table`, `count_prob`, `p_pos`) are reproduced verbatim in the script.

Closed form for the release part. With scale b = 2 gamma n / epsilon_release, a = gamma / b = epsilon_release / (2 n). A selected entry with input +gamma is positive with probability 1 - exp(-a) / 2, with input -gamma with probability exp(-a) / 2 and with input 0 with probability 1/2. The selection and the noise are drawn separately, so the probability of a joint event is the product. A selected entry is a distinct index when `replace` is False, so n entries carry noise. Event probabilities for E5 and E6 are products of these terms.

Block agreement. A chi-square test with 4 degrees of freedom compares the 5 block counts of a world with their pooled rate. Its survival function is exp(-x/2) * (1 + x/2).

Power. For a true log ratio e with the denominator probability p_c fixed at its predicted value, p_a equals p_c * exp(e) and SE(e) is sqrt((1 - p_a) / (N * p_a) + (1 - p_c) / (N * p_c)) with N 500,000. The normal approximation of LB gives power equal to the standard normal cdf of (e - claim) / SE - z, with z 2.2414 (one tail at 1.25%). The smallest effect at 80% power is the value e that solves e = claim + (z + 0.8416) * SE(e). It is a statement about the event under that pair only.

Ceiling. The largest LB that any outcome can give at 500,000 runs per world is ln(lo(N, N) / hi(0, N)) with the same intervals. It must be above every claim, otherwise the check could not fail.

What a pass means. For each row a pass means that for the stated event under the stated pair the empirical epsilon is not above the claim by more than about the stated excess. The true epsilon of the filter is the largest over all events and all neighbouring pairs, so each checked quantity is a lower bound on it. A pass in E3 covers values 0.2 and 0.8 gamma only. A pass in E5 covers one sign flip pair, one n and the default `noise_var` only. A pass in E6 covers one joint event and pair at n 2.

## Decision thresholds

1. A row holds when LB is at most the claim. An excess is found when LB is above the claim.
2. A null result counts as informative only when its excess at 80% power is at most half of the claim. Otherwise it is reported as uninformative whatever the lower bound is.
3. A numeric prediction holds when the observed value is inside the stated tolerance. A prediction that does not hold stays in the record as written.
4. A positive control passes when LB is above 0.1 times the claim.
5. The numeric computation and the closed form must agree with the prediction table to 1 percent relative before the first run. They are recomputed by the script as a check.

## Stopping rule

N is fixed at 500,000 per world and per row, six rows, one full run. There are no interim looks, no extra seeds and no change of configuration after the first full run. If any LB is above its claim, one replication of that row runs with fresh seeds (the block seeds above plus 5,000,000) and both results are reported. An excess is called found only when both runs show LB above the claim, and if the replication does not, both are reported as they are, with no interpretation added. The replication is the only run that may be added. If the whole script exceeds 1,500 seconds, the run is reported as it is and the time prediction stays failed.

## Not covered

These parts of the filter and of the claims are outside every row of this file and stay untested.

1. Other neighbouring definitions, including one changed coordinate at a time, and any pair other than the six above.
2. Other events: the marginal event that one entry is selected, events on the order of the selected entries, and the exact set at n larger than 4 (its probability is near 1e-5 at d 24 and n 6).
3. `replace` True with the exact set, and `replace` True in the release rows (E5 and E6 use `replace` False).
4. Release rows at other n, at an explicit `epsilon_release`, at `noise_var` other than the default, and with a non-default `gamma` or `tau`.
5. `epsilon` other than 1 in the selection rows, explicit `epsilon_threshold` or `epsilon_query`, and the class default `epsilon` 0.1.
6. d above 40, n above 10, several arrays, scalar passthrough, `NUM_STEPS_CURRENT_ROUND` other than 1 and the chunk size of 1,000,000 entries.
7. Composition over several calls (the ledger is a plain sum, `pure_dp_sum`) and any delta.
8. Other versions of `nvflare` (the two filter files are byte identical in 2.8.3, 2.9.0 and 2.9.1) and other dependency versions.

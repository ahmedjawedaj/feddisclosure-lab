# v0.16 P2 pre-registration: what the Flower server observes with protections on

Status: written before the P2 script exists and before any real call in this phase. Date: 2026-11-26. The commit that adds this file is the timestamp.
Subject: `flwr` 1.27.0 (the version pinned by this repository). The strategies `flwr.server.strategy.DifferentialPrivacyServerSideFixedClipping` wrapping `FedAvg`, and the upstream `SecAggPlusWorkflow` with the `secaggplus_mod` client modifier, driven in the Docker stack of `compose.flower.n4.yaml` plus `compose.wire.yaml`. Tracker item T7. Predictions S4, S6 and S6b of `docs/v0.16-p2-server-view-inventory.md`.
Script: `scripts/audit_p2_server_view.py` (written after this file). Tests: `tests/privacy/test_audit_p2_server_view.py`. Metric returning client and recording server hook (written after this file): `src/feddisclosure/training/p2_metrics_client.py` and `src/feddisclosure/training/p2_metrics_server.py`.

## Question

Three questions, each about a channel that the inventory marks as not covered by the stated guarantee of a protection. None of them is a claim that the channel leaks anything.

1. S4. When a client returns non-empty fit metrics under SecAgg+, does the Flower server process see those metrics in clear, both in the reply message and in the `FitRes` that reaches `aggregate_fit`, while the array records of the same reply are empty?
2. S6. If a client's participation depends on the norm of its clipped update, do the released-or-not bit and the participant set of a round predict that norm above chance? This is a conditional hypothesis. The dependence is an assumption of the model and is not observed in any deployment.
3. S6b. In the same rounds, does the change in the number of results change the effective noise multiplier of the fixed clipping strategy by the factor of row C4 of `docs/v0.16-p1-flower-dp-audit.md`, and does the exact epsilon follow from `gauss_eps` of the harness?

Where each claim is written. The channel table of the inventory (rows 4 and 6) says that the code clears array records only and that a reported failure releases nothing. SecAgg+ and central DP make no statement about either channel, which is the reason they are examined.

## What was already known before this file was written

Stated so that predictions are not presented as blind.

1. W5 of `docs/v0.15-wire-validation.md`. In the hosted run the sample count was visible in 20 of 20 SecAgg+ replies. The metrics record was present in 20 of 20 and carried no metric value in any, because the repository client returned an empty dictionary. The metrics half of W5 was therefore not exercised. No client in this repository returned a metric before this phase.
2. Rows C3 and C4 of `docs/v0.16-p1-flower-dp-audit.md` (release 0.16.0, flwr 1.27.0). C4 with `num_sampled_clients` 10 and 2 results aggregated measured sensitivity 0.500, sigma 0.09996, effective multiplier 0.200 and exact epsilon 33.1. C1 with 10 results measured effective multiplier 1.000 and epsilon 4.38. The C4 formula there is effective multiplier z m / n.
3. Source reading of flwr 1.27.0. `secaggplus_mod.py` clears the array records of the reply in the collect stage (`arr_record.clear()` on each array record of the output content) and leaves the other records, including the `fitres.metrics` config record and the `fitres.num_examples` metric record, in the message. `SecAggPlusWorkflow` builds the legacy `FitRes` objects from the collect-stage replies with `compat.recorddict_to_fitres` and hands them, with the dequantised aggregate in `parameters`, to `strategy.aggregate_fit`. In `DifferentialPrivacyServerSideFixedClipping.aggregate_fit` a non-empty `failures` list returns `(None, {})` before any clipping, a result list shorter than `num_sampled_clients` logs a warning and continues, and the noise scale is `noise_multiplier * clipping_norm / num_sampled_clients` regardless of the result count. All S4 and S6 predictions below come from this reading.
4. A scratch computation of the exact Gaussian epsilon was run before this file. It is a pure scipy evaluation of the Balle and Wang (2018) formula, with no Flower call, for mu equal to 1 and 10/9 at delta 1e-5. Output: epsilon 4.377178 for mu 1.0 and 4.947319 for mu 1.111111. It also evaluated the exact binomial power of the S6 rule for 2,000 rounds (see the power section). File `/tmp/p2_scratch_formula.py`, SHA-256 `94746350168d757a09769cb9be60292043745185503becc9c9ed59fc813c17da`. The same arithmetic is part of the script, so the epsilon predictions below are confirmatory and not blind.
5. No Flower class was called, no Docker command was run for this phase and no S4 or S6 number was measured before this file. The sandbox facts used to plan the run (Flower 1.27.0 installed, Docker daemon running, the images `flwr/superlink:1.27.0`, `flwr/supernode:1.27.0` and `feddisclosure-flower-exec:0.12.0` present) were read from `docker images` and the installed package.
6. The values of the dependence strength (0.85 and 0.15), the threshold (0.8 C) and the norm range were chosen by the author for this file. They were not tuned on any data.

## Design

### S4 (Docker, real strategy)

The stack is `compose.flower.n4.yaml` plus `compose.wire.yaml`, run by `scripts/run_wire_capture.py --modes secagg --seeds 2`. The ServerApp is the recording ServerApp of v0.15 (`secagg_server_capture`) with one addition from `p2_metrics_server`: the application strategy class is swapped for a subclass that writes to the artifact directory the `FitRes.metrics`, the `num_examples` and the node identifier of every result that `aggregate_fit` receives. The ClientApp is the repository client with the SecAgg+ modifier and one change from `p2_metrics_client`: `fit` returns a non-empty metrics dictionary and also appends the exact dictionary it sent to a file in its own attestation mount (host side receipt, never sent). Metrics returned by each client: `probe_const` (a float equal to 1234.5 plus the site index), `train_loss` (a float, the mean cross entropy of the final local model on the client's own training records) and `n_local` (an integer, the local record count). Four clients, one round, one local full batch step, learning rate 0.15, `num-shares` 4, `reconstruction-threshold` 2. Seeds 0 and 1.

Per run the script reads the recorded server messages of the collect stage (the replies the ServerApp receives from the grid) and the file written by the strategy hook, and decides the following. All four must hold for all four clients of both seeds.

| ID | Check |
|---|---|
| S4a | The collect-stage reply of each client has a `fitres.metrics` config record with exactly the three keys |
| S4b | The three values equal the values in that client's receipt, with float equality on the double value |
| S4c | The `FitRes` of that node that reached `aggregate_fit` carries the same three values |
| S4d | The array records of the collect-stage reply hold zero arrays, for each client |

S4 passes when S4a to S4d hold in 8 of 8 client replies (4 clients, 2 seeds). A run that does not finish, or whose capture summary is not marked complete, counts as not run and is not counted as a failure of the prediction. If both seeds do not finish the row is reported as NOT RUN with the reason. The participant set (the node identifiers that sent a collect-stage reply) and the reply sizes are recorded without a prediction.

### S6 and S6b (in process)

The strategy under test is `flwr.server.strategy.DifferentialPrivacyServerSideFixedClipping(FedAvg(inplace=True, fraction_fit=1.0, fraction_evaluate=0.0, min_fit_clients=10, min_available_clients=10), noise_multiplier=z, clipping_norm=1.0, num_sampled_clients=10)`, driven through `configure_fit` and `aggregate_fit` as in `scripts/audit_flower_dp.py` (stub client proxies, a 16 float32 parameter vector, global parameters all zero, `FitRes` objects with `num_examples` 1 for every client, so weights are equal). C = 1, n = 10, delta = 1e-5. The Message API classes in `flwr.serverapp.strategy` are not driven in this phase.

Round model of S6. Client 0 is the target. Clients 1 to 9 always respond with a fixed random direction update of raw norm 3C, which Flower clips to C. In each round the target draws a raw norm r from Uniform(0.2 C, 1.4 C). Its clipped norm is c = min(r, C), which is the norm of the update after Flower's clipping helper (checked below). The label of the round is high when c > 0.8 C. This is the median of c, so the label is balanced in distribution (probability 0.5 exactly). The target participates with probability 0.85 when the label is high and 0.15 when it is low (dependence arms), or with probability 0.5 whatever the norm (control arms). The update direction of the target is random.

| Arm | What a non-participating target does | What the observer sees |
|---|---|---|
| bit-dep, bit-ctl | Reported as a failure in the `failures` list, so Flower releases nothing | Only whether `aggregate_fit` returned parameters |
| set-dep, set-ctl | Absent from both lists, so 9 results arrive and Flower releases a rescaled aggregate | Only whether client 0 is among the clients of the result list |

Each arm has 2,000 rounds. The observer predicts high when the target participated (the direction is fixed in advance) and low otherwise. Accuracy is the share of the 2,000 rounds in which the prediction equals the label. In the bit arms participation is read from the release bit, in the set arms from the participant set.

Seeds. Round draws use `numpy.random.default_rng([20261126, k])` with k = 0, 1, 2, 3 for bit-dep, bit-ctl, set-dep, set-ctl. The noise of the strategy uses the global numpy generator, seeded with `numpy.random.seed(20261126 + k)` before each arm. Noise on or off does not change the release bit or the participant set.

Round model of S6b. Two configurations, with the strategy at n = 10 and z = 1: M10 (10 results) and M9 (9 results, the target absent). The measured client is client 1, present in both. Sensitivity is measured with z = 0 as the L2 distance between the aggregate with client 1 sending a norm 5C update and with client 1 sending a norm 1e-6 update (the zero-out stand-in of P1), the other results fixed at norm 3C random directions (`default_rng(1700 + m)` for m = 10 and 9). Sigma is measured with z = 1 from 20,000 runs at the null update, as the root mean square over the 16 coordinates of the per-coordinate sample standard deviation (`numpy.random.seed(20261127)`). Effective multiplier = sigma / (sensitivity), mu = sensitivity / sigma, epsilon = `gauss_eps(mu, 1e-5)`, zero-out adjacency, one round, no sampling amplification, no composition.

## Predictions

A prediction that fails stays in the record as written. Interval method for S6: Wilson 95% two-sided (z = 1.959964) on the count of correct predictions out of 2,000. A rule that uses a limit is read at that limit and not at the point estimate.

| ID | Statement | Prediction and rule |
|---|---|---|
| S4 | Non-empty fit metrics under SecAgg+ are visible to the server in a real run | S4a to S4d hold in 8 of 8 client replies. Values are visible and the array records are empty. Confidence 0.9 |
| S6-bit | Release bit predicts the target's clipped norm class | Accuracy 0.85 within plus or minus 0.03, and the Wilson lower limit above 0.5. Confidence 0.95 |
| S6-set | Participant set predicts the same | Accuracy 0.85 within plus or minus 0.03, and the Wilson lower limit above 0.5. Confidence 0.95 |
| S6-ctl | Controls with no dependence | The Wilson interval of bit-ctl and of set-ctl each contains 0.5. Confidence 0.9 for both together (each interval excludes 0.5 by chance about 5 percent of the time, and no re-draw is made) |
| S6-exact | The release rule of the source reading | In the bit arms the strategy returns `None` in exactly the rounds where the target failed, 2,000 of 2,000 in each of the two bit arms. In the set arms it returns parameters in 2,000 of 2,000 rounds and the number of results is 9 plus the participation indicator. Confidence 0.97 |
| S6-clip | The clipped norm is min(r, C) | For 200 draws of r from the S6 range with noise off and a single client strategy, the norm of the released update equals min(r, C) within relative 1e-5 in 200 of 200 |
| S6b-sens | Sensitivity follows C / m | M10 0.1000 and M9 0.1111, each within relative 0.1 percent |
| S6b-sigma | Noise scale does not follow the result count | Sigma 0.1000 in both, each within 2 percent of z C / n |
| S6b-zeff | Effective multiplier changes by m / n | M10 1.000 and M9 0.900, each within 2 percent, and their ratio 0.900 within 2 percent |
| S6b-eps | Exact epsilon from `gauss_eps` | M10 4.377 and M9 4.947 at delta 1e-5, each within 1 percent |
| S6b-mix | The dependence moves the multiplier with the norm | In the set-dep arm the share of rounds with 9 results is 0.50 within plus or minus 0.03. The mean effective multiplier of the rounds with a high label is 0.985 and of the rounds with a low label is 0.915, each within plus or minus 0.01. Per round multipliers are the measured M10 and M9 values |

S6 as a whole passes when S6-bit, S6-set, S6-ctl, S6-exact and S6-clip pass. S6b as a whole passes when its five rows pass. Each row is also reported on its own.

Expected values that are not rules. The S6-bit and S6-set accuracies are 0.85 in expectation, with binomial standard deviation 0.008 over 2,000 rounds. Exact epsilon at M10 matches row C1 of P1 (4.38).

## Power of each null result

Null results in this phase. They are the control arms of S6 (no dependence, interval contains 0.5), the empty array records of S4d, and any dependence arm that would come back at chance.

1. S6 threshold test. The rule excludes 0.5 when the number of correct predictions out of 2,000 is at least 1,044 (accuracy 0.522, computed with the Wilson formula in the scratch file). By exact binomial probability, the probability that the rule excludes 0.5 is 0.44 at a true accuracy of 0.520, 0.61 at 0.525, 0.77 at 0.530, 0.88 at 0.535, 0.95 at 0.540 and 0.99 at 0.550. The smallest true accuracy that the check finds with 80 percent power is 0.531. For the symmetric rule used here accuracy equals 0.5 plus half the difference between the participation probability of high rounds and of low rounds, so the smallest difference found with 80 percent power is 0.062. The size of the test when the true accuracy is 0.5 is 0.026 for the one sided rule (0.052 for the two sided reading used in the control rows). A control arm that contains 0.5 therefore rules out a dependence of 0.062 or more in participation probability between the high and the low class, for this threshold and this observer only. It does not rule out smaller dependence, a dependence on a different function of the norm, a dependence that acts on the other clients, or an observer that uses timing or message sizes. The covered inputs are the two observable bits (release bit, participant set) in a single seed of 2,000 independent rounds each.
2. S4d. The check reads the recorded replies at the ServerApp grid and counts array records and arrays in them. It is exact for the recorded objects, with no sampling error. Positive control: the unit tests apply the same function to a reply that carries one non-empty array record and to the unmodified replies of the v0.15 capture format, and it must report arrays in the first and none in the second. The null covers the array records of the collect-stage replies only. It says nothing about the masked vector, which travels as bytes inside a config record by the design of the protocol, and nothing about the setup, share keys and unmask stages.
3. A dependence arm that returns accuracy near 0.5 would be reported as a failed prediction. Its detection power is the one in item 1, which at the registered strength of 0.85 versus 0.15 is above 0.999.
4. S4 itself is not a null. It is an exact positive check, with a single positive control available in the existing W5 run (metrics record present and empty when the client returns no metric) and in a unit test where the metrics are removed from a recorded reply and the check must fail.

## Stopping rule

Fix before the first run: S4 has seeds 0 and 1, one SecAgg+ run each, 4 clients, 1 round. S6 has 4 arms of 2,000 rounds, one pass each, with the seeds above. S6b has two sensitivity pairs and two noise samples of 20,000 runs, plus the 200 draws of S6-clip. No replication is allowed for S6 and S6b. For S4 a run may be repeated once only when it did not reach the first Flower round for an infrastructure reason (image build, network, port or permission failure, shown by a capture summary marked incomplete and a Docker log). Both attempts are then reported. If the run did not finish for a reason that cannot be repaired within about 45 minutes of work, S4 is reported as NOT RUN and S6 and S6b are delivered alone. Nothing else is added after the first full run. A failed row is not re-drawn, re-tuned or dropped.

## Limits

Every clause that no script check covers is listed here.

1. The dependence of participation on the norm is a modelling assumption of this study. Nothing here shows that any client behaves this way, and no real deployment was observed.
2. The nine other clients always respond and have the same norm, weight and direction type. Background dropout, failures of other clients and unequal weights are not in the S6 and S6b rounds. Unequal weights are row C3 of P1.
3. The observer is told the direction of the dependence in advance. An observer without that knowledge would need labelled rounds, which are not modelled.
4. S6 and S6b drive the strategy class `DifferentialPrivacyServerSideFixedClipping` of `flwr.server.strategy` directly with a constructed result list and a constructed failure list. They do not run the SecAgg+ workflow, so how a real dropped or failed client appears in `state.failures` is not exercised. The classes in `flwr.serverapp.strategy` are not driven. P1 measured the same C4 numbers on them.
5. The failure mode in the bit arms assumes that a reported failure reaches `aggregate_fit` as a non-empty failure list. How a given deployment reports a missing reply (a timeout, an error message, silence) was not examined here.
6. S4 runs one Docker host, four clients, one round, two seeds, the legacy `flwr.server.strategy` API with `SecAggPlusWorkflow`. The metric types are two floats and one integer. Other types, larger metric records and several rounds were not run.
7. S4 says that the values reach the ServerApp process and the strategy. It does not say what anyone can infer from them. The metrics here are fabricated for the probe and the loss value is data dependent only through the client's own training records. No claim about leakage from the values follows.
8. The relay streams recorded in the S4 runs are not analysed in this phase. A network observer between the SuperNode and the SuperLink is not examined. The server side proxy sees the messages as the ServerApp sees them.
9. S4d checks array records of the collect-stage reply. It does not check that the masked vector bytes carry no information about the update. That is W1 and W2 of v0.15, with their own limits.
10. The participant set and the reply sizes in S4 are recorded without a prediction and are descriptive only. Message timing and size as a channel (channel 8) is not examined. An active server (channel 7) is outside the assumptions of both protections and is not examined.
11. S6b epsilon values are per round, zero-out adjacency, delta 1e-5, Gaussian mechanism only, without sampling amplification, composition or an accountant. The sensitivity is measured for one client that is present in both configurations. The sensitivity of the target itself when present is not measured separately.
12. The rows S6b-mix use the measured M10 and M9 multipliers and the participation of the S6 set-dep arm. They are not a measurement of a separate mechanism.
13. One seed per S6 arm and no multiplicity correction. The tolerances are the author's judgments. Controls are expected to contain 0.5 with probability about 0.95 each and no re-draw is made.
14. The scratch computation of the power numbers and of the two epsilon values was run before this file and is disclosed in item 4 of the section on prior knowledge. The repository history cannot prove that no mechanism ran before the commit that adds this file.
15. The Docker run is on this sandbox (2 CPUs) and not on the hosted runner of v0.15. Image contents come from a local rebuild of `docker/flower/SuperExec.Dockerfile`.

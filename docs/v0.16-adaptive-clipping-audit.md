# v0.16 T8b: how Flower implements adaptive clipping, measured against Andrew et al. (2021)

Status: measured, integrated in release 0.16.3 (not yet peer reviewed).
Pre-registration: `docs/preregistration/v0.16-adaptive-clipping.md` (committed before the harness existed and before any full run).
Evidence: `reports/results/privacy/v0160/flower_adaptive_clipping/flwr-1.27.0/` and `flwr-1.44.0/`.
Harness: `scripts/audit_flower_adaptive_clipping.py`. Tests: `tests/privacy/test_audit_flower_adaptive_clipping.py`.
Reference: Andrew, Thakkar, McMahan and Ramaswamy, arXiv 1905.03871.

## Summary

The harness runs the four public adaptive clipping strategy classes of `flwr` (server side and client side, each in the legacy `flwr.server.strategy` API and the Message API `flwr.serverapp.strategy`) with a `FedAvg` inner strategy and fake client replies. It was run on `flwr` 1.27.0 (pinned by this repository) and 1.44.0, the only two releases installed here. Every one of the 82 rows per version held its pre-registered prediction, and the measured numbers are the same on both versions and on all four variants to the digits shown below.

1. The noise budget split follows the paper. The model noise multiplier is adjusted to (z^-2 - (2 sigma_b)^-2)^(-1/2), the default count noise is m/20, the inverse relation returns the configured z to within 1.2e-16, and an input with z at or above 2 sigma_b is rejected (rows A1, A2).
2. The count noise follows the paper. The noise is added to the count before the division by the number of replies, so the standard deviation of the noisy fraction is sigma_b / m (row A5).
3. The geometric update has the paper's form and the paper's defaults (rows A0, A3).
4. The bit that feeds the update is set when an update IS clipped. In the paper b_i is 1 when the update is NOT clipped. With the update rule unchanged this moves the clip in the opposite direction to the paper reading: when every update is clipped the clip shrinks by exp(-0.1) per round at defaults, where the paper reading grows it by exp(0.1) (rows A3, A4, A4b, A10). Against a fixed set of update norms the clip keeps moving away from the target quantile instead of settling at it (row A11).
5. The model noise is scaled with the clip norm after the round's update. Algorithm 1 of the paper scales it with the norm used for clipping in that round. This holds for the server-side and the client-side variants (row A6).
6. When fewer clients reply than `num_sampled_clients`, the noise scale uses `num_sampled_clients`, the fraction divides by the reply count, and a warning is logged (row A7).
7. The count noise and the model noise come from the numpy global generator, and the constructors take no seed (row A8).

These are measurements under stated configurations on synthetic updates. They are not statements about how well a trained model behaves, and the privacy accounting of the whole mechanism was not measured.

## Setup

16 float32 parameters, global model zero, `FedAvg` with equal `num_examples` of 1. Updates are vectors along one axis with a chosen L2 norm. For V1 and V3 the strategy clips. For V2 and V4 rows A3, A4, A4b, A10 and A11 take the bit from the real client mod (`flwr.client.mod.adaptiveclipping_mod` and `flwr.clientapp.mod.adaptiveclipping_mod`) fed the clip norm the strategy puts in its config. Rows A5 to A8 give V2 and V4 a chosen number of set bits. The counted fraction is recovered from the new clip as f = 0.5 - ln(C_1 / C_0) / 0.2. Noise rows use 10,000 rounds (A5) and 20,000 rounds (A6, A7) with a fixed numpy seed. The noise free path is a noise multiplier of 0, which stores a count noise of 0.

## Where the measurement differs from the paper reading

Each item gives the configuration that would be needed to reach the paper reading, or says that none was found.

1. Bit direction (A3, A4, A4b, A10, A11). The bit is set for clipped updates, and the update rule is the paper's rule applied to that fraction. Both the server-side code and the client mods do this, in both versions. Configuration needed: none found. `target_clipped_quantile` only moves the fixed point and cannot change the sign, and a non-positive `clip_norm_lr` is rejected by every constructor (checked once outside the harness, see the deviation log). The class documentation describes the argument as the desired quantile of updates that should be clipped, so the naming is consistent with the implementation. What differs is the sign of the loop against the paper's. Reasoning, not measured: the direction does not change what the count query reveals, so no privacy statement is made from this row.
2. Order of operations (A6). The update of the clip happens before the noise is added, and the noise uses the new clip. The paper's Algorithm 1, as read once, scales the noise with the clip used in that round. At the A6 configuration the new clip is 0.6075 of the old one on average. At defaults the ratio is about 0.905 when all updates are clipped, which is the figure the earlier phase measured in its rows A1 and A2. Configuration needed: none found. Whether the paper's order is the intended one for the framework was not checked.
3. Fewer replies than sampled (A7). The paper fixes m and has no reading. The measurement records which count is used where. The noise scale uses `num_sampled_clients`, which agrees with the paper if m means the configured cohort. The fraction uses the reply count. To remove the mismatch, set `num_sampled_clients` equal to the number of replies. Flower logs a warning in this configuration on both versions and aggregates anyway.

## Corrections to earlier text

`docs/v0.16-p1-flower-dp-audit.md` said the client-side adaptive variant adds noise before it updates the norm. Row A6 on V2 and V4 measured the opposite, and the code reading agrees: the client-side classes aggregate, update the clip, then add noise. The same document said the direction of the clip movement was not compared with the paper, which is now done in A3 and A4. Both statements were corrected in release 0.16.3 and the correction is listed in `CHANGELOG.md`.

## Limits

1. Two releases only, 1.27.0 and 1.44.0, run with the default Python 3.13. `/tmp/flwr_latest` holds the same 1.44.0 files, so it adds nothing. Other releases were not run.
2. The legacy classes are identical in the two versions apart from import paths, and the Message API classes differ only in how arrays are wrapped, by a file diff. Identical results are therefore expected and are not independent evidence.
3. All variants and both versions used the same seeds, so the noise rows share one noise sample and their agreement is not independent either.
4. Fake client replies on one small synthetic parameter vector. No training, no real data, no deployment. The harness says nothing about how often the measured configurations occur.
5. The client-side noise rows A5 to A8 feed a chosen number of set bits and rely on rows A3 and A4 for what a set bit means. Only A3, A4, A4b, A10 and A11 run the real client mods.
6. The paper's relations were read through a summarising fetch of the ar5iv copy, once for the ordering and bit definition and once before for the budget relation. The ordering reading comes from the pseudocode lines of one fetch and is moderately confirmed, not double checked against the PDF. The paper's justification for the factor 2 in 2 sigma_b was not confirmed.
7. The privacy guarantee of the whole mechanism, including the release of the noised count and composition over rounds, was not measured. No epsilon is reported.
8. The harness was written after the pre-registration commit in the same working session. Predictions came from code reading and from the earlier phase's adaptive rows, which the pre-registration discloses.
9. Quick smoke runs of the harness were done before the full runs, as listed in the deviation log.

## Reproduce

```bash
python3 -I scripts/audit_flower_adaptive_clipping.py --out out/ # about 25 minutes
PYTHONPATH=/tmp/flwr44 python3 scripts/audit_flower_adaptive_clipping.py --out out44/ # 1.44.0
python3 scripts/audit_flower_adaptive_clipping.py --out out/ --quick   # about 2 minutes
pytest tests/privacy/test_audit_flower_adaptive_clipping.py
```

Quick mode uses 500 and 1,000 rounds. At 500 rounds the A5 standard error is about 3 percent, which is the size of the tolerance, so A5 can fail in quick mode. The full run uses 10,000 rounds.

## Deviation log

Nothing above the Deviation log heading of the pre-registration was edited after its commit. The same entries are in that file.

1. Row A8 configuration. The pre-registration named z = 1 with n = 10. Flower rejects that at construction because z equals 2 times the default sigma_b of 0.5, which is the same boundary as row A1c2. The harness uses n = 20 with 20 updates, and 8 set bits for the client variants. This was found in the first smoke run and the harness was changed before any full run.
2. Smoke runs. Before the full runs the harness was run in quick mode on 1.27.0 and on 1.44.0 and the output was read. In quick mode A5 was outside its 3 percent tolerance, because 500 rounds give a standard error of about 3 percent. No tolerance and no round count of the full run was changed.
3. Choices the pre-registration left open. The A1d grid is z in 0.1, 0.5, 1, 2 and 5 each with sigma_b of 0.6 z and 5 z, plus (1, 0.51) and (1, 100). The A7 warning is matched by the text "sampled clients" in a WARNING record of the `flwr` logger. For the client variants the set bits are the first k replies. Noise is the output minus the output of a noise free twin strategy at the same clip.
4. Row A9 is emitted as one summary entry per client-side variant listing whether each of its rows held.
5. Command line. The 1.27.0 run used `python3 -I`. The 1.44.0 run used `PYTHONPATH=/tmp/flwr44` without `-I`, because `-I` ignores `PYTHONPATH`. Both used the same interpreter and packages.
6. One check outside the harness and not in the JSON, not pre-registered. Constructing each of the four classes with `clip_norm_lr` of -0.2 raises `ValueError` on both versions.
7. The Flower warnings were printed to the terminal during the runs. This does not affect the results.

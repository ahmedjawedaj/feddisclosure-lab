Caveats that matter when quoting these results:

* W1 is a vacuous pass. The naive attack scores 0 of 40, far below the floor of 0.725, and gets nothing from a single masked vector, which is expected. The pooled Wilson intervals treat the 40 images as independent although the 8 images of a seed come from one update, so the effective n is closer to 5 seeds. The pass rule uses point estimates. A positive control at the analysis level (`test_w1_fails_when_the_victim_reply_carries_an_unmasked_update`) feeds an unmasked quantised update as the masked vector and checks that W1 then fails.
* W5 passes on sample counts only. The repository client returns no metric values, so the metrics half of the row was not exercised. The check output now reports `counts_visible` (20) and `metrics_present` (0) separately and sets `metrics_vacuous`. The verdict rule is unchanged and count visibility decides it.
* W3 is judged on pooled rates and mean MSE only, which gives low power with 5 seeds. It compares different rounding draws. The per-seed gaps (captured minus simulated) are larger than the tolerances in places and cancel when pooled. Rate gaps by seed: +0.25, 0, -0.125, -0.25, +0.25. Mean MSE gaps by seed: -0.0111, -0.0013, +0.0100, +0.0154, +0.0011. Four of the five seeds exceed the 10 point rate tolerance and two (seeds 2 and 3) exceed the 0.01 MSE tolerance, so a per-seed reading of the rule would not pass. The pooled reading is the one used, and the label says so.
* The real wire format matched the reading of the Flower source. Arrays were found as single float32 objects in the relay streams.
* Four clients, one round, one Docker host.

## Question

The v0.14 view study used the upstream SecAgg+ quantiser arithmetic in a simulation. It did not look at a deployed stack. This work package asks what an observer actually sees on a deployed Flower 1.27.0 SecAgg+ stack and whether the simulated attack numbers hold there.

Setup of every run. Four clients, eight public digits each, one round, one local full batch SGD step, learning rate 0.15, model `DigitMLP` (64 inputs, 10 outputs). Labels are known to the attacker. The victim is client 0. The data selection is `select_view_records` from `src/feddisclosure/attacks/view_seed.py`, the same function the simulation uses.

## Two observers

**Server view.** `RecordingGrid` in `src/feddisclosure/training/secagg_server_capture.py` wraps the ServerApp grid. All four SecAgg+ stages pass through it (setup, share keys, collect masked vectors, unmask). For every message it records direction, stage, node id, timestamp, payload size and the SHA-256 of the content. It also records the hash of every array and every bytes value. For the replies of the collect stage it saves the masked vectors themselves, the clear sample count and the metric record. It saves the global model that goes out, and the final dequantised aggregate that the workflow hands to `aggregate_fit`. It never opens a client dataset. The wrapper returns the grid's reply objects unchanged, and a test checks this.

The existing application `secagg_server.py` is not edited. The capture ServerApp calls its `main` and swaps the strategy class for a subclass during the call. The default application behaves exactly as before.

**Network view.** `docker/wire_relay/relay.py` is a plain TCP relay. `compose.wire.yaml` puts one relay in front of each SuperNode, so the relay name tells which site a connection belongs to. For every connection the relay logs byte counts, timestamps and a rolling SHA-256 per chunk, and it dumps the raw stream to `${FDL_RUN_DIR}/relay` (size capped, truncation flagged). It parses nothing. The analysis reads HTTP/2 framing and gRPC message framing from the dumps, and falls back to the raw bytes when the dump does not parse.

**Linking the views.** A proxied object is an array or a bytes value. Its identity is the SHA-256 of its exact bytes. Flower sends an array as an `ArrayChunk` object whose content is the numpy-format bytes, so the same bytes appear inside the relay stream. The analysis extracts every numpy-format blob from the relay dump, hashes it and looks the proxied hashes up. A second search looks for the raw float32 bytes of each saved array. This link also maps each node id to a site, because the masked vector of a node appears only in the relay of its own site.

## Two modes per seed

1. SecAgg+ run: upstream `SecAggPlusWorkflow` with the secaggplus client modifier.
2. Plaintext control: the same app, strategy and seeds with the default workflow and no SecAgg+. The relay must be able to recover each client update here.

The two runs of a seed share data, initial model and training seeds. The client receipts (`weights_sha256`) of both runs are compared, so the plaintext updates are shown to be the updates the SecAgg+ clients also had.

## Predictions and how each is decided

All rules are the pre-registered ones.

| ID | Rule | How the analysis decides it |
|---|---|---|
| W1 | Recognisable rate at most floor plus 5 points | The masked vector of the victim is dequantised naively with the public clipping range, quantisation range and the visible weight. Gradient matching inversion is run on it with known labels. The floor is `class_average_rate_mse_below_0_05` from `label_floor`. Pooled over seeds |
| W2 | Max coordinate error below the proven bound in every run | Captured dequantised aggregate against the exact weighted mean of the plaintext updates. Bound is 2 c n / T plus the float64 server term, plus the weight rounding term when sizes differ (`docs/proofs/one-round-secagg-error.md`) |
| W3 | Rate within 10 points and mean MSE within 0.01 over at least 5 seeds | Aggregate inversion on the captured aggregate against the simulation (`secagg_aggregate`) run on the run's own data and the captured initial model. Fewer than 5 seeds cannot pass |
| W4 | Recognisable rate at least 85% | The initial model and each client update are rebuilt from the relay streams alone. Inversion runs on the victim's rebuilt update. The rebuilt updates are also compared bit for bit with the proxy record |
| W5 | Observed in 100% of recorded SecAgg+ replies | Share of collect stage replies with the sample count and the metric record in clear, and the count equal to the true record count |
| W6 | Every proxied object hash appears in the relay stream | Every unique object hash of the plaintext run is searched in all relay dumps by blob hash and by raw float32 bytes |

Rates are pooled over victim images and reported with Wilson 95% intervals from `src/feddisclosure/evaluation/intervals.py`. A prediction that fails is written as FAIL and not reworded.

### Data and initial model

The analysis does not assume the simulation partition. It reads the run's manifest, verifies the file hashes, loads the records the clients actually held, and uses the captured initial model. It reports whether the selection equals `select_view_records` for that seed (it does by construction). The W3 simulation always runs on the run's own records and model.

### Fail closed

* The orchestrator marks a run failed when the CLI exits non-zero, when the capture summary is not complete, when a relay log is missing or has no traffic, or when the client receipts do not verify. It then exits with code 2 and writes `capture_status.json` with `complete: false`.
* The analysis refuses a run whose capture summary is incomplete. A seed that cannot be evaluated for a check makes that check FAIL. Exit code 3 means at least one seed could not be analysed.
* The recording proxy raises on any recording error. The run then stops and the summary says `completed: false`.

## How to run

On a Docker host:

```bash
export PYTHONPATH=src:.
python scripts/run_wire_capture.py --seeds 5 --output reports/results/privacy/v0150/wire/local
python scripts/analyze_wire_capture.py --runs reports/results/privacy/v0150/wire/local
```

Print the commands without running them:

```bash
python scripts/run_wire_capture.py --seeds 2 --output /tmp/wire --dry-run
```

On GitHub (dispatch only):

```bash
gh workflow run wire-capture.yml --ref main -f seeds=5 -f iterations=300
```

Expected time on the hosted runner is about 25 to 40 minutes for 5 seeds (image build once, then about two to three minutes per run).

Where the saved evidence is. The workflow writes to `reports/results/privacy/v0150/wire/hosted` on the runner. The evidence of the hosted run described above was committed as `reports/results/privacy/v0150/wire/live/` (the directory name in this repository is `live`, not `hosted`). The commands above write to `wire/local` so that a local run never lands in the saved evidence. The tracked `wire/live/env/*.env` files are generated run settings. They hold only paths on the hosted runner and SHA-256 digests of the staged partitions, no secrets and no credentials, and they are kept in Git on purpose, although `.gitignore` ignores `.env` files elsewhere (a plain `.env` and the `*.env` files under `native_flower`).

## What the unit tests cover

* Hash recording and transparency of the proxy, all four stages, push and pull path, error propagation, and the capture ServerApp against the real upstream workflow and client modifier in one process.
* Relay stream search: a known float32 array is found, a different one is not, and arrays split by HTTP/2 framing or inside a compressed gRPC message are found at the right layer.
* The real relay over localhost, including the dump cap and tamper detection.
* The W check functions on known answers, including failing and edge cases, and the bound arithmetic against the numbers in the proof note.
* The analysis on synthetic runs with known answers, and variants that must fail (missing relay traffic, hidden counts, aggregate outside the bound, too few seeds, a seed that cannot be analysed).
* Static checks of the compose override and the workflow.

## What only the hosted run can show

* That Flower 1.27.0 sends each array as one verbatim object over the SuperNode to SuperLink gRPC channel, which the design reads from the source and the analysis can fall back on at the HTTP/2 and gRPC layers.
* The real relay dumps, container permissions on the bind mounts and the relay start order.
* The real W1 to W6 numbers.

## Limits

* One Docker host and an insecure internal network.
* The relay sees the SuperNode to SuperLink channel only. The ServerApp to SuperLink channel is seen by the proxy.
* The client in this repository returns no metrics, so W5 checks that the metrics record is present and that the sample count is visible and correct. The metrics half is vacuous here. A client that returned a metric would expose it the same way, but that was not tested.
* Four clients and one round. Results do not extend to other sizes or to several rounds.
* W3 compares two attack results that use different rounding draws. Equal results are expected only up to that noise.
* A failed reconstruction is evidence about this attack only. It is not a privacy guarantee.
- W1 treats a masked vector as opaque and runs only the gradient-matching attack on it. It does not examine how masks are generated. That is the subject of an open upstream issue and pull request (flwrlabs/flower #7522 and #7570), and W1 says nothing about it.

# Reproducibility notes for v0.15

This page says which software produced which evidence, what a separate reproducibility review pass (R4) re-ran and what it found, and which inputs a fresh checkout does not have. It claims no more than the review checked.

## Which torch produced which evidence

| Evidence | torch | Where this is recorded |
|---|---|---|
| v0.14 native Docker and Flower runs (`reports/results/native_flower/v014/`) | 2.5.1+cpu | `torch_reference.json` of the 7 runs and `01_pip_install.log` |
| Docker image, and the hosted workflows that start Docker (`flower-docker-native`, `parity-live`, `scaling-n8`, `wire-capture`) | 2.5.1 CPU | pinned in the Dockerfile and the workflow files. The live parity, wire capture and 8-client memory evidence come from these |
| Local v0.15 runs (DP informed attack, fault matrix, scaling study, Fashion-MNIST study, external baselines, label floor and interval recomputation) | 2.15.0+cpu | the session environment. Only `prereg_check_external.json` stores it (its `versions` block). The other result files do not record a torch version |
| Hosted Fashion-MNIST rerun (`fashion_mnist/hosted/`) | 2.5.1 CPU | pinned in `.github/workflows/fashion-mnist-study.yml`. The result files do not record a torch version |
| v0.14 Opacus DP studies and LiRA runs | not recorded | the saved files do not say. Opacus 1.6.0 needs torch 2.6.0 or newer |

The scaling study and the DP informed trials were regenerated byte for byte under both torch 2.15.0+cpu and torch 2.5.1, so for those two the torch build did not change a saved number.

Torch 2.5.1 and Opacus 1.6.0 cannot be installed together without ignoring a declared requirement. The package metadata of Opacus 1.6.0 says `torch>=2.6.0`. The Docker based workflows use torch 2.5.1 and do not import Opacus. Anything that imports Opacus needs torch 2.6.0 or newer. `docs/v0.14-reproduce.md` has the install commands for both cases.

## What review R4 reproduced

A separate review pass re-ran parts of the v0.15 evidence from the saved inputs.

Byte for byte identical output:
* the scaling study (61 JSON files)
* the DP informed attack trials
* the fault matrix `summarize` step
* the external baselines `summarise-inversion` step

Reproduced numerically, with only runtime or version fields differing:
* the SecAgg+ bound search (`secagg_bound_search.json`)
* the label floor
* the recomputed intervals

Not part of that review, so not claimed here: the Docker runs and hosted workflows, the attack tuning, the Fashion-MNIST download and tuning, and the LiRA reference run. Their saved outputs are evidence of one execution each.

## Inputs a fresh checkout does not have

`.gitignore` excludes `data/` (prepared partitions and raw dataset files) and every `*.pt` file. Four things follow.
* The two fault matrix gate tests in `tests/privacy/test_fault_matrix.py` need prepared partitions and saved final models. Without them they skip and print the missing paths.
* `scripts/study_reply_order.py replay` and `p3` need the same kind of inputs and stop with a `checkpoints not in checkout` message. `summarize` works from committed files.
* The MNIST and Fashion-MNIST files are downloaded or placed by hand, checked against pinned SHA-256 values, and never committed. See `docs/data-provenance.md`.
* The tracked `wire/live/env/*.env` files hold only paths on the hosted runner and digests of staged partitions.

## Fast test suite counts depend on the environment

`pytest -q -m 'not slow'` skips whole modules when `flwr` or `opacus` is missing, so the pass and skip counts differ between environments. The README quick start gives the count for the hosted CI unit job environment (torch only, no `flwr`, no `opacus`, clean checkout) and for a full environment (everything installed, git-ignored data present). Both are recorded by `scripts/record_fast_suite.py` with the commit they ran on, and `scripts/verify_readme_claims.py` flags a record that is older than the code. The records are `fast_suite_ci_env.txt` and `fast_suite.txt` in `reports/results/privacy/v0150/`.

## Install hint

Install the CPU build of torch first, so that pip does not pull a CUDA build when it installs the extras:

```bash
python -m venv .venv && source .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -e '.[test,research]'
```

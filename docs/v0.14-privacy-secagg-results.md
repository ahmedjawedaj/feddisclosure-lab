# v0.14 results: SecAgg+, OpenDP, Opacus and full MNIST

Branch `feature/v0.14-native-execution`. All numbers below are re-derivable from the files named next to them. Nothing here is a privacy certification. Formal guarantees (epsilon, delta) are reported separately from empirical attack results.

## 1. Native Docker + Flower (Phase 1 recap and MNIST scale run)

Evidence: `reports/results/native_flower/v014/`.

| Run | Data | Rounds | Result |
|---|---|---|---|
| run-iid-d | Digits, IID | 2 | PASS, parity within 1e-5, independent `docker inspect` of 8 containers |
| run-iid-repeat | Digits, IID | 2 | PASS, final model byte-identical to run-iid-d |
| run-noniid-labelskew | Digits, severe label skew | 2 | PASS, parity within 1e-5 |
| fault-before-run, fault-after-round1, fault-supernode-down-before-run | Digits | 2 | Correctly refused by the gate (see limits) |
| run-mnist-full-iid | Full MNIST train split (60,000 images, SHA-256 verified), 3 sites | 10 | PASS, parity True, 3 clients x 10 train and 10 evaluation receipts, final global accuracy 0.9568 on pooled validation shards, worst client 0.9503 |

The MNIST run took 238 seconds through `flwr run . fdl-docker --stream` against the Deployment Runtime. The independent PyTorch reference gave the same weights within 7.8e-7 per layer (tolerance 1e-5). The static topology check also passed for this run, which confirms the Dockerfile and compose edits did not regress isolation.

Limits that remain:
- Fault handling is wait-until-timeout. Flower waits for the missing node or executor, and the gate refuses the run afterwards. It is not fail-fast.
- Parity checks weight equality only. Isolation is shown by the topology and `docker inspect` evidence, not by parity.
- The MNIST run used IID partitioning only. A non-IID MNIST native run was not executed. Non-IID was covered on Digits natively and on MNIST in the DP study below.
- Hosted GitHub Actions did not run because no authorised remote exists. BLOCKED.

## 2. Flower SecAgg+ (official implementation)

Evidence: `reports/results/secagg/v014/`, summary `secagg_verification.json`.

Setup: `SecAggPlusWorkflow` on the server and `secaggplus_mod` on the clients, inside the Docker topology with 3 real clients, 3 shares, reconstruction threshold 2. A matched plaintext control uses the same app with `use-secagg=false`.

| Check | Result |
|---|---|
| 2 rounds with SecAgg+ | "Secure aggregation completed" twice, 3 results and 0 failures per round |
| SecAgg+ vs plaintext control, max abs diff | 3.56e-5 |
| Plaintext control vs independent PyTorch | 2.98e-8 |
| Single-round error vs analytic bound, max weight 1000 | 2.53e-5 observed, 2.98e-5 bound |
| Single-round error vs analytic bound, max weight 200 | 5.48e-6 observed, 5.96e-6 bound |

The bound is n x quantisation step x max_weight / total_samples per round. It comes from reading the upstream quantisation code. My first tolerance (2e-5) ignored the max_weight amplification and was too tight. It was superseded, not loosened to fit, and the derivation is recorded in the JSON.

Collusion (single round, victim client 2):
- Server alone assuming the victim equals the aggregate: error 2.08e-2.
- Server plus 1 colluding client: error 1.89e-2.
- Server plus 2 colluding clients (n minus 1): error 7.6e-5, so the victim update is recovered to quantisation precision.

So SecAgg+ gives no protection against an honest-but-curious server that also controls n minus 1 clients. This is inherent to secure aggregation and not a defect of this setup.

Dropout, n=3 and threshold 2:
- Client executor stopped before the run: no model written, run refused.
- Client executor stopped after the first train receipt: upstream logged "Not enough shares to recover secret in unmask vectors stage" and no model was written.
- Reading the upstream source (`secaggplus_workflow.py`, share counting per neighbour with the node's own ID removed) suggests n=3 cannot tolerate a missing client at this threshold and that n of 4 or more is needed. This explanation comes from code reading. I did not run an n of 4 or more topology, so treat it as unverified.

Two silent-failure bugs were found and fixed on the way (plaintext control writing untouched initial weights, mid-protocol dropout publishing a round-1 model). The server now refuses to write a final model unless every configured round produced an aggregate. The failed runs are kept as `*-preguard` and `plaintext-control-failed-modbug`.

What SecAgg+ does not show here: it hides individual updates from an honest-but-curious server only. It does not bound what the aggregate or final model leaks, and it provides no differential privacy.

## 3. OpenDP releases with accounting

Evidence: `reports/results/privacy/v014/opendp/`.

Engine: OpenDP 0.16.0 `make_laplace`, pure epsilon-DP, add/remove-one adjacency, count sensitivity 1, persistent SQLite ledger with fixed-point micro-epsilon.

- Privacy map returns the requested epsilon at every tested level.
- Empirical MAE matches Laplace theory (epsilon 1.0: 0.993 vs 1.000, epsilon 0.25: 4.017 vs 4.0).
- Empirical distinguishing advantage stayed below the DP bound (e^eps minus 1)/(e^eps + 1) at all epsilons. This is a sanity check and not a proof.
- Three-site HTTP run: 4 releases at epsilon 0.25 spent the budget, the 5th was refused with HTTP 409.
- Ledger checks all passed: retry with same request ID returns the identical cached release at no extra cost, ID reuse with different parameters is rejected, cap increase is refused, restart cannot reset spent budget.

Utility cost is large for small counts. At epsilon 0.05 the MAE is about 20 on a true count of 3. Do not read the formal guarantee as useful accuracy.

## 4. Opacus DP-SGD in federated training

Evidence: `reports/results/privacy/v014/digits_full_dpfedavg/` (`runs.json`, `summary.json`).

Setup: DP-FedAvg with per-client persistent Opacus `PrivacyEngine` (RDP accountant, Poisson sampling, clip norm 1.0, delta 1e-5) across rounds so the budget composes over the whole run. Matched non-private baseline uses the same seeds, data, rounds and optimiser. 10 seeds, 20 rounds, 5 local epochs, Digits, IID and label skew. This is single-process simulation of the FL loop, not the Docker topology.

Formal guarantee reported: achieved epsilon per client at delta 1e-5 (max over clients). Achieved values never exceeded the target (0.996, 3.991, 15.992 for targets 1, 4, 16). `secure_mode` is off, so floating-point and RNG caveats apply.

Test accuracy (mean, 95% CI over 10 seeds):

| Partition | Non-private | eps 16 | eps 4 | eps 1 |
|---|---|---|---|---|
| IID | 0.964 [0.961, 0.967] | 0.929 [0.922, 0.936] | 0.905 [0.898, 0.912] | 0.594 [0.556, 0.632] |
| Label skew | 0.903 [0.897, 0.908] | 0.857 [0.836, 0.878] | 0.765 [0.734, 0.796] | 0.424 [0.366, 0.483] |

Worst-client validation accuracy:

| Partition | Non-private | eps 16 | eps 4 | eps 1 |
|---|---|---|---|---|
| IID | 0.941 | 0.881 | 0.863 | 0.529 |
| Label skew | 0.899 | 0.631 | 0.461 | 0.112 |

Under label skew, DP hurts the worst client far more than the average. At epsilon 1 the worst client is near chance.

Empirical membership inference (loss threshold, AUC):
- All modes sit between 0.505 and 0.530. The attack is near chance even without DP.
- DP did not reduce the measured AUC. Paired differences versus non-private are slightly positive (for example IID eps 16: +0.011, CI [0.007, 0.015]. Label skew eps 16: +0.024, CI [0.018, 0.031]).
- This is a negative result and is preserved as measured. It does not show DP is harmful. It shows this attack has no measurable signal on this small, well-regularised setup, so the test cannot show a benefit. It says nothing about stronger attacks.

Communication is identical across modes (1,156,800 bytes). DP wall time per run is about 4 to 5 times the non-private time in this simulator.

## 5. Full MNIST DP-FedAvg study

Evidence: `reports/results/privacy/v014/mnist_full_dpfedavg/`. Full 60,000 image MNIST split across 3 sites, 10 rounds, 1 local epoch, batch 32, learning rate 0.1, delta 1e-5, clip 1.0, epsilon targets 2 and 8, seeds 0 to 2 only. With 3 seeds the t-intervals are wide and some worst-client intervals exceed 1.0, so read them as "very uncertain" rather than as bounds.

| Partition | Mode | Achieved eps | Test acc | Worst-client acc | MIA AUC |
|---|---|---|---|---|---|
| IID | non-private | none | 0.954 [0.951, 0.958] | 0.947 | 0.500 |
| IID | DP eps 8 | 7.996 | 0.897 [0.893, 0.901] | 0.889 | 0.499 |
| IID | DP eps 2 | 1.994 | 0.893 [0.890, 0.895] | 0.884 | 0.499 |
| Label skew | non-private | none | 0.851 [0.845, 0.857] | 0.870 | 0.462 |
| Label skew | DP eps 8 | 7.996 | 0.781 [0.738, 0.824] | 0.727 | 0.476 |
| Label skew | DP eps 2 | 1.994 | 0.761 [0.708, 0.814] | 0.675 | 0.480 |

Paired accuracy cost of DP versus non-private: IID about 6 points at both epsilons (CIs exclude 0), label skew 7 to 9 points (CIs exclude 0 but are wide). Membership AUC stays near 0.5 in every cell. Under label skew the DP AUC is slightly higher than non-private (+0.014 to +0.017, CIs exclude 0), again the opposite of a leakage reduction, and the attack signal is too weak to interpret. Runtime for DP is about 9 to 10 times the non-private simulator time on IID. Communication is the same in all modes.

The epsilon 2 and epsilon 8 accuracies are close on IID. With only 10 rounds and 1 local epoch the noise multiplier difference is small compared with other limits, so this study does not discriminate well between those two budgets.

Single-silo Opacus gate (`reports/results/privacy/v014/opacus_single_client/`, existing `run_opacus_dp_sgd.py`): 128 records, 5 epochs, achieved epsilon 7.99995 at delta 1e-5. Public test accuracy 0.167 versus 0.225 for the non-private control. Both are close to chance because the silo is tiny and training is only 20 steps, so this gate verifies the accounting path and not utility.

## 6. Claims policy

- Epsilon and delta are properties of the mechanism and accountant, reported as achieved values.
- Attack AUCs and inversion errors are empirical and only apply to the tested attacker.
- SecAgg+ is reported as a protocol that hides individual updates from the server under the stated assumptions. It is not counted as differential privacy.
- No novelty, certification or "100% secure" claim is made.

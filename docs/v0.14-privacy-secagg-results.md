The MNIST run took 238 seconds through `flwr run . fdl-docker --stream` against the Deployment Runtime. The independent PyTorch reference gave the same weights within 7.8e-7 per layer (tolerance 1e-5). The static topology check also passed for this run, which confirms the Dockerfile and compose edits did not regress isolation.

Two of the three extra MNIST runs failed the 1e-5 weight parity gate. The gate was not relaxed and both stay recorded as FAIL. What I found:
- Not environment and not threads. The independent reference is deterministic across repeats, and the Digits repeat of the native run is byte-identical.
- Flower FedAvg multiplies each client array by `n_i / total` in float32 and adds in reply order. The reference averages in float64 and casts once. The two differ by about 1 ULP per round.
- 1 ULP matters here. A one-ULP perturbation of the initial weights moves the final label-skew model by 2.9e-3 (`numerical_sensitivity.json`), so label skew and some seeds amplify the difference by orders of magnitude.
- `scripts/reproduce_flower_bitwise.py` replays the run with Flower's float32 arithmetic and searches the reply orders. It reproduces every saved Flower round bit for bit against the next-round client receipt hashes in all four MNIST runs (`bitwise_replay.json`). So the Flower run is internally exact, and the FAIL is a statement about float64 versus Flower arithmetic, not about a wrong model.
- The practical reading: for IID with a lucky seed the two agree within 1e-5. For skewed or unlucky runs they do not. A parity gate at 1e-5 is too tight for 10 rounds of MNIST, but I did not change it. A better gate would compare against the float32 replay, which is now available.

Fault handling is now fail-fast. A watchdog resolves the container IDs up front and exits with code 125 when a watched client executor or SuperNode stops. Evidence in `reports/results/native_flower/v014/fail_fast/`:

| Fault | Result |
|---|---|
| Client executor stopped before the run | Detected 1.0 s after start, run over in 11 s |
| Client executor stopped after round 1 | Detected 28 s after start, run over in 28 s |
| SuperNode stopped after round 1 | Detected 30 s after start, run over in 30 s |

Replay gate (new, `scripts/verify_flower_replay_gate.py`, summary `replay_gate_summary.json`). A run passes only when the runner and topology are native-verified, client attestations hold, and an independent float32 replay with Flower's reply-order arithmetic reproduces every per-client per-round weight hash and the final model bit for bit. All 7 native runs pass it. The old float64 1e-5 gate is unchanged and still passes 5 of 7 (label skew and seed 3 fail). The replay gate is a different and stronger claim about reproducibility. It does not turn the float64 FAIL into a PASS.

`--no-fail-fast` restores the old behaviour. The SecAgg dropout runs below need it, because there a lost client is the thing under test.

Limits that remain:
- Parity checks weight equality only. Isolation is shown by the topology and `docker inspect` evidence, not by parity.
- Hosted GitHub Actions did not run because no authorised remote exists. BLOCKED.

## 2. Flower SecAgg+ (official implementation)

Evidence: `reports/results/secagg/v014/`, summary `secagg_verification.json`.

Setup: `SecAggPlusWorkflow` on the server and `secaggplus_mod` on the clients, inside the Docker topology with 3 real clients, 3 shares, reconstruction threshold 2. A matched plaintext control uses the same app with `use-secagg=false`.

| Check | Result |
|---|---|
| 2 rounds with SecAgg+ | "Secure aggregation completed" twice, 3 results and 0 failures per round |
| SecAgg+ vs plaintext control, max abs diff | 3.56e-5 |
| Plaintext control vs independent PyTorch | 2.98e-8 |
| Single-round error vs analytic bound, max weight 1000 | 2.53e-5 observed, 2.98e-5 bound |
| Single-round error vs analytic bound, max weight 200 | 5.48e-6 observed, 5.96e-6 bound |

The bound is n x quantisation step x max_weight / total_samples per round. It comes from reading the upstream quantisation code. My first tolerance (2e-5) ignored the max_weight amplification and was too tight. It was superseded, not loosened to fit, and the derivation is recorded in the JSON.

Collusion (single round, victim client 2):
- Server alone assuming the victim equals the aggregate: error 2.08e-2.
- Server plus 1 colluding client: error 1.89e-2.
- Server plus 2 colluding clients (n minus 1): error 7.6e-5, so the victim update is recovered to quantisation precision.

So SecAgg+ gives no protection against an honest-but-curious server that also controls n minus 1 clients. This is inherent to secure aggregation and not a defect of this setup.

Dropout, corrected in this release. My first n=3, threshold 2 runs stopped the client after its first train receipt, so the client was already absent when round 2 began and had sent no key shares. That halts SecAgg+ at any n and any threshold, so it did not test a mid-protocol dropout. My earlier statement that n=3 cannot tolerate a missing client was wrong and is withdrawn.

The real test kills the client container during round 2, after key sharing. Upstream tolerates the loss when the surviving share holders number at least the reconstruction threshold. Upstream also requires threshold below the number of shares (an n=4, threshold 4 run was refused). Five scenarios ran in Docker with the rule written down before the runs (`dropout_matrix_summary.json`):

| Scenario | Survivors | Threshold | Predicted | Observed |
|---|---|---|---|---|
| n=4, kill 1 | 3 | 2 | tolerated | Tolerated, round 2 had 3 results, model within bound |
| n=4, kill 1 | 3 | 3 | tolerated | Tolerated, round 2 had 3 results, model within bound |
| n=4, kill 2 | 2 | 2 | tolerated | Tolerated, round 2 had 2 results, model within bound |
| n=4, kill 2 | 2 | 3 | halt | Halted, "Not enough shares", no model written |
| n=3, kill 1 | 2 | 2 | tolerated | Tolerated, round 2 had 2 results, model within bound |

All five match the prediction. Two earlier attempts killed too late and are kept as `*-fault-landed-too-late`. They show no dropout and are not used as evidence.

Four-client full participation:
- One round, SecAgg+ vs independent PyTorch: 3.2e-5 against the derived bound 4.0e-5. PASS.
- Two rounds, three replicates: 4.1e-5, 3.7e-5, 4.1e-5. All inside 2 times the bound.
- Two rounds, original baseline run: 1.9e-4, which is above the naive 2 times 4.0e-5 tolerance. **FAIL against that check, kept as FAIL.**
- Cause: my two-round tolerance assumed round-1 quantisation error does not grow in round 2. It can. Adding noise inside the one-round bound to the exact round-1 model and running an exact round 2 gives a difference above 2 times the bound in about 40% of 200 trials (median 3.6e-5, 95th percentile 2.0e-4, `error_propagation.json`). The 1.9e-4 outlier sits in about 24 first-layer elements, which fits ReLU activation flips. The one-round bound is a valid worst-case bound. A multi-round bound of that form is not.
- Four real runs and 200 noise trials are enough to reject the naive tolerance. They do not give a proven multi-round bound.
- Replacement: a statistical acceptance rule (`scripts/mc_secagg_multiround.py`, `multiround_acceptance_rule.json`). The same 2-round FedAvg ran 300 times with the upstream SecAgg+ quantiser arithmetic and fresh stochastic rounding. The simulation is faithful at one round (Monte Carlo maximum 3.66e-5 inside the derived worst-case bound 3.97e-5). At two rounds the difference is bimodal: median 4.2e-5, 90th percentile 1.98e-4, 99th percentile 2.09e-4, maximum 2.19e-4, and 38.7% of trials exceed the naive 2 times bound. Rule: accept a Docker run when its difference is at or below the empirical 99th percentile. All four real runs pass, at percentiles 0.72 (original baseline), 0.38, 0.09 and 0.38, so none sits in the tail. This is a percentile rule for this configuration and not a bound. It says the observed Docker values are typical of upstream quantisation noise.

Two silent-failure bugs were found and fixed on the way (plaintext control writing untouched initial weights, mid-protocol dropout publishing a round-1 model). The server now refuses to write a final model unless every configured round produced an aggregate. The failed runs are kept as `*-preguard` and `plaintext-control-failed-modbug`.

What SecAgg+ does not show here: it hides individual updates from an honest-but-curious server only. It does not bound what the aggregate or final model leaks, and it provides no differential privacy.

## 3. OpenDP releases with accounting

Evidence: `reports/results/privacy/v014/opendp/`.

Engine: OpenDP 0.16.0 `make_laplace`, pure epsilon-DP, add/remove-one adjacency, count sensitivity 1, persistent SQLite ledger with fixed-point micro-epsilon.

- Privacy map returns the requested epsilon at every tested level.
- Empirical MAE matches Laplace theory (epsilon 1.0: 0.993 vs 1.000, epsilon 0.25: 4.017 vs 4.0).
- Empirical distinguishing advantage stayed below the DP bound (e^eps minus 1)/(e^eps + 1) at all epsilons. This is a sanity check and not a proof.
- Three-site HTTP run: 4 releases at epsilon 0.25 spent the budget, the 5th was refused with HTTP 409.
- Ledger checks all passed: retry with same request ID returns the identical cached release at no extra cost, ID reuse with different parameters is rejected, cap increase is refused, restart cannot reset spent budget.

Utility cost is large for small counts. At epsilon 0.05 the MAE is about 20 on a true count of 3. Do not read the formal guarantee as useful accuracy.

## 4. Opacus DP-SGD in federated training

Evidence: `reports/results/privacy/v014/digits_full_dpfedavg/` (`runs.json`, `summary.json`).

Setup: DP-FedAvg with per-client persistent Opacus `PrivacyEngine` (RDP accountant, Poisson sampling, clip norm 1.0, delta 1e-5) across rounds so the budget composes over the whole run. Matched non-private baseline uses the same seeds, data, rounds and optimiser. 10 seeds, 20 rounds, 5 local epochs, Digits, IID and label skew. This is single-process simulation of the FL loop, not the Docker topology.

Formal guarantee reported: achieved epsilon per client at delta 1e-5 (max over clients). Achieved values never exceeded the target (0.996, 3.991, 15.992 for targets 1, 4, 16). `secure_mode` is off, so floating-point and RNG caveats apply.

Test accuracy (mean, 95% CI over 10 seeds):

| Partition | Non-private | eps 16 | eps 4 | eps 1 |
|---|---|---|---|---|
| IID | 0.964 [0.961, 0.967] | 0.929 [0.922, 0.936] | 0.905 [0.898, 0.912] | 0.594 [0.556, 0.632] |
| Label skew | 0.903 [0.897, 0.908] | 0.857 [0.836, 0.878] | 0.765 [0.734, 0.796] | 0.424 [0.366, 0.483] |

Worst-client validation accuracy:

| Partition | Non-private | eps 16 | eps 4 | eps 1 |
|---|---|---|---|---|
| IID | 0.941 | 0.881 | 0.863 | 0.529 |
| Label skew | 0.899 | 0.631 | 0.461 | 0.112 |

Under label skew, DP hurts the worst client far more than the average. At epsilon 1 the worst client is near chance.

Empirical membership inference (loss threshold, AUC):
- All modes sit between 0.505 and 0.530. The attack is near chance even without DP.
- DP did not reduce the measured AUC. Paired differences versus non-private are slightly positive (for example IID eps 16: +0.011, CI [0.007, 0.015]. Label skew eps 16: +0.024, CI [0.018, 0.031]).
- This is a negative result and is preserved as measured. It does not show DP is harmful. It shows this attack has no measurable signal on this small, well-regularised setup, so the test cannot show a benefit. It says nothing about stronger attacks.

Communication is identical across modes (1,156,800 bytes). DP wall time per run is about 4 to 5 times the non-private time in this simulator.

## 6. Claims policy

- Epsilon and delta are properties of the mechanism and accountant, reported as achieved values.
- Attack AUCs and inversion errors are empirical and only apply to the tested attacker.
- SecAgg+ is reported as a protocol that hides individual updates from the server under the stated assumptions. It is not counted as differential privacy.
- No novelty, certification or "100% secure" claim is made.

## 6. Stronger membership attack: LiRA-style shadow models

Evidence: `reports/results/privacy/v014/lira/large_overfit/`, `large_moderate/` and `large_mnist_overfit/` (`summary.json`, `models.json`, `scores.npz`). Code: `src/feddisclosure/training/lira_study.py`, driver `scripts/run_lira_study.py`. The smaller first runs (`overfit_v2/`, `moderate/`, 24 shadows and 8 targets) and the older `overfit/` are kept. Where they differ from the large runs, the large runs are the ones to read (see the correction below).

Attacker: knows the pipeline, hyperparameters, mechanism and epsilon, trains 64 matched shadow federations on random halves of the same pool, and sees only the final global model's output on a candidate record. It does not see client updates. Each of 16 target federations is scored with a per-example Gaussian likelihood ratio (IN versus OUT) on the scaled logit confidence, a global-variance variant, and a plain loss-threshold baseline. Model: MLP, 3 clients, Opacus DP-FedAvg with a persistent engine and RDP accountant, delta 1e-5. Intervals are 95% t-intervals over the 16 target federations. Empirical audit, not a guarantee.

Digits overfit regime (pool 360, 40 rounds, 10 local epochs):

| Mode | Achieved eps | Held-out accuracy | LiRA AUC | LiRA TPR at 1% FPR | Loss-threshold AUC |
|---|---|---|---|---|---|
| Non-private | none | 0.922 | 0.742 [0.730, 0.753] | 0.131 [0.113, 0.149] | 0.584 [0.566, 0.601] |
| DP eps 8 | 7.41 | 0.585 | 0.543 [0.529, 0.557] | 0.023 [0.011, 0.035] | 0.564 [0.551, 0.578] |
| DP eps 2 | 1.86 | 0.195 | 0.518 [0.500, 0.536] | 0.012 [0.007, 0.017] | 0.525 [0.507, 0.543] |

Digits moderate regime (pool 1200, 20 rounds, 5 local epochs):

| Mode | Achieved eps | Held-out accuracy | LiRA AUC | LiRA TPR at 1% FPR | Loss-threshold AUC |
|---|---|---|---|---|---|
| Non-private | none | 0.944 | 0.605 [0.596, 0.615] | 0.051 [0.044, 0.058] | 0.519 [0.510, 0.528] |
| DP eps 8 | 7.00 | 0.866 | 0.537 [0.528, 0.546] | 0.017 [0.013, 0.022] | 0.528 [0.522, 0.533] |
| DP eps 2 | 1.76 | 0.582 | 0.508 [0.499, 0.517] | 0.011 [0.007, 0.015] | 0.521 [0.511, 0.531] |

Second public dataset, MNIST 28x28 subset (pool 600, 10 rounds, 8 local epochs):

| Mode | Achieved eps | Held-out accuracy | LiRA AUC | LiRA TPR at 1% FPR | Loss-threshold AUC |
|---|---|---|---|---|---|
| Non-private | none | 0.839 | 0.823 [0.817, 0.830] | 0.233 [0.217, 0.248] | 0.642 [0.631, 0.654] |
| DP eps 8 | 6.01 | 0.555 | 0.575 [0.564, 0.586] | 0.022 [0.016, 0.029] | 0.556 [0.546, 0.567] |
| DP eps 2 | 1.52 | 0.209 | 0.504 [0.492, 0.515] | 0.015 [0.008, 0.021] | 0.524 [0.513, 0.534] |

What this shows:
- A stronger attack finds leakage that the loss threshold from section 4 could not. Without DP, LiRA reaches AUC 0.74 (Digits overfit), 0.61 (Digits moderate) and 0.82 (MNIST), against 0.58, 0.52 and 0.64 for the loss threshold. At 1% false positive rate LiRA identifies 13% to 23% of members in the overfit regimes, while the loss threshold gets 2% in each overfit regime (chance is 1%).
- The result holds on both public datasets.
- DP at epsilon about 2 brings LiRA to about chance (AUC 0.50 to 0.52). DP at epsilon about 6 to 8 does not: LiRA stays measurably above chance in all three settings (0.537 to 0.575, intervals exclude 0.5) and still identifies about 2% of members at 1% FPR. So a formal epsilon of 6 to 8 left a detectable audit signal here.
- The price is large. Held-out accuracy falls from 0.92 to 0.59 and 0.20 on Digits overfit, from 0.84 to 0.56 and 0.21 on MNIST, and in the moderate regime from 0.94 to 0.87 and 0.58. Digits moderate at epsilon 8 is the only setting that keeps usable accuracy (0.87) while reducing the attack to AUC 0.54.
- Correction to the first, smaller run. With 24 shadows and 8 targets the epsilon 8 results looked like chance (0.510 and 0.519) and LiRA looked weaker than the loss threshold on DP models. With 64 shadows and 16 targets the residual signal is visible. The small run understated the leakage because its per-example estimates were noisy. This is a reason to read any single attack result as a lower bound on leakage.
- On DP models LiRA is not clearly stronger than the loss threshold. In the Digits overfit regime at epsilon 8 the loss threshold is slightly higher (0.564 against 0.543), while in the other settings LiRA is higher or equal. Do not claim LiRA is the better attacker under DP.
- A low attack AUC does not prove privacy, and a measurable AUC does not contradict an epsilon guarantee. The formal epsilon is the guarantee and the attack audits one attacker.

Scope limits: single-process simulation (not the Docker topology), `secure_mode` off, 16 target federations per cell, Digits and a 600 image MNIST subset only. The attack targets the final global model, not client updates. Section 7 covers what observers of updates can do.

## 7. Protected versus unprotected: what an observer can reconstruct

Evidence: `reports/results/privacy/v014/view_comparison/` (`summary.json`, one `seed*.json` per seed). Code: `src/feddisclosure/attacks/view_study.py`, driver `scripts/run_view_comparison.py`.

**Correction in v0.14.3.** The v0.14.2 version of this section compared every attack with the overall mean image (MSE 0.073), which is the wrong baseline for an attacker that knows the labels. It also read the SecAgg+ aggregate row as leakage and the DP rows as protection. Both readings are withdrawn. The point estimates below are unchanged, the baseline and the intervals are new. See `CHANGELOG.md`.

Setup: 4 clients with 8 distinct public Digits records each, one local SGD step at learning rate 0.15, a shared initial model, 10 seeds, so 80 victim images per view. Client 0 is the victim. The attack is the repository's DLG-style gradient matching (300 iterations) with the true labels given to the attacker, which is a favourable privilege. The score is the mean squared error of the victim's 8 images after optimal matching (lower means more leakage). A reconstruction counts as recognisable when its error is below 0.05.

Baselines on the same seeds (`reports/results/privacy/v0143/label_floor.json`, built by `scripts/compute_label_floor.py` with the exact v0.14.2 record selection, no attack rerun):
- Label-only floor: rebuild every victim record as the class-average image of the labelled public pool (the images no client holds). MSE 0.046, 54 of 80 images recognisable (67.5%). The matched-scoring variant gives MSE 0.045 and the same rate. The floor is a prior-knowledge reference, not an attack. It uses a pool of 1765 labelled public images per seed, against the 32 records that the 4 clients hold. The inversion attack itself uses no public images, so the two are not given the same information. See the pool-size table below.
- Mean-image floor of v0.14.2: MSE 0.073, 2 of 80 recognisable. It ignores labels and is too weak here. Random public digits give 0.093.
- Identification rate: how often the true record is nearest to the class-average image among 10 same-label public candidates is 0.105 against a chance level of 0.100. This is a different question from MSE and the two are not comparable.

Label floor against the size of the labelled public pool (`pool_size_sensitivity` in `label_floor.json`). For each seed and size, 20 random subsets of the public pool are drawn with a fixed generator and the results are averaged over subsets and the 10 seeds. A class that is missing from a small subset is rebuilt as the subset mean image. At 20 images, 77% of the subsets miss at least one class.

| Labelled public images behind the floor | Floor MSE | Floor recognisable |
|---|---|---|
| 20 | 0.071 | 31% |
| 50 | 0.057 | 48% |
| 100 | 0.050 | 57% |
| 300 | 0.047 | 64% |
| 1765 (full pool) | 0.046 | 67.5% |
| SecAgg+ aggregate attack, max_weight 1000 (no public images) | 0.057 | 55% |

The aggregate attack row is below the floor only for a pool of roughly 100 or more labelled public images. With 50 or fewer, the floor has the lower recognisable share, and its error is about the same (50 images) or worse (20 images). The size of the pool is a choice of the reference, so the claim in the next section is about this attack and not about every attacker.

What each observer sees:
- plaintext: the victim's individual update.
- SecAgg+: only the aggregate, produced with the upstream Flower quantiser arithmetic (clipping range 8, quantisation range 2^22, weight ratio, stochastic rounding). Two `max_weight` settings: the default 1000 and a tuned 16.
- SecAgg+ with n minus 1 colluders: the server and 3 clients subtract their own updates from the aggregate.
- DP: Opacus DP-SGD (per-sample clip 1.0, Gaussian noise) on every client, seen individually, through SecAgg+, and through SecAgg+ with collusion.

What this shows:
- Plaintext and n minus 1 collusion stay clearly above the label floor. With one update, or an update recovered by colluders, the attack beats what the labels alone give by about 24 to 26 points, and the error returns to the plaintext level (0.015 to 0.023). The quantiser setting changes this little.
- SecAgg+ aggregate only, max_weight 1000, does not beat the label-only floor in this experiment. The recognisable share (55%) is below the floor (67.5%) and the error (0.057) is above it (0.046). With max_weight 16 the share is 58.8%. Its paired difference to the floor is -8.8 points with an interval of -23.8 to +5.0, so it cannot be told apart from the floor. This attack uses no public images, so an attacker that starts from public images (a prior-initialised attacker) could beat the floor, and the floor itself depends on how many labelled public images it uses (table above). This replaces the v0.14.2 reading that 55 to 59% of victim images were still recognisable and that the aggregate leaked. It is a statement about this attack in this setting (one step, 4 clients, 8 records each, known labels). It does not show that the aggregate is safe against other attacks, more steps or other model sizes.
- The DP rows show that a naive attacker fails. The attacker matches gradients without modelling clipping or noise, and at sigma 0.2 and above its reconstruction is worse than the mean image (0.179 against 0.073). That is evidence about this attacker only. It makes no claim about how well DP protects against an attacker that knows the mechanism. The v0.14.2 sentence that DP "stopped" the attack is withdrawn.
- Single-step epsilon is shown only to give scale (RDP accountant, no subsampling, delta 1e-5). Even a meaningless epsilon of 295 (sigma 0.05) cut recognisability from 94% to 16%, because clipping and noise both hurt a naive matching attack. That is not a privacy statement.
- DP here is a single step on 8 records. The utility price over a full training run is in sections 4 to 6 and is large.

Checks C1 to C5 of `docs/preregistration/v0.15.md` for these corrections are in `reports/results/privacy/v0143/prereg_check_corrections.json`. C1, C2 and C4 are consistency checks on data that had already been seen (post-probe), not confirmations. C3 and C5 are the checks that were not tied to the probe. C5 does not count skipped tests as passed: it needs zero failures, zero skips, and the label-floor tests must have run.

Scope limits: an observation-model study with real quantiser arithmetic, not an attack on captured Docker traffic. Single local step, known labels, known learning rate and initial model. The attacker matches naively and does not model clipping or noise. A failed reconstruction is evidence about this attack only. The floor uses the labelled public pool of the same seed (1765 images). It is a prior-knowledge reference that needs the victim labels and a labelled pool of public images. The attack here gets the labels but no public images.


Note added in v0.15: the one-round bound above (n x step x max_weight / total_samples) is a heuristic form. The proven worst-case per-coordinate bound is 2cn/T, where T is the sum of the integer quantised weights, and it also covers the float32 client path. See `docs/proofs/one-round-secagg-error.md`. The old acceptance rule at the empirical 99th percentile of 300 runs has only 35 to 58 percent confidence of covering the true 99th percentile.

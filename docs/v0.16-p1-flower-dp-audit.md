# v0.16 P1: measured privacy of Flower's differential privacy mechanisms

Status: released in 0.16.0. Not peer reviewed.
Pre-registration: `docs/preregistration/v0.16-p1.md` (committed before any run).
Evidence: `reports/results/privacy/v0160/flower_dp_audit/flwr-1.27.0/` and `flwr-1.44.0/`.
Harness: `scripts/audit_flower_dp.py`. Tests: `tests/privacy/test_audit_flower_dp.py`.

## Summary

The harness runs the real Flower classes in process and compares the Gaussian mechanism that executes with the one implied by the configured parameters. It was run on `flwr` 1.27.0 (pinned by this repository) and 1.44.0. The measured numbers are identical on both versions for every row that exists in both, except R1. The central rows share one seeded noise sample, so their sigma is one measurement and not six.

1. With equal client weights and all sampled clients responding, the central DP strategies deliver the configured noise multiplier within 0.04% (row C1).
2. In two fixed clipping configurations the executed mechanism is weaker than the configured parameters imply: unequal client weights (C3), and `num_sampled_clients` set higher than the number of results that are aggregated (C4). With adaptive clipping and all clients clipped, the update noise is 0.903 of the reference algorithm's at the default learning rate and 0.607 at learning rate 1.0 (A1, A2).
3. `LocalDpMod` meets its configured (epsilon, delta) for epsilon up to 5 on the tested grid and does not meet it for 10 and 20 (L1). If `sensitivity` is set equal to `clipping_norm` it does not meet it for any tested epsilon (L2).
4. `flwr` 1.44.0 has an optional accountant on the Message API fixed clipping strategies. With the accountant enabled, the C3 input raises an error and the C4 input releases nothing. Without it, and in the `flwr.server.strategy` API, the C3 and C4 numbers are unchanged. Which release introduced the accountant was not checked.

Flower's how-to guide on differential privacy labels the feature as a preview. Flower logs a warning in the C4 configuration, and its documentation does not state an adjacency relation. These are measurements under stated configurations and not statements about intended use.

## Setup

16 float32 parameters, clipping norm C = 1, noise multiplier z = 1, `num_sampled_clients` n = 10, delta = 1e-5. Sensitivity is measured with the noise multiplier set to 0. Sigma is measured over 20,000 runs. The Gaussian parameter is mu = sensitivity / sigma, and exact epsilon follows from the Balle and Wang (2018) formula. The empirical column is a 95% Clopper-Pearson lower bound on epsilon from 200,000 trials per world, which makes no Gaussian assumption and cannot certify more than about 10.9 at this trial count.

Adjacency is zero-out: the target client's update is replaced by a null update with the number of results unchanged.

## Central DP with fixed clipping

Claimed reading: mu = 1/z = 1, which is epsilon 4.38 at delta 1e-5 for one round.

| Row | Configuration | Sensitivity | Sigma | Effective z | Exact eps | Empirical eps lower bound |
|---|---|---|---|---|---|---|
| C1 | 10 results, equal weights | 0.100 | 0.09996 | 1.000 | 4.38 | not run |
| C3 | target reports 91 examples, nine others report 1 | 0.910 | 0.09996 | 0.110 | 79.4 | 10.90 |
| C4 | `num_sampled_clients` 10, 2 results aggregated, no failure reported | 0.500 | 0.09996 | 0.200 | 33.1 | 10.49 |

The same numbers were measured for `flwr.server.strategy` and `flwr.serverapp.strategy`, on both versions. The noise is consistent with a Gaussian in a Kolmogorov-Smirnov check (p = 0.72, a weak check because mean and scale are estimated from the same sample).

Why. Noise is scaled as zC/n. The wrapped FedAvg averages with weights taken from the `num_examples` each client reports, so a client with weight share s moves the aggregate by sC. With m responses and equal weights each client moves it by C/m. The effective multiplier is z/(ns) in C3 and zm/n in C4.

Reaching C4. A client failure does not lead here. In `flwr.server.strategy` a non-empty failure list makes the wrapper return no aggregate, and in the Message API a reply that carries an error does the same. C4 is reached when `num_sampled_clients` differs from the number of results the wrapped strategy aggregates, for example when it does not match the sampling settings of the wrapped strategy. Whether replies that are absent at a timeout also lead here in the Message API was not verified.

Reading C3 correctly. The client with the large share is the one whose protection drops. A client cannot lower another client's protection by reporting a large count, because that shrinks every other share.

Adjacency (pre-registered row C2). Under replace-one adjacency the sensitivity in C1 is 0.200 and exact epsilon is 10.0 instead of 4.38. A user who assumes replace-one should halve the effective multiplier.

Accounted mode, 1.44.0 only (not pre-registered).

| Row | Input | Outcome |
|---|---|---|
| C1-msg-acc | as C1 | aggregate released, accountant reports eps 4.73 (RDP), exact one-round value 4.38 |
| C3-msg-acc | as C3 | `ValueError: Accounted aggregation requires equal client weights.` |
| C4-msg-acc | as C4 | no aggregate released, nothing composed (the reply count check is strict in accounted mode) |

Other rows.

| Row | Result |
|---|---|
| C0 (not pre-registered) | a client that returns the global model unchanged raises `ZeroDivisionError` in the clipping helper |
| C5 | client-side clipping variant with one client that does not clip: sensitivity 0.5 for an update of norm 5C. The server relies on clients to clip in this variant. |
| C6 | integer arrays: no privacy mismatch measured. See the deviation log for why the prediction named the wrong mechanism. A clipped update on a model with an integer array raises a numpy casting error. |

## Central DP with adaptive clipping

`DifferentialPrivacyServerSideAdaptiveClipping`, configured noise multiplier 0.5, all 10 updates clipped at C_t = 1. The reference algorithm (Andrew et al. 2021) scales the noise with the norm used for clipping. In the measured implementation the norm is updated between clipping and noising, so the noise is scaled with the next round's norm.

| Row | `clip_norm_lr` | Predicted sigma ratio | Measured sigma ratio | mu measured | mu reference |
|---|---|---|---|---|---|
| A1 | 0.2 (default) | 0.905 | 0.903 | 1.92 | 1.73 |
| A2 | 1.0 | 0.607 | 0.607 | 2.85 | 1.73 |

When the norm grows in a round the same ordering adds more noise than the reference, so the noise is lower only in rounds where the norm shrinks. The same ordering is present in the Message API server-side adaptive strategy by code reading, which was not run. The client-side adaptive variant adds noise before it updates the norm.

What these rows do not show. The comparison is with the reference algorithm's update noise only. The release of the noised clipped count and the total budget implied by the configured multiplier were not measured. The mu values treat the noise as one Gaussian with the root mean square scale, although the scale depends on the noised count. That approximation is cruder at learning rate 1.0. The direction in which the norm moves when clients are clipped follows the implementation's own convention for the clipped bit, which was not compared with the paper.

## Local DP

`LocalDpMod(clipping_norm, sensitivity, epsilon, delta)` adds Gaussian noise with sigma = sensitivity * sqrt(2 ln(1.25/delta)) / epsilon. Measured sigma matches this formula within 0.2% in every row. Measured replace-one sensitivity of the clipped update is 2C.

L1, `sensitivity` = 2C (the true value).

| Configured eps | Exact delta / configured delta | Exact eps at configured delta | Meets (eps, delta) |
|---|---|---|---|
| 0.5 | 0.0016 | 0.35 | yes |
| 1 | 0.0041 | 0.75 | yes |
| 2 | 0.013 | 1.61 | yes |
| 5 | 0.13 | 4.54 | yes |
| 10 | 2.3 | 10.39 | no |
| 20 | 153 | 25.44 | no |

The classical calibration is proved only for epsilon below 1. On this grid it is conservative up to 5 and falls short above that.

L2, `sensitivity` = C. The parameter is independent of `clipping_norm`, and nothing ties the two together. This is a user configuration. No Flower text was found that recommends it.

| Configured eps | Exact eps at configured delta |
|---|---|
| 0.5 | 0.75 |
| 1 | 1.61 |
| 2 | 3.51 |
| 5 | 10.39 |
| 10 | 25.44 |
| 20 | 68.49 |

These rows rest on measured sigma and sensitivity plus the exact formula. The Clopper-Pearson test has no power at these levels, as stated in the pre-registration.

## Predictions

Every pre-registered prediction held except C6, where the outcome (no noise on the integer array) was as predicted and the stated mechanism was wrong. R1 held on 1.27.0 and not on 1.44.0.

## Limits

1. One framework, two versions, one small parameter vector, one round. No sampling amplification and no composition were measured.
2. The harness calls strategy and mod classes directly. It does not run a deployment, so it says nothing about which configurations occur in practice.
3. C3 and C4 are consequences that follow from reading the code. The contribution here is the measurement and the exact epsilon, not the discovery that weights matter.
4. Prior art was searched in the literature before the phase started. Flower's own release history was not checked at that point, and the accountant in newer releases was found only during the re-check.
5. No other framework has been measured yet, so nothing here is a comparison.
6. Zero-out with a fixed result count is the only adjacency measured for central DP, apart from the replace-one column. Add-or-remove adjacency with FedAvg's data-dependent denominator was not measured.
7. The adaptive rows were run on `flwr.server.strategy` only.
8. The harness was first committed after the pre-registration commit. Parts of it were drafted while the pre-registration was being written. The pre-registration text above its deviation log is unchanged since that commit (checked by diff). Predictions were written from code reading. The repository history cannot prove that no mechanism ran before the pre-registration commit.

python scripts/audit_flower_dp.py --out out/           # about 35 minutes
python scripts/audit_flower_dp.py --out out/ --quick   # about 30 seconds

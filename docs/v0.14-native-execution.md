### Defects found by the first real run (all fixed, none by weakening a gate)

1. Egress through a TLS-inspecting proxy broke `pip` inside `docker build`. Added an optional
   BuildKit secret (`FDL_BUILD_CA_BUNDLE`) that is never stored in an image layer.
2. Image `/app` and Flower home were root-owned for the unprivileged `app` user, breaking the
   editable install. Ownership fixed in the Dockerfile.
3. Flower 1.27 requires quoted string values in `--run-config`. The runner now formats them.
4. Receipt/artifact mounts created by the host were not writable by container uid 49999, so
   every ClientApp failed (`PermissionError`). Preparation now chowns (or opens) only those
   output folders, never the data mounts.
5. Docker Hub returned HTTP 429 once on the shared egress IP. A retry fixed it (infrastructure only).

Failed attempts `run-iid-a/b/c` are preserved and shown as FAIL by
`scripts/summarize_native_scenarios.py`.

### Honest limitations

- Smoke scale: 2 rounds, 600 samples, 120 training records. 15-22% accuracy is expected here
  and is not a utility claim. Longer training is Phase 3.
- Fault handling: a stopped executor makes the server wait until the runner timeout, rather
  than failing fast. Minimum-3 is enforced (no partial aggregate was ever produced), but
  graceful round-level failure and retry are not implemented.
- Receipts attest process activity, not remote attestation. A host-root or Docker-daemon
  adversary is out of scope. The transport is insecure and single-host.
- Hosted GitHub Actions did not run (no authorized remote). This is a sandbox execution.

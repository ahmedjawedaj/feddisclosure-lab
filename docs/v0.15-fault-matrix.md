# v0.15 WP8: fault matrix, does the evidence chain have teeth?

The question. The repository has gates, verifiers and audits that say a privacy pipeline is sound. Would any of them notice if it were not? Five kinds of known fault are injected one at a time and every detector is asked. The pre-registered predictions F1 and F2 are in `docs/preregistration/v0.15.md`. Results are in `reports/results/privacy/v0150/prereg_check_faults.json` and `reports/results/privacy/v0150/fault_matrix/`.

Result in one line. F1 PASS (4 of 5 faults detected by the specified detectors, the plaintext fallback evades them and is caught only by an extension that needs the honest client vectors) and F2 PASS (power 1.000 at noise factors 0.25, 0.5 and 2, false positive rate 0.010).

## The five faults and why these five

No Docker daemon is available here. Each fault is either injected into a real component or written into a copy of saved real evidence.

| Fault | How it is injected | Real components |
|---|---|---|
| F1 DP noise scale wrong | noise multiplier 0.25, 0.5 or 2 times the claimed sigma 1.0 | Opacus 1.6.0 `PrivacyEngine` step |
| F2 Per-sample clipping skipped | max grad norm 1e6, and the noise multiplier divided by 1e6 so the noise std stays at the claimed sigma times C. Only clipping is missing | Opacus 1.6.0 `PrivacyEngine` step |
| F3 Plaintext fallback | the SecAgg+ aggregate replaced by the plain weighted mean. Variant a keeps logs and markers. Variant b removes the "Secure aggregation" log lines and the workflow marker file, as a run that never entered the workflow would | upstream quantiser through `view_study.secagg_aggregate` for the honest side, saved native evidence copies for the verifiers |
| F4 Wrong threshold or dropout handling | (a) a loss of 2 of 4 clients is tolerated at threshold 3, (b) a loss that leaves exactly threshold-many survivors halts the run, (c) the aggregate silently includes the dropped client's round 1 update | saved dropout matrix evidence copies, upstream quantiser |
| F5 A client trains from a stale global model | in round 2 client 1 trains from the round 1 global model | real PyTorch client training on the saved partitions, upstream quantiser |

Why a stale model for F5 and not a duplicated update. Stale models arise from ordinary failures (a retry, a cache, a late node) and need no deliberate bug, so they are the more likely fault. A duplicated update shows up in the same detectors with the same size of error, so a second variant would add rows and no information.

Why these five. They are the faults that can be injected without touching mask generation, which is outside this work package (mask reuse is therefore not one of the seeded faults). They cover the three places where trust is placed: the DP step (F1, F2), the secure aggregation arithmetic and mode (F3, F5) and the protocol rule for dropouts (F4).

## Detectors

| Id | What it is | Needs |
|---|---|---|
| A | Existing verifiers run as programs on tampered copies: `verify_secagg_dropout_matrix.py`, `verify_secagg_native.py`, `verify_flower_parity.py` (certify, 1e-5 float64 parity), plus `verify_flower_topology.py` static certification of the real compose files. A fault is flagged when a pass or fail field that passes on the honest copy fails on the tampered copy | the saved evidence format |
| B | White-box many-run DP audit. Ten real Opacus runs of 2,410 coordinates per audit. Standardised residual is the output minus the known clipped sum, divided by the claimed sigma times C. A two-sided chi-square test at level 0.01 on the variance, and the estimated noise std is reported. A clipping-norm audit runs the same engine configuration with noise switched off on three single records and requires every clipped norm to be at most C (relative slack 1e-4) | the clipped sum, ability to switch noise off |
| C | Black-box informed identification attack from `dp_informed.py` (any-label candidates, u 10, inner-product rule). An audit is 60 real Opacus steps. It flags when the one-sided 95 percent Clopper-Pearson lower limit of the success rate exceeds the ReRo bound for the claimed sigma (0.389). By construction it can only see less noise than claimed | the other 7 records and a candidate list |
| D1 | Quantisation error of the aggregate against the exact weighted mean must stay inside the proven bound 2cn/T plus the weight rounding term, from `docs/proofs/one-round-secagg-error.md` | the honest client vectors |
| D2 | Extension added before the run. The aggregate is tested against the exact distribution of the upstream stochastic rounding (exact mean, exact variance and exact fourth moment per coordinate). Z test on the sum of squared standardised errors, two-sided at level 0.01 over the two rounds. It exists because a plaintext aggregate has error zero, which is inside any error bound | the honest client vectors |

Design constants were fixed before any evaluation run: claimed sigma 1.0, C 1.0, 8 records per client, learning rate 0.1, level 0.01, 200 audits per condition, evaluation audit indices 0 to 199. The only tuning-index work (indices 9000 and up) was a calibration check of D2 on 100 honest simulations. It found a mistake in the simulator (the rounding draws were reused across rounds) and no constant was changed after that. The 1e-6 clip tolerance and the minimum rounding variance 0.05 for D2 were stated in the code before the runs.

Detection power is the share of audits (or of simulated experiments) that raise a flag, with a Clopper-Pearson 95 percent interval. A cell counts as detected when its rate is at least 0.9. Evidence gates are deterministic, so they have a yes or no.

How the wording was read. A fault type counts as detected only if every one of its variants is detected, by a detector whose control false positive rate is at most 0.05. The power rule is read on the point estimate and the interval is shown. The F1 verdict uses the strict count. The D2 extension is reported and not used for the verdict.

## Which faults evade, and what that means

Every fault was seen by something, but not everything was seen by the existing evidence chain.

- F3 plaintext fallback evades A and D1. The numerical verifiers compare the final model to an independent recomputation within a tolerance. A plaintext aggregate is closer to the recomputation than a real SecAgg+ aggregate is (3e-8 against 4e-5), so the check passes and in the two-round baseline it even turns from failed to passed. `verify_secagg_native.py` does record `secure_aggregation_enabled`, `workflow_engine` and the count of "Secure aggregation completed" lines, and for variant b the report shows `None` and 0, but no pass or fail rule reads those fields. A reviewer who reads the report would see it, the gate would not. Only D2 saw the fallback, because a plaintext aggregate has a quantisation error about 37 standard deviations too small (median Z of minus 37.4 against about 0 for honest runs). D2 needs the honest client vectors, which an auditor of a deployed system does not have. In a deployment the realistic cure is a gate that requires the workflow marker and the expected log lines. That check is not in the repository and was not added here.
- F2 skipped clipping evades the noise test (the noise is right), and the black-box attack (power 0.350). The attack is built on the assumption that the other records contribute clipped gradients, so unclipped contributions swamp its residual. Only the clip audit sees it.
- F1 noise x2 (more noise than claimed) evades the black-box attack by construction. It is a privacy-safe direction and utility-unsafe. Only the white-box noise test sees it.
- Naive tolerance false positives. The two-round tolerance of 2 times the one-round bound is exceeded by honest SecAgg+ runs. The saved baseline run exceeds it, and in 200 honest simulations 35 percent of runs do. The verifier already records this as a failed check and does not relax it. That makes the tolerance check weak for two-round evidence. Detection in the matrix used the scenarios that pass on honest evidence. For F5 the discrimination is large (the differences are 50 to 150 times the tolerance), so this does not affect the result here, but a smaller stale-model effect could hide inside the noise of the tolerance.

## What each detector can and cannot see

- A (existing verifiers). Sees wrong protocol outcomes against the stated rule, and final models that differ from an independent recomputation by more than the tolerance. Cannot see a fault that makes the result more exact (plaintext), a fault that leaves the numbers alone (anything in the topology), faults in realised DP noise or clipping (no existing gate looks at them, the native release gate only reads the accountant report), and any rule violation in a configuration the dropout matrix does not contain (it covers n 3 and 4 with thresholds 2 and 3).
- B (white-box DP audit). Sees realised noise scale to about 3 percent (24,100 values per audit) and any clipping that exceeds C on the probe records. Cannot see faults that act only when noise is on (the clip probe runs with noise off), faults that depend on the data in ways the probe records do not exercise, and anything about composition, accounting or sampling. It needs white-box access.
- C (informed attack). Sees much less noise than claimed, with power 0.95 at factor 0.5. Cannot see extra noise, cannot see skipped clipping, and a null result is weak evidence. Each audit needs 60 real runs.
- D1 (error bound). Sees any wrong contribution larger than the quantisation step amplification (errors 700 to 3,300 times the bound here). Cannot see faults with a small error or with no error.
- D2 (error distribution). Sees both too much and too little error. Calibration is good for full participation and slightly loose for three clients (false positive rate 0.025 at nominal 0.01), because the normal approximation is coarser with fewer terms.

## Honest limits

- Simulation, not the deployed stack. Docker is not available. F1 and F2 use the real Opacus engine, so they are faithful. F3, F4 and F5 are produced by a simulator that uses the real upstream quantiser and real PyTorch training on the saved partitions, and are written into copies of saved evidence from real Docker runs. The verifiers then run for real on those copies. No faulty stack was deployed. F4a and F4b move logs from other real runs and test whether the verifier reads the evidence correctly. They do not test whether a deployed SecAgg+ would behave that way. The tampered copies are consistent in the fields the verifiers read, and a different forgery could differ in fields they do not read.
- Evidence gates are deterministic and run on one tampered copy per variant, so there is no repetition and no interval for column A. The honest copy shows what a clean run looks like and nothing more.
- The faults are large. The sensitivity table covers only the noise factor. Small stale-model effects, small noise shifts in the secure aggregation arithmetic and partial fallbacks (a plaintext fallback for one round or one client) were not injected.
- D1 and D2 assume the auditor can recompute the honest client updates. The existing verifiers also recompute them, but only in a test bench and not in a deployment.
- The DP audit uses the claimed sigma and C, one setting (sigma 1, C 1, batch 8, one full-batch step at a random initialisation, 2,410 parameters). It says nothing about several steps, Poisson sampling or an accountant.
- The informed attack setting has one candidate mode (any-label, u 10). Other settings change its power.
- Mask reuse was not seeded. This table says nothing about it.
- The 200-audit rates are all 0 or 1 for the faults that are detected. The Clopper-Pearson lower limit is 0.982, so the data support power of at least 0.98, and no finer statement.

## Reproduce

    PYTHONPATH=src:. python scripts/run_fault_matrix.py dp --workers 2    # about 22 minutes on 2 CPUs, resumable, run in the background
    PYTHONPATH=src:. python scripts/run_fault_matrix.py sim               # about 4 minutes
    PYTHONPATH=src:. python scripts/run_fault_matrix.py gates             # about 90 seconds, tampered copies under /tmp/fault_matrix_evidence
    PYTHONPATH=src:. python scripts/run_fault_matrix.py summarize         # summary.json and prereg_check_faults.json
    PYTHONPATH=src:. python -m pytest tests/privacy/test_fault_matrix.py -q    # about 75 seconds

Files: `src/feddisclosure/evaluation/fault_matrix.py`, `scripts/run_fault_matrix.py`, `tests/privacy/test_fault_matrix.py`, `reports/results/privacy/v0150/fault_matrix/` (`dp/`, `secagg_sim/`, `gates/gate_results.json`, `summary.json`) and `reports/results/privacy/v0150/prereg_check_faults.json`. `gate_results.json` records the file hashes of every tampered file and the digests of the saved evidence directories before and after the run. They are equal, so no saved evidence was changed. Tampered copies are refused inside `reports/results` by `safe_tamper_root`, and a test checks that.

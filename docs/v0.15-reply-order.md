# v0.15 reply order, the float64 parity gate and an opt-in deterministic aggregation

Status: replay evidence, plus live runs on hosted Docker described near the end (results in the live section). The client change and the run-config key described below are on main. P1 is recorded as PASS in replay only. The live runs confirm transport and client determinism but exercise no config that fails upstream.

Pre-registered predictions are in `docs/preregistration/v0.15.md` (section "Parity and determinism", P1 to P3). Thresholds were not changed. Machine-readable result: `reports/results/privacy/v0150/prereg_check_parity.json`. Per-run detail: `reports/results/native_flower/v0150/reply_order/`.

## Background and credit

Flower 1.27 `flwr.serverapp.strategy.FedAvg` calls `aggregate_arrayrecords`, which sums float32 `array * (weight / total)` in place in the order the replies are handed over. That order follows reply arrival, and node ids are random per registration, so the order is not fixed between runs. Float addition is not associative, so the aggregate can change in the last bit and later rounds can amplify that.

This is not a new finding. Reply order dependence and the resulting non-determinism in Flower have been discussed publicly, for example in a thread on the Flower forum (https://discuss.flower.ai/t/non-determinism-only-when-number-of-clients-is-increased/807), and the BlazeFL project works on deterministic federated simulation (Azuma and Nishio, arXiv 2604.03606, https://github.com/kitsuyaazuma/blazefl). This repository only measures how that effect interacts with its own 1e-5 float64 parity gate and adds an opt-in strategy.

In v0.14.x the strict gate (`scripts/verify_flower_parity.py`, `atol = rtol = 1e-5` against the float64 PyTorch reference) passed 5 of 7 native runs. `scripts/reproduce_flower_bitwise.py` and `scripts/verify_flower_replay_gate.py` replay all 7 exactly in plain PyTorch using the reply order implied by the receipts.

## What was added

`DeterministicFedAvg` in `src/feddisclosure/training/deterministic_fedavg.py`, a subclass of the same `FedAvg` that `flower_server.py` uses.

1. It reads the site id each client reports, sorts the replies by site id (not node id), then averages with the formula of `task.fedavg_weighted`, the aggregation of the float64 reference: float64 accumulation of `array * (weight / total)` in site order and one cast back to float32.
2. It fails closed. A reply with no site id, a malformed one (not a non-negative integer) or two replies with the same site id raise `SiteIdError` before any arithmetic.
3. Train metrics are also aggregated in site order so the summary is reproducible. Evaluate metrics are untouched (they are reported numbers and never enter the model).
4. It is opt-in. Default behaviour is the unchanged upstream `FedAvg`, so all existing evidence reproduces. The summary file only gets an `aggregation` key when the opt-in is on.

Opt-in: run-config key `aggregation="deterministic"` or environment variable `FDL_AGGREGATION=deterministic` on the server process. Any other value is an error, so a typo cannot silently leave the upstream arithmetic in place.

### What this changes about the gate, stated plainly

With `DeterministicFedAvg` the server arithmetic is the reference arithmetic by construction. After this change the float64 parity gate tests transport and client determinism only. It no longer tests Flower's aggregation arithmetic. A pass with the strategy on must not be described as evidence that upstream `FedAvg` aggregates correctly or reproducibly. Runs with the upstream strategy remain the way to observe that, and their saved gate results (5 of 7) stay in the evidence.

### What it does not touch

The SecAgg+ path does not use the strategy aggregation, so `DeterministicFedAvg` does not apply to it and nothing in this note changes any SecAgg+ result. Sorting by site id is a determinism measure only and is not a privacy measure.

### Client change (applied on main)

A reply does not carry a site id by default. The ClientApp only writes the id to its local attestation events, and node ids are no use because the server cannot map them to sites. The strategy therefore reads a small `ConfigRecord` named `site` with key `site-id`. It is not a MetricRecord, so it is not averaged into any metric and passes the upstream reply check. The patch is in the train handler of `src/feddisclosure/training/flower_client.py` and the `aggregation = "upstream"` key is in `[tool.flwr.app.config]` of `pyproject.toml`, both on main:

```python
from feddisclosure.training.deterministic_fedavg import site_record
...
    reply = RecordDict({"arrays": ArrayRecord(model.state_dict()), "metrics": MetricRecord(metrics)})
    if str(context.run_config.get("aggregation", "upstream")) == "deterministic":
        reply["site"] = site_record(site_id)
```

`site_id` is the variable already computed in that handler (`FDL_SITE_ID`, equal to the receipt site id). With a client that lacks the patch and the strategy on, the server raises `SiteIdError` in round 1. It does not guess.

## Replay study

`scripts/study_reply_order.py` replays each setup in plain PyTorch and retrains every client from the aggregated model in every round. For every reply order (3 clients gives 6, 4 clients gives 24) it aggregates with the upstream float32 arithmetic and with `DeterministicFedAvg`, and compares with the float64 reference trajectory using the unchanged gate (`torch.allclose` with `atol = rtol = 1e-5` on every tensor). Two views:

* one round: each round is aggregated once from the reference trajectory's client updates, so only that round's arithmetic differs
* trajectory: the same permutation is used in every round and clients retrain from the result. This is a restricted family of schedules (n! of the n!^rounds possible ones)

For the 7 native runs the replay is first checked against the saved evidence: replaying the per-round orders from `bitwise_replay.json` reproduces the saved native final model bit for bit in 7 of 7 runs, the float64 replay equals the saved reference checkpoint bit for bit in 7 of 7, and the replayed gap equals the saved native gate gap (for example 0.012978928 for `run-mnist-full-iid-seed3`).

The replay study had no saved native 4-client run to start from. Live run 45076810526 (see the live section) has since produced native 4-client runs for Digits iid, 10 rounds, in both modes. Each has a single reply order, so it checks one point of the 24 replayed orders and cannot show order dependence. All other 4-client rows are replay only, on prepared 4-client data. `c4-digits-iid-2round` is the shipped 4-client config and was fixed as the one P2 is judged on before any result was seen. The other two 4-client rows are exploratory. `data/training/mnist-full-iid-4c-v015` was prepared with `prepare_partitions(..., dataset="mnist", clients=4, partition="iid", seed=20261118)` and is not tracked in git.

### Predictions

* P1 (7 of 7 native runs pass the unchanged gate with `DeterministicFedAvg`): PASS in replay only, 7 of 7, worst difference 0. The rule says native runs, and the 7 native runs were not re-run with the strategy on. The reading used is that the 7 native runs are judged in replay, plus 3 live Digits configs. The live runs confirm transport and client determinism but exercise no config that fails upstream, because the MNIST configs that failed upstream were not run live. The strategy is the reference arithmetic by construction, so this is a weak test.
* P2 (upstream pass rate over reply orders strictly below 100% for 4 clients): FAIL on the pre-declared primary configuration. The shipped 4-client digits config passes the gate for all 24 orders (100%, worst 3.0e-08). The exploratory 4-client MNIST 10-round setup is at 83.3% and would satisfy the rule, and the 4-client digits 10-round setup is at 100%. Read together, order dependence at 4 clients is shown for one of the three setups, and it is not shown for the shipped config. Strictly as written and as scoped before the results, P2 is FAIL. Two of the seven 3-client native runs fail the gate, and the replay with the observed orders reproduces them exactly. They fail for all 6 orders, so their verdict does not depend on the order, and P2 is about 4 clients.

## P3: does reply order move a privacy metric?

Metric: victim mean per-image MSE of the repository's gradient-matching inversion (`view_study.attack`, which calls `gradient_inversion.reconstruct`, 350 iterations, known labels) on the victim's one-step full-batch plaintext model delta (8 records, learning rate 0.15), scored by the evaluator with optimal matching (`view_study.score_victim`). Why this metric: it is the repository's own headline privacy measure, it is a continuous number so small shifts show up, and the attack is deterministic given its inputs, so any difference comes from the starting model.

Design: 4-client IID digits. The starting model is the global model after round 1 aggregated in each of the 24 reply orders with upstream arithmetic (12 are bitwise distinct). The victim is site 0. A seed (8 seeds) picks the 8 victim records and the attack initialisation. The seed standard deviation is the sample SD of the per-seed MSE, averaged over orders. The reply-order effect is the largest minus the smallest seed-mean MSE across orders. P3 passes if the effect is below the seed SD, as written. Verdict: PASS, but the metric is insensitive on this setup and cannot fail (see the sensitivity control).

| Setting | Order effect | Seed SD | Ratio | Result |
|---|---|---|---|---|
| Start model after round 1 (main) | 3.2e-09 | 0.0160 | 2e-07 | PASS |
| Start model after 10 rounds, same permutation each round (stress) | 7.4e-04 | 0.0241 | 0.031 | PASS |

The mean-image no-information floor is 0.074 and the attack MSE is about 0.17, so the attack on this setup is poor in absolute terms. The weights differ by at most 9e-08 between orders even after 10 rounds in this setup.

Sensitivity control, to show the metric can move: Gaussian perturbations of the round-1 model, 8 perturbed starts per scale, same seeds.

| Perturbation scale | Order-effect analogue | Seed SD |
|---|---|---|
| 1e-08 | 7.2e-09 | 0.0160 |
| 1e-07 | 6.0e-04 | 0.0161 |
| 1e-06 | 2.5e-03 | 0.0163 |
| 1e-04 | 3.3e-03 | 0.0171 |
| 1e-02 | 8.8e-03 | 0.0169 |

The metric responds from about 1e-07 upward but does not exceed the seed SD even at 1e-02. Reply order changes the model at about 1e-08, below where the metric responds.

Limitations: one attack and one metric, one 4-client IID digits setup, one local step, plaintext updates only (nothing about SecAgg+ or DP), seeds vary the victim batch and the attack initialisation but not the data partition or the model init, and the reply orders are fixed permutations repeated every round. The comparison uses the single-seed SD as the pre-registration states. The effect is also far below the standard error of an 8-seed mean (about 0.006). Because the control never crosses the seed SD, a PASS here shows that reply order is negligible next to seed noise. It does not show that the metric could detect a large model change.

## What was shown and what was not

Shown, in replay: the saved failing gate results are reproduced exactly by float32 replay with the observed reply orders, and they fail for every one of the 6 orders, so the cause is float32 server arithmetic against the float64 reference accumulated over rounds and not one unlucky order, `DeterministicFedAvg` arithmetic equals the float64 reference bit for bit and is order invariant, and reply order does not move the chosen privacy metric beyond seed noise.

Live runs added later: six hosted Docker runs with and without the strategy, including a native 4-client run in each mode (one reply order each). They show transport and client determinism and that the strategy is bitwise equal to the reference in those configs.

Not shown: any live run of a config that fails upstream, order dependence at 4 clients for the shipped config or in any live run, any effect on SecAgg+, and any claim about Flower beyond the single reply-order mechanism. Passing the gate with the strategy on says nothing about upstream aggregation.

## Reproduce

What a fresh checkout can and cannot do. The `replay` and `p3` commands need inputs that Git does not hold: the prepared partitions under `data/training/` and, for the 7 native runs, the Docker-produced `server/final_model.pt` and the reference checkpoints under `checkpoints/` (all `*.pt` files are git ignored). Without them the script stops with a `checkpoints not in checkout` message that lists the missing files. Produce them with the Docker runs in `docs/v0.14-reproduce.md` or copy them from a full evidence bundle. `summarize` needs only the saved `replay_*.json`, `p3_victim_mse.json` and the live parity files, which are committed, so it works in a fresh checkout and rewrites `prereg_check_parity.json` byte for byte. The wording in that file (labels, scope and sensitivity notes, the live run block) is kept in constants at the top of `scripts/study_reply_order.py`, and a test regenerates the file from the saved inputs and compares it with the committed one.

```bash
export PYTHONPATH=src:.
for r in run-iid-d run-iid-repeat run-noniid-labelskew run-mnist-full-iid run-mnist-full-iid-seed2 \
         run-mnist-full-iid-seed3 run-mnist-full-labelskew c4-digits-iid-2round c4-digits-iid-10round c4-mnist-iid-10round
do python scripts/study_reply_order.py replay --run $r; done      # about 6 minutes in total on 2 CPUs
python scripts/study_reply_order.py p3 --seeds 8 --stress-rounds 10  # about 3 minutes
python scripts/study_reply_order.py summarize                       # writes prereg_check_parity.json
python -m pytest -q tests/training/test_deterministic_fedavg.py tests/training/test_reply_order_study.py
```

## Live confirmation on hosted Docker

The workflow `.github/workflows/parity-live.yml` ran six native Docker runs (run 45076810526): three configs, each with upstream aggregation and with `aggregation = "deterministic"`. The configs are Digits iid with 3 clients and Digits non-iid with 3 clients, both for 2 rounds, and Digits iid with 4 clients for 10 rounds. The 10 rounds apply only to the 4-client config. Evidence is in `reports/results/native_flower/v0150/live_parity/`.

| Config | Upstream worst difference | Deterministic worst difference |
|---|---|---|
| iid, 3 clients, 2 rounds | 3.0e-8 | 0.0 |
| non-iid, 3 clients, 2 rounds | 3.0e-8 | 0.0 |
| iid, 4 clients, 10 rounds | 8.9e-8 | 0.0 |

All six pass the unchanged 1e-5 gate. With the strategy on, the Flower checkpoint is bit for bit equal to the reference in all three configs, which also shows client training in the containers is reproducible. Upstream also passes, so these shipped Digits configs do not trigger the reply order effect and this live run neither confirms nor refutes P2. Each live run has one observed reply order, so even the 4-client runs are one sample of the 24 orders. The MNIST configs that failed upstream in earlier native runs were not run live.

A first attempt (run 45074469691) passed both 3 client configs and stopped the 4 client config at the evidence check in both modes, because the check hardcoded 8 containers and a 4 site deployment has 10. The check now scales with the number of sites (PR 7). No numeric comparison was affected.

## Live confirmation commands (reference)

Prerequisites, both already on main: the `aggregation = "upstream"` key in `[tool.flwr.app.config]` of `pyproject.toml` (Flower rejects a `--run-config` key that is absent from that table, and the default keeps current behaviour) and the client patch shown above.

Command for each run (2 or 3 runs, the most informative are the two that fail upstream: `fedavg_mnist_full_native_seed3.yaml` and `fedavg_mnist_full_labelskew_native.yaml`):

```bash
python scripts/run_flower_docker.py --config configs/training/fedavg_mnist_full_native_seed3.yaml \
  --data-dir data/training/mnist-full-docker-iid-seed3-v014 --run-dir reports/results/native_flower/v0150/run-mnist-full-iid-seed3-det \
  --env-file /tmp/run-seed3-det.env --timeout 1500 --extra-run-config 'aggregation="deterministic"'
R=reports/results/native_flower/v0150/run-mnist-full-iid-seed3-det; D=data/training/mnist-full-docker-iid-seed3-v014
python scripts/run_torch_reference.py --config configs/training/fedavg_mnist_full_native_seed3.yaml --data-dir $D --output $R/torch_reference.json
python scripts/verify_flower_parity.py --flower-dir $R/server --reference-json $R/torch_reference.json \
  --reference-checkpoint $R/checkpoints/mnist-full-iid-native-v014-seed20261120_final.pt --manifest $D/manifest.json \
  --output $R/flower_parity.json --require-deployment
```

The reference checkpoint file name follows the `id` field of the chosen config. Check `$R/checkpoints/`. Expected: `verified_numerical_parity: true`, every layer `max_abs_diff` 0.0 (bitwise equal), and `server/flower_summary.json` containing the `aggregation` key. If the parity result is not exactly 0.0, client training in the container is not bit reproducible, which is a finding about client determinism. Keep the failure. The 4-client form of the command uses `compose.flower.n4.yaml` through the same script and `configs/training/fedavg_digits_iid_4clients.yaml`. A live upstream 4-client run without the flag exists for Digits iid (run 45076810526, one reply order, passes). A live upstream 4-client MNIST run, which is the config that shows order dependence in replay, has not been done.

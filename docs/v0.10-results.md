# FedDisclosure Lab v0.10.0 — disclosure-control and output-leakage research

Date: November 20, 2026. Both studies use synthetic or approved public data only.

## Track A: experiment-ID reset and persistent release policy

**Threat model:** An authenticated analytics user can send typed, allowlisted count queries and choose `experiment_id`. They only see the gateway's federated aggregate or a generic rejection, not per-institution memberships. The database and synthetic labels belong to each institution; the evaluator knows only the synthetic ground truth. This is an educational research setting with one shared research principal, not a multi-user production identity system.

**Defect reproduced:** The previous history rule stored the query membership history under attacker-controlled `experiment_id`. The user could request `all_records` with ID A and `negative_records` with ID B, obtaining 110 and 107. The resulting complement discloses the restricted aggregate count of 3, even though both individually accepted counts exceed the threshold of 5.

**Mitigation:** `principal_history` compares against all prior releases for the same site-wide authenticated principal, independent of `experiment_id`. The mode is locked at the site and gateway; callers cannot switch to `naive`, and the site's persistent SQLite lock refuses subsequent unprotected restarts or upgrades after pre-existing query releases. A repeated identical query is still permitted in this experiment.

**Actual three-site HTTP run:**

| Policy | HTTP result sequence | Restricted count inferred? |
|---|---|---|
| `history` with different experiment IDs | 200, 200, 200, 200 | Yes, count 3 |
| `principal_history`, policy pinned | 200, 409, 200, 403 | No, for this two-query attack |

HTTP gateway never returns raw site IDs, row IDs or per-site counts. `scripts/run_history_scope_benchmark.py` stores exact status codes and returned federated counts in `reports/results/sprint1/history_scope_http.json`.

**Broader matched policy-engine matrix:** 15 deterministic population seeds, minimum-cell thresholds 2/5/10, and two prevalence bands, giving **90 matched synthetic populations** evaluated with four release conditions and three sequential typed queries each, for **1,080 actual SQLite policy evaluations**. Results:

| Condition | Exact complement-count inference | Released second query | Harmless repeat permitted |
|---|---:|---:|---:|
| No history | 90/90 (100%) | 90/90 | 90/90 |
| History, same experiment ID | 14/90 (15.6%) | 14/90 | 90/90 |
| History, ID reset | 90/90 (100%) | 90/90 | 90/90 |
| Principal-wide history, ID reset | 14/90 (15.6%) | 14/90 | 90/90 |

The residual 14 are cases in which the near-duplicate rule does not reject the complement (often because all local sensitive differences are zero or above the minimum threshold); **15.6% is not a privacy risk probability for real populations.** All counts are generated synthetically. Query denial is not a calibrated false-positive measure of legitimate analytical workload. The matrix tests one known two-query technique and does not establish defense against general adaptive inference or external side information. **None of these controls provides differential privacy.** The matrix was verified against the documented rule and SHA-256 using `scripts/verify_history_matrix.py`.

## Track B: five-seed output-only membership study

Prior v0.7 training artifacts contain five independently trained FedAvg models for IID and five for strongly non-IID, each with three institution clients, identical client training sizes/optimizer budgets and four training rounds. These are **PyTorch independent-worker** checkpoints, not native Flower.

**Critical design correction:** The two partition conditions do *not* have exactly the same train/validation membership sets. For each seed the evaluator now selects a shared pool of training examples present in **both** models' training sets (455–466 shared records) and the same held-out records, then queries the **identical 120 example records** and ordering for both models. The attacker sees only softmax probability vectors; the evaluator retains membership ground truth and model weights. Although the query cohort is exactly matched, the underlying training-member sets still differ. The comparison is **descriptive, not causal**.

| Uncalibrated output-only attack | IID mean ROC-AUC (5 models) | Severe non-IID mean ROC-AUC (5 models) | Paired mean difference |
|---|---:|---:|---:|
| Maximum confidence | 0.4935 | 0.4876 | −0.0059 |
| Negative entropy | 0.5011 | 0.5043 | +0.0033 |
| Top-two margin | 0.4949 | 0.4894 | −0.0055 |

The sample has 60 members and 60 nonmembers per checkpoint. A 1% false-positive operating point has coarse resolution: even one false positive exceeds it. The three heuristics are weak and the observed AUCs near 0.5 **are not evidence of a privacy guarantee**. No selection of the strongest seed or attack is performed.

Ten checkpoint hashes and manifest hashes are validated against original training evidence. `scripts/verify_balanced_membership.py` independently re-scores all **30 attack evaluations**, checks tensor SHA-256 and validates matched query IDs without exposing them to the attacker. The five-seed uncertainty intervals are exploratory and not sufficiently powered for a confirmatory inference claim.

## Native acceptance gates that remain open

Docker Compose, Flower ServerApp/ClientApp, upstream Flower SecAgg+, OpenDP and Opacus have **not** been executed in this environment; no runtime or DP/secure-aggregation guarantee is claimed. Docker is absent and the Python package index cannot be resolved. The protected Compose overlay and its CI script are ready for a compatible native runner, but YAML/static tests do not prove container isolation. Full 28×28 MNIST and external dataset replication remain future work.

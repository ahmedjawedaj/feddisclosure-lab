# v0.12 native Flower three-institution deployment: execution protocol

## Research assertion

An isolated Flower *Deployment Runtime* can train the existing public-digit
PyTorch model across three separately started institutional containers without
mounting their data into the coordinator or each other's executors. Equal
initialization, optimizer settings, and partitions allow numerical comparison
with the existing independent-worker FedAvg reference.

**Status as of 2026-11-20:** deployment assets and contract tests implemented;
**native execution NOT verified**. Docker CLI/daemon and Flower dependencies are
not installed in the current restricted runtime. No native parity, isolation,
cryptographic protection, or performance claim is made.

## Architecture

- One `flwr/superlink:1.27.0`, running the Deployment Runtime in separate-process isolation mode.
- One custom `serverexec` running Flower's upstream ServerApp plugin, mounting
  only the server artifact folder. The coordinator sees model updates and
  metrics, not raw institutional rows.
- Three separate `flwr/supernode:1.27.0` instances, each with a different
  node-config `partition-id`, connected to the SuperLink.
- Three separate `clientexec-{0,1,2}` Flower SuperExec processes. Each receives
  **one and only one read-only bind mount** (`/site`) plus its own append-only
  client-event output directory (`/attestation`). Per-site SHA256 digests and
  site identity are checked when a ClientApp trains or evaluates.
- An optional one-shot `flwr-cli` container, which has neither client data nor
  evaluator truth mounted. It calls `flwr run . fdl-docker --stream` explicitly;
  **the default `local-simulation` profile is never used in native certification**.
- Separate host-controlled public test set and evaluator. This is intentionally
  not mounted by any Flower service. The reference runner uses the evaluator
  only in its own process after the native run.

The whole stack uses local insecure transport and is ONLY for a trusted
single-host research sandbox. Multi-host operation requires TLS, authentication,
external access policies, a privacy assessment and additional tests.

## Run on a clean Ubuntu Docker host

Requires: Docker Engine, Compose v2, Python 3.12, internet for pinned images and
public package indexes; sufficient CPU RAM/disk for PyTorch CPU images.

```bash
python -m pip install -e '.[test]'
python -m pip install --index-url https://download.pytorch.org/whl/cpu 'torch==2.5.1'
python -m pip install 'scikit-learn>=1.4,<2' 'numpy>=1.26,<3'
python scripts/verify_flower_topology.py
python scripts/run_flower_docker.py --prepare-only
python scripts/run_flower_docker.py
python scripts/run_torch_reference.py \
  --config configs/training/fedavg_digits_iid.yaml \
  --data-dir data/training/digits-docker-iid-v012 \
  --output reports/results/native_flower/v012/torch_reference.json
python scripts/verify_flower_parity.py \
  --flower-dir reports/results/native_flower/v012/server \
  --reference-json reports/results/native_flower/v012/torch_reference.json \
  --reference-checkpoint reports/results/native_flower/v012/checkpoints/digits-iid-smoke-v1_final.pt \
  --manifest data/training/digits-docker-iid-v012/manifest.json \
  --output reports/results/native_flower/v012/flower_parity.json --require-deployment
```

Use a fresh `--run-dir` and `--env-file` for independent repeats. The
preparation script refuses accidental reuse of a different dataset and refuses
mismatched or tampered NPZ files. Do not modify the evidence files to force a
pass. To inspect container failures, pass `--keep-running` and use
`docker compose --env-file .env.flower.generated -f compose.flower.yaml logs`.
Remember to stop the containers afterwards; do not publish them to a network.

## Evidence and acceptance

For a **passed native deployment gate**, require ALL of the following:

1. Native runner exits 0 and `flower_run.json.native_flower_verified=true`.
2. Actual `docker inspect` output confirms **eight independent running Flower
   containers** (SuperLink, ServerApp executor, three SuperNodes, three ClientApp
   executors), no published ports and a shared dedicated network.
3. ClientApp executors have three *different* site data mounts, all read-only;
   no coordinator, SuperNode or CLI service has a site dataset mount.
4. All three institutional ClientApps emit actual `train` receipts for *each*
   required round and at least one evaluation receipt, linked to one native
   Flower run ID, correct hashes and local sample counts.
5. ServerApp stores real model checkpoint and serialized run summary.
6. Exact same public-digit split, seed, model initialization, local SGD schedule
   and aggregation weights run through independent-worker PyTorch.
7. Strict `--require-deployment` parity report has
   `verified_numerical_parity=true` for all tensors and the expected tolerance.
8. CI job succeeds with downloadable logs and artifacts; failures and timeouts
   are retained rather than counted as passes.

The runner's metadata and ClientApp receipt JSON files are **audit evidence, not
cryptographic remote attestation**. Site filesystem isolation is a verified
container mount boundary on a trusted host, not a guarantee against a host-root
adversary or an untrusted Docker daemon. A model-update observer can still
observe individual updates in this FedAvg baseline. It is neither DP nor
SecAgg+.

## Known concerns for native bring-up

The underlying Flower version is pinned to 1.27.0. The SuperExec image, CLI
profile, `--plugin-type`, `--appio-api-address` and process-isolation flags
follow Flower 1.27's official deployment documentation. The exact container
images and flags still need the first actual Docker run and may require fixes.
If the Flower strategy drops a node or fails its minimum-three threshold,
retain the failure. Do not reduce the client count to disguise the problem.

Official upstream references:
- https://flower.ai/docs/framework/1.27/en/docker/tutorial-quickstart-docker.html
- https://flower.ai/docs/framework/1.27/en/docker/tutorial-quickstart-docker-compose.html
- https://flower.ai/docs/framework/1.27/en/how-to-run-flower-with-deployment-engine.html
